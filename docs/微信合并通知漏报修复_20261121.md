# 微信连发两条起不再告警：合并通知被整条跳过（2026-11-21 修复）

> 版本：`1.0.0-rc2` / `versionCode 3`。发现者是用户真机实测，不是我们测出来的。
> 现场照片：`docs/img/realdevice/rd05` ~ `rd08`。

## 一、现象

用户在真机上连发三条同一条微信诈骗话术，结果：

| 第几次 | 通知栏形态 | 银盾反应 |
|---|---|---|
| 第 1 次 | 单条：`-zzz～y / 我临时遇到急事，不方便打电话，先转300到这个卡号：` | ✅ 主界面弹提示（没拍到） |
| 第 2 次 | 合并：`[2条]-zzz～y：我临时遇到急事，不方便打电话，先转300…` | ❌ 什么都没弹 |
| 第 3 次 | 合并：`[3条]-zzz～y：4.【招聘兼职】线上数据录入，…` | ❌ 什么都没弹 |

照片：`rd05`（通知栏，单条）、`rd06`（锁屏横幅，`[2条]`）、`rd07`（桌面横幅，`[3条]`）、
`rd08`（通知栏，`[3条]`）。

## 二、根因：一段"多条合并就跳过"的分支，前提是错的

`NotiGuard.java` 原第 281 行：

```java
// 【2026-11-16 加】同一个会话连来好几条时，微信的通知正文会变成
// "2 条新消息"这类汇总文案，真正的消息内容不在里面。
// 拿这句话去判词库，得出的结论毫无意义（还可能是高分），
// 所以直接跳过 —— 等它展开成具体内容时，下一条通知会带正文。
if (body.matches("^\\d+\\s*条新消息.*$") || body.matches("^\\[\\d+条\\].*$")) {
    Log.i(TAG, "微信通知是多条合并（" + body + "），跳过判定");
    return;
}
```

这段是 11-16 联调时为修另一个问题加的（当时发现"2 条新消息"被拿去判词库，判出高分）。
**它的前提"合并时没有真内容"在华为 EMUI 上不成立**：

```
[2条]-zzz～y：我临时遇到急事，不方便打电话，先转300到这个卡号：
[3条]-zzz～y：4.【招聘兼职】线上数据录入，日结300
        ↑ 前缀                ↑ 就是原话，"4." 是第几条
```

前缀后面是**完整的一句真话**，被 `^\[\d+条\]` 整条吃掉了。

用旧正则跑一遍，两条都被跳过（`交付包/_outbox/verify/OldLogic.java`）：

```
旧逻辑→跳过判定  [2条]-zzz～y：我临时遇到急事，不方便打电话，先转300到这个卡号：
旧逻辑→跳过判定  [3条]-zzz～y：4.【招聘兼职】线上数据录入，日结300
旧逻辑→跳过判定  3 条新消息
```

## 三、为什么这个 bug 特别坏

1. **骗子催钱就是连发。** 第一句弹了提示，老人也许正好没看手机；第二、三句催得更急，
   银盾反而一句话不说。**最需要提醒的时刻闭嘴。**
2. **静默没有任何外部迹象。** logcat 里只留一行"微信通知是多条合并…跳过判定"，
   界面上、子女端上全是空白，不做真机实测根本发现不了。
3. 它伪装成"合理的设计"——注释写得很像深思熟虑过的取舍，所以 11-16 加进去后，
   四轮回归都没人怀疑这一行。

## 四、修法

新增 `stripMergeWrapper()`，只跳过**真正没有内容**的那种：

| 输入 | 判不判 |
|---|---|
| `[2条]-zzz～y：我临时遇到急事…` | ✅ 剥成 `我临时遇到急事…` 照判 |
| `[3条]-zzz～y：4.【招聘兼职】…` | ✅ 剥前缀 + 去序号后照判 |
| `3 条新消息` | ❌ 确实没内容，跳过 |
| 单条 `注意：您的快递已到驿站` | ✅ 原样返回，**一个字符都不改** |

三个细节：

1. **单条通知不做任何处理就返回。** 只有真剥过 `[N条]` 包装的才走冒号逻辑，
   否则会把"注意：您的快递已到"这种正文的前半句切掉。
2. **只取第一个冒号后的内容。** 发件人在 `EXTRA_TITLE` 里已经有一份，正文里重复的那次
   没必要再判；而且备注名带"财务""客服"很常见，拿昵称去判会白白加分（真机那个备注名
   `-zzz～y` 就属于这类噪声）。
3. **冒号必须在前 24 个字内**，否则说明这个冒号属于正文本身（`卡号：6222 0000 1111`）。

改动范围：判定（`judgeSms`）、验证码检测（`looksLikeCodeRequest`）、群消息判定
（`looksGroupMessage`）、子女端推送文案全部改用剥离后的 `judgeBody`；
**去重指纹仍用原始 `body`**（前缀不同就是不同通知，不能混）。

## 五、验证

### 1. 纯逻辑：12 条用例全过

`交付包/_outbox/verify/StripTest.java`，12 pass / 0 fail，覆盖：

- 真机那两种真实格式（必须判出）
- 回归：单条含冒号正文、`注意：`开头、普通聊天（必须原样）
- 纯汇总 `3 条新消息` / `12条新消息`（必须空）
- 群消息合并 `[2条]家庭群：张三：…` → 只剥一层，剩 `张三：…`
- 边界：空串、只有前缀、`[2条]张三：`、冒号在很后面

### 2. 端到端：模拟器实跑，四条全部判出

把假微信壳改成模拟真微信的合并行为（同一通知 ID + `[N条]昵称：` 前缀）后重跑：

```
00:08:12 微信消息 from=张主任 分数=50 阶段=S1 级别=warn  工号(+20)、社保局(+15)、陌生号码(+15)
00:08:40 微信消息 from=张主任 分数=30 阶段=S2 级别=warn  医保卡(+15)、陌生号码(+15)
00:08:57 微信消息 from=张主任 分数=40 阶段=S3 级别=high  不要告诉(+25)、陌生号码(+15)
00:09:02 微信消息 from=张主任 分数=72 阶段=S3 级别=block 逾期(+15)、注销(+12)、含链接(+20)、
                                                        停用通知带链接(+15)
```

第 2/3/4 条在旧逻辑下全部会被跳过。**分数与单条时完全一致**（50/30/40/72），
说明剥离前缀没有改变判定结果，只是让它能进判定。

### 3. 界面侧：首页"今日检测"对上了

`4 条消息 / 4 次预警` —— 修复前只会是 `4 条消息 / 1 次预警`（后三条被跳过）。

## 六、仍然存在的边界（要如实说）

1. **合并通知只带最后一条的正文。** 如果某条消息来时银盾正在被杀/被冻结，
   它那一版通知被下一条覆盖后，就再也判不到了。这是系统只给一份正文决定的，
   不是这次能修的。
2. **有些 ROM 只给"你收到一条新消息"。** 这种连内容都没有，判不了。
   依赖微信里「我 → 设置 → 消息通知 → 通知显示消息详情」打开（`docs/真机验证清单.md` 已记）。
3. **本次只验证了 EMUI 的格式。** 小米/OPPO/vivo 的合并格式没实测过，
   如果它们用别的写法（比如"2 个联系人发来消息"），需要照着真机日志再补一条规则。

## 七、顺带改的：假微信壳现在会"真合并"

原来壳用 `NOTI_ID + idx` 让每条通知独立，于是演示永远看不到合并形态，
**这个 bug 在模拟器上不可能被复现**——这也是它活到现在的原因。

现在壳改成真微信的行为：同一通知 ID（覆盖）+ 连发时自动加 `[N条]昵称：` 前缀。
以后演示"连发两条"，看到的就是真机上的那副样子。

## 八、验收步骤（真机）

1. 装 `银盾_v1.0.0-rc2_20261121-0011.apk`（覆盖安装，权限保留）；设置面板底部应显示
   `v1.0.0-rc2`。
2. 让队友连发三条微信（单条 → 两条 → 三条），每条都应弹浮条、子女端都应收到。
3. 首页"今日检测"的"次预警"应与消息条数一一对应。
4. 若第三条判到 block（要钱/要码/含链接），通知栏那条微信通知应被撤掉。
