## 三、迁移数据（在旧服务器 123.249.25.139 上做）

### 3.1 先备份（不能省）

```bash
sudo mysqldump -u root -p --databases yindun > /root/yindun_backup_$(date +%F).sql
ls -lh /root/yindun_backup_*.sql
```

备份文件再 scp 一份回自己电脑（`scp ops@123.249.25.139:/root/yindun_backup_*.sql .`），别只放服务器上。

### 3.2 导入顺序

**【改】顺序很重要，写反了会白折腾一下午。**

你原来写的顺序是「先跑 schema.sql + migrate → 最后导 dump」。问题在 `mysqldump --databases`
导出的文件里带 `DROP TABLE IF EXISTS`：最后一步导 dump 会把前面刚建好的表**全删掉按 dump 重建**，
前面跑的迁移全部作废。今天这份 dump 因为来自已经迁移过的库，结构碰巧一致，看不出问题；
换成更老的 dump 就是「服务启动报缺列」，而且报错完全不指向迁移顺序。

正确顺序（四步，一步都不能少）：

```bash
RDS=<RDS内网地址>
U=<管理员账号>

# 1. 只建库，不建表
mysql -h $RDS -u $U -p -e "CREATE DATABASE IF NOT EXISTS yindun CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;"

# 2. 先导旧库（表结构 + 数据一起进来）
mysql -h $RDS -u $U -p yindun < /root/yindun_backup_2026-11-XX.sql

# 3. 补新版本才有的表（IF NOT EXISTS，已有的不动）
mysql -h $RDS -u $U -p yindun < /opt/yindun/sql/schema.sql

# 4. 跑迁移 —— 两个都要，都可重复执行
mysql -h $RDS -u $U -p yindun < /opt/yindun/sql/migrate_20261110_callaudio.sql
mysql -h $RDS -u $U -p yindun < /opt/yindun/sql/migrate_20261111_event.sql
```

**【改】原来漏了第一个迁移文件。** `sql/` 下有三个文件，你只写了两个：

| 文件 | 作用 | 漏了会怎样 |
|---|---|---|
| `schema.sql` | 建表 | — |
| `migrate_20261110_callaudio.sql` | `yd_report.reporter` 的 ENUM 加 `callaudio` | **不报错**，录音复盘的上报会被 MySQL 截断成空串，数据静默丢 |
| `migrate_20261111_event.sql` | `yd_alert` 加 `call_id` / `kind` | 事件回放取不到数据 |

第三个是「静默丢数据」型故障，比报错难查十倍。三个都跑。

### 3.3 核对

```bash
mysql -h $RDS -u $U -p yindun -N \
  -e "SELECT 'alerts',COUNT(*) FROM yd_alert UNION ALL SELECT 'reports',COUNT(*) FROM yd_report;"
# 必须是 alerts 428 / reports 32（以你 〇-1 记下的数字为准）
```

### 4.1 确认没问题之后，才关本机数据库

**【改】这里要多一步，不然停不掉。**

```bash
sudo systemctl stop mysql redis-server
sudo systemctl disable mysql redis-server
```

停完必须**把 systemd 单元里对 mysql/redis 的依赖摘掉**。原因：单元里有

```ini
After=network.target mysql.service redis-server.service
Wants=mysql.service redis-server.service
```

`Wants` 是**显式依赖**，跟 `enable/disable` 没关系。只要这两行还在，**每次 restart yindun
都会把 mysql 和 redis 重新拉起来**：白吃四百多兆内存，旧库还在被写，迁移就不算完成。

摘法（跑一次就好，脚本会自动探测本机还有没有这俩服务）：

```bash
cd /opt/yindun && sudo bash install.sh
# 会打印「本机没有 mysql/redis 服务，单元只依赖 network」或「检测到本机数据库服务」
```

**⚠️ 但注意**：`install.sh` 第 5 步会 `rsync` 覆盖 `/opt/yindun` 的代码。
**只在确认它跑的是仓库最新代码时才用**——你现在手上那份代码快照是 11-18 之前的，
直接跑会把线上刚上线的规则 3.6（220 词）打回 3.4（212 词）。

安全做法，手动改一行就够：

```bash
sudo cp /etc/systemd/system/yindun.service /root/yindun.service.bak
sudo sed -i 's/^After=.*/After=network.target/; /^Wants=/d' /etc/systemd/system/yindun.service
sudo systemctl daemon-reload && sudo systemctl restart yindun
sudo systemctl status mysql redis-server   # 应该是 inactive / disabled，且没被拉起来
```

**截图 8**：`systemctl status mysql redis-server` 显示 stopped/disabled，且 `systemctl status yindun` 仍 active。

## 五、第三阶段：新机器部署 + 录屏（等队长说「代码冻结」打 tag 之后再做）

1. 发给码道智能体：

   > 帮我开通一台按需计费的 ECS：2核4G、40G 系统盘、1M 按流量带宽、Ubuntu 22.04，
   > 放在 vpc-default / subnet-default，绑一个新建的安全组（入方向只放 22 端口给我的 IP）。

2. **【改】新机器上 `.env` 不能照抄旧机器的**

   旧机器的 `RDS_HOST=127.0.0.1`（因为库就在本机）。抄到新机器，新机器会去连自己的 localhost，
   连不到任何东西。表现是服务照常启动、`health` 里 `rds:false`，看起来"部署成功"，其实数据全在内存里。

   新机器 `.env` 必须是：

   ```ini
   RDS_HOST=<RDS 内网地址>      ← 不是 127.0.0.1
   REDIS_URL=redis://:<密码>@<Redis 内网地址>:6379/0
   ```

   并且**新机器的内网 IP 要先加进 RDS 安全组的 3306 白名单**（见第一节末尾）。
   验收只有一条：`health` 里 `rds:true` + `redis:true`，且重启后告警记录还在。

3. **【改】用仓库里的 `deploy/install.sh`，不要用你本地那份**

   你原来的脚本第 8 步固定写 `After/Wants=mysql.service redis-server.service`，
   在新机器上会引用两个不存在（也不需要）的单元。仓库版改成了运行时探测，本机没有就不写。

   录屏开始（**从「裸机没装 Node」录起**，一直录到浏览器打开子女端网页）：

   ```bash
   scp 本机 deploy/install.sh ops@<新机器IP>:/root/
   ssh ops@<新机器IP>
   sudo bash /root/install.sh --repo https://github.com/6fvmtyymc9-sketch/yindun.git
   # 我实测过从 ECS 访问 github.com 是通的（200 / 0.86s），这条能走
   # 私有仓库要凭证；走不通就改用 --src（先把 cloud/ scp 上去）
   ```

   脚本最后会打印 **规则版本号**，录屏时让它出现在画面里：「3.6 · 关键词 220 条」——
   这是三秒内能自证"部署的是哪一版"的凭据。

4. 演示数据：从旧机器导一份过去，否则子女端页面是空的。
5. **如实说明**：`sft.enabled` 会是 `false`（专用模型不在云端，靠队长那条隧道），
   汇报说「模型服务待接入」，不要伪造成功状态。
6. **演示完把 ECS 实例删掉**（不是停止！按需实例停止仍收存储费）。
