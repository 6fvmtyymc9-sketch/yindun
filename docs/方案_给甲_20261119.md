## 1. 开通实例（如果还没开）

控制台的具体菜单以你看到的为准，下面是**选型要点**，别选错：

**RDS for MySQL**
- 规格：**单机版 2 核 4G** 就够（数据不到 5 MB，峰值是评估时的并发查询）
- 存储：40 GB 起步
- **VPC / 子网：必须和 ECS 选同一个**（这一步选错，后面全白费）
- 端口 3306，字符集 `utf8mb4`
- 账号：可以直接用 `root`，也可以新建 `yindun` 账号只授权 `yindun` 库（更规范，可选）

**DCS for Redis**
- 版本：**基础版 1G 单机**足够（只存会话状态与限流计数）
- **VPC 同上**
- 端口 6379，**开启密码认证**
- 连接串形如 `redis://:<密码>@xxx.dcs.myhuaweicloud.com:6379/0`；
  有些实例要求带用户名 `redis://<用户名>:<密码>@host:6379/0` —— **以控制台给的那串为准**

## 3. 改 `.env`（六行，有两个坑）

### 坑一：键名是 `RDS_PASS`，不是 `RDS_PASSWORD`

写成 `RDS_PASSWORD`，`install.sh` 会拦；就算用别的办法跑通，服务也读不到，
**静默降级成内存存储**，你还以为连上了。

### 坑二：**绝对不能追加同名行**

`cloud/src/env.js` 是这么写的：

```js
if (m && process.env[m[1]] === undefined) process.env[m[1]] = m[2];
```

`=== undefined` 判断 → **同一个键出现两次，取第一个值**。这跟标准 `dotenv` 正好相反
（dotenv 是后者覆盖前者）。

你上午已经踩过一次：用 `>>` 追加了一行 `RATE_REPORT_PER_DAY=3000`，重启后还是 1200。
**这次必须原地改，不能追加。**

```bash
# 3.1 备份
cp /opt/yindun/.env /root/env.bak.$(date +%Y%m%d_%H%M)

# 3.2 每个键必须只有一行
for k in RDS_HOST RDS_PORT RDS_USER RDS_PASS RDS_DB REDIS_URL RATE_REPORT_PER_DAY; do
  echo -n "$k: "; grep -c "^$k=" /opt/yindun/.env
done
```

**有输出大于 1 的**，先清重复（保留最后一行）再往下：

```bash
awk -F= '!/^[A-Z_0-9]+=/{print;next}{a[$1]=$0}END{for(k in a)print a[k]}' \
  /opt/yindun/.env > /tmp/env.dedup && mv /tmp/env.dedup /opt/yindun/.env
```

```bash
# 3.3 原地改值（有该行就替换，没有才追加）
set_kv() {
  k="$1"; v="$2"; f=/opt/yindun/.env
  if grep -q "^$k=" "$f"; then
    sed -i "s|^$k=.*|$k=$v|" "$f"
  else
    printf '%s=%s\n' "$k" "$v" >> "$f"
  fi
}

set_kv RDS_HOST    rm-xxxxxxxx.mysql.rds.myhuaweicloud.com
set_kv RDS_PORT    3306
set_kv RDS_USER    yindun
set_kv RDS_PASS    'RDS密码'
set_kv RDS_DB      yindun
set_kv REDIS_URL   'redis://:DCS密码@xxx.dcs.myhuaweicloud.com:6379/0'

# 3.4 复查
for k in RDS_HOST RDS_PORT RDS_USER RDS_PASS RDS_DB REDIS_URL; do
  echo -n "$k: "; grep -c "^$k=" /opt/yindun/.env
done
grep -E '^(RDS_HOST|RDS_PORT|RDS_USER|RDS_DB)=' /opt/yindun/.env
```

> 密码里如果含 `|`、`&`、`$`，`sed` 会出问题。最稳是**在控制台把密码改成纯字母数字**再填。

## 4. 迁移数据库（四步，**顺序绝对不能换**）

```bash
# 4.1 只建库，不建表
mysql -h <RDS_HOST> -P 3306 -u <账号> -p \
  -e "CREATE DATABASE IF NOT EXISTS yindun CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;"

# 4.2 整个 dump 导进去（表结构 + 数据一起进来）
mysql -h <RDS_HOST> -P 3306 -u <账号> -p \
  --default-character-set=utf8mb4 yindun < /root/yindun_pre_rds_XXXX.sql

# 4.3 补新版本才有的表（IF NOT EXISTS，已有的不动）
mysql -h <RDS_HOST> -P 3306 -u <账号> -p yindun < /opt/yindun/sql/schema.sql

# 4.4 两个迁移脚本，一个都不能漏
mysql -h <RDS_HOST> -P 3306 -u <账号> -p yindun < /opt/yindun/sql/migrate_20261110_callaudio.sql
mysql -h <RDS_HOST> -P 3306 -u <账号> -p yindun < /opt/yindun/sql/migrate_20261111_event.sql
```

**为什么顺序不能反**

`mysqldump --databases` 导出的文件里带 `DROP TABLE IF EXISTS` 和 `CREATE DATABASE IF NOT EXISTS`。
**先建表、再导 dump，等于把刚建好的表再删一遍**，按 dump 里的旧结构重建；
换成更老的 dump 就会「服务启动报缺列」。

**4.4 那两个脚本漏了会怎样（都是静默的，不报错）**

| 漏跑 | 后果 |
|---|---|
| `migrate_20261110_callaudio.sql` | `yd_report.reporter` 的 ENUM 没有 `callaudio` → **录音复盘的上报被 MySQL 截断成空串，数据直接丢** |
| `migrate_20261111_event.sql` | `yd_alert` 缺 `call_id` / `kind` → **事件回放失效** |

两个脚本都能重复执行，跑两遍不会出事。

## 5. 切流（顺序有讲究）

```bash
# 5.1 先停本机库 —— 停掉之后没法再往旧库写，也让出约 400MB 内存
systemctl stop mysql redis-server 2>/dev/null || systemctl stop mariadb redis 2>/dev/null || true

# 5.2 再重启应用（此时只能连 RDS/DCS，连不上会降级内存并打警告）
systemctl restart yindun
sleep 6
systemctl status yindun --no-pager | head -12
```

**为什么先停库再重启**：反过来，服务会先连旧库、再连新库，中间那几秒来了上报就写进即将被丢弃的旧库。

```bash
journalctl -u yindun -n 40 --no-pager | grep -Ei "RDS|Redis|存储|连接"
```

正常应该是：

```
[RDS] 连接成功
[Redis] 连接成功
```

出现「连接失败，降级内存」就先别往下走：

| 报错 | 大概率原因 |
|---|---|
| `ETIMEDOUT` | 白名单 / VPC 没配（第 0 节第 3 条） |
| `Access denied` | 账号或密码错，或该账号没有 `yindun` 库权限 |
| `ER_BAD_DB_ERROR` | 库还没建（4.1 没跑） |
| `Connection is closed`（Redis） | 密码错，或连接串格式不对（要不要用户名） |

## 6. 验收（三条硬标准，一条不满足就不算成功）

把核对脚本放上去（我直接发你文件）：

```bash
mkdir -p /opt/yindun/tools
# scp check_storage.js 到 /opt/yindun/tools/
node /opt/yindun/tools/check_storage.js \
  --expect alerts=<基线>,reports=<基线>,drills=<基线>,events=<基线> \
  --forbid-local
```

脚本**只读**，不写任何东西。它输出 MySQL/Redis 版本、四张表条数，
以及两个最容易漏的列检查（`reporter` 有没有 `callaudio`、`yd_alert` 有没有 `call_id`/`kind`）。

**三条硬标准**

| # | 标准 | 为什么 |
|---|---|---|
| 1 | `--forbid-local` 通过 | 证明连的不是本机库。**`health` 里的 `storage.rds:true` 证明不了这件事**，连 127.0.0.1 也是 true |
| 2 | 四条与 2.3 节基线**逐项相等** | 一条不差才算导全 |
| 3 | **重启一次后数据还在** | `systemctl restart yindun` 再查一遍 —— 这条才证明真读 RDS，不是内存 |

```bash
# 第 3 条
systemctl restart yindun && sleep 6
node /opt/yindun/tools/check_storage.js --expect alerts=<基线>,reports=<基线>

curl -s http://localhost:8080/api/health | grep -o '"storage":{[^}]*}'
# 期望 {"rds":true,"redis":true}
```

`check_storage` 输出、`health` 的 storage 字段、重启前后各一次的条数。

## 7. 出问题怎么回滚（三条路，都很快）

| 情况 | 怎么回 |
|---|---|
| `.env` 写错（键名/密码/连接串） | `cp /root/env.bak.XXXX /opt/yindun/.env && systemctl restart yindun` |
| RDS 连不上、一时查不出原因 | ①`.env` 改回 `RDS_HOST=127.0.0.1`、`REDIS_URL=redis://127.0.0.1:6379/0`；②`systemctl start mysql redis-server`；③`systemctl restart yindun`。**本机库一直没删，是完整回滚副本** |
| 数据导歪了 | dump 还在 `/root/yindun_pre_rds_*.sql`，重跑第 4 节四步（dump 自带 DROP，会自己重建） |

**绝对不要做**：`DROP DATABASE yindun`（本机那份是唯一回滚副本）；
对 RDS 上的表做 `ALTER`（表结构以 `sql/schema.sql` 和两个 migrate 为准）。
