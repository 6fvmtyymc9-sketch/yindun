## 一、结论先行

**做了，跑通了，结果是"局部成功、整体泛化失败"。**

| 老师定的成功判据 | 目标 | 实测 | 判定 |
|---|---|---|---|
| CGoDial 留出 300 通正常，误报 | 降到两成以下 | **1 / 300（0.33%）** | ✅ 达成，且远超目标 |
| holdout 诈骗召回 | ≥ 19/20 | **20 / 20** | ✅ 达成 |
| 30 通真人录音正常，误报 | 要下降 | **10/15 → 15/15** | ❌ **反向恶化** |

一句话解释这个矛盾：**模型学会的是"政务热线那种文风"，不是"什么不算诈骗"。**

三条判据里前两条是在**与训练数据同源**的分布上测的，第三条是真实分布。同源分布上的巨大改善掩盖了泛化能力的退化——这正是必须先看第三行才能下结论的原因。

**不能因此说 LoRA 无效，也不能说它有效。** 准确的表述是：

> 在训练数据同源的分布上，LoRA 把正常样本误报从 82.0% 压到 0.33%，证明"模型有能力学会说不"；但在训练数据没覆盖的分布（短短信、真人电话口语转写）上，模型出现模式塌缩，一律输出「是」，误报反而比微调前更高。根因是训练数据正常侧只有单一来源与单一文体，模型走了"认文风"的捷径。

## 二、训练做了什么

### 2.1 数据

用 `tools/build_judge_data.py` 生成，脚本从 `tools/sft_server.py` 直接 import 提示词，**训练与推理的 prompt 一字不差**。

| 集合 | 条数 | 正负 | 来源 |
|---|---|---|---|
| train | 1,900 | 诈骗 952 / 正常 948 | 正常：CGoDial `real` 政务热线 ASR；诈骗：`Telecom_Fraud_Texts_8` 五个类别 |
| val | 100 | 均衡 | 从 train 切 5% |
| heldout_cgodial | 300 | 全正常 | CGoDial 按场景配额留出（gov 200 / 交管 40 / etc 40 / 珠宝 20） |
| **leak_check** | — | — | **0**（文本级去重，防止 CGoDial 常见开场白造成 id 不同的重复泄漏） |

诈骗五类取自 `Telecom_Fraud_Texts_8`（`tools/build_fraud_texts.py`，可复现）：冒充公检法 1,565、贷款征信 1,218、客服退款 1,502、冒充熟人 1,426、刷单返利 3,416，合计 9,127 条，按 `--per-class` 抽样。

**这里已经埋下了本实验最大的缺陷**：正常侧 100% 是政务热线长对话（100~800 字、客服腔、ASR 连续文本），诈骗侧 100% 是短信短文本。两侧的**文体与长度分布完全错开**。

与原始 `AntiFraud-SFT/args.json` 对齐（除了学习率）：

| 参数 | 值 | 与原模型对比 |
|---|---|---|

| `lora_rank` / `alpha` | 32 / 32 | 同 |

| `loss_scale` | **last_round** | 同（只对第二轮"结论"算 loss，不学人造的场景标签） |

可训练参数 **7,995 万**（占全模型 0.94%）。

### 2.3 训练结果


## 四、根因：模式塌缩 + 认文风

### 4.1 塌缩的直接证据

30 通真人录音（文字模式）里，LoRA 只输出了 **5 种不同的 reason**，其中 17 条是同一句：

```
17× 冒充老师、领导或亲友，以代购、垫付、急用钱为由要求转账
 4× 以点赞、刷单、做任务返利为名，诱导下载软件或先垫付资金
 3× 冒充平台客服，以退款、理赔为名诱导操作账户或提供验证码
```

而 base 模型在 CGoDial 300 条上给出 **293 种不同 reason**。塌缩是微调引入的，不是原模型的问题。

### 4.2 机理

1. 训练集正常侧 100% 是 CGoDial 政务热线：长、客服腔、ASR 连续、无口语碎片。
2. 训练集诈骗侧 100% 是短信：短、模板化、必含索款或链接。
3. 在只有两类、且两类在**长度和文体上完全可分**的数据上做 SFT，最小化 loss 的最短路径是学"长文客服腔 → 否，短句 → 是"，而不是学诈骗语义。
4. 真实分布（老人收到的短信、家里人的电话）恰好落在"短句"一侧 → 一律判是。

**这不是 LoRA 的失败，是训练数据构建的失败。** 与 11-20 那次"SFT 恒答是"的性质不同：那次是负样本答案没进 loss（数据标注缺陷），这次是负样本进了 loss 但分布太单一（数据覆盖缺陷）。

### 4.3 为什么 CGoDial 上看起来完美

CGoDial 留出 300 条与训练集**同源**：同一批政务热线、同一套 ASR 输出、同样的客服腔。模型在上面 99.7% 判否，本质是**认出了熟悉的文体**，而不是判断出"这不是诈骗"。

所以"误报降到 0.33%"这个数字，**只能说明模型能拟合训练分布，不能说明它具备反诈判别力**。任何把这一行单独摘出来宣传的写法都是不诚实的。

## 五、复现方式

```bash
# 0. 数据集（本地生成，可复现）
python tools/build_fraud_texts.py --src <Telecom_Fraud_Texts_8 目录> --out fraud_texts.jsonl
python tools/build_judge_data.py --cgodial cgodial_flow_dialogs.jsonl --extra fraud_texts.jsonl \
    --out data --per-class 1000        # 自带 leak_check

# 1. 训练（会自动停推理服务腾显存）
bash tools/train_lora.sh

# 2. 加载 LoRA 到 8001 并重测（自动取最大 checkpoint）
bash tools/eval_lora.sh

# 3. 单独跑音频
python tools/eval_audio.py --url http://127.0.0.1:8001 --dir audio --out eval/lora_audio.jsonl --workers 3
```

环境：`~/venv-swift/bin/python3`（swift 3.12.6 / transformers 4.48.3 / torch 2.3.1 / peft 0.18.1）。系统 python 没有 peft，加载 LoRA 必须用 venv-swift。

## 六、下一步建议（给老师）

**在补数据之前，不要再做全量重训。** 同样的数据换更大 epoch 只会让塌缩更重。

按性价比排序：

1. **给正常侧加两个来源**（成本最低、收益最大）
   - 短信正常侧：`Telecom_Fraud_Texts_8` 的 `label0` 有 **17,048 条营销/通知短信**，与我们 holdout 的分布接近，直接可用
   - 通话正常侧：把 30 通评估集的**同类另录**数据（或 CGoDial 之外的场景，如快递、外卖、医院回访）补进来
   - 目标：正常侧至少 3 种来源、长度覆盖 10~800 字

2. **按长度分层抽样**，保证"短正常"与"短诈骗"、"长正常"与"长诈骗"都有样本，打断"长度→标签"的捷径

3. **加一个反捷径检查**（写进评测脚本）：分别统计短文本（<60 字）和长文本（≥60 字）上的误报率，若两者差距 >30 个点，说明模型仍在认文风

4. 数据补齐后重训，仍用同一份 CGoDial 留出 300 + holdout 35 + 30 通真人录音三套一起验，**三套都过才算过**

**关于线上**：本轮结果不支持接入。`SFT_URL` 继续留空，理由从"未验证"更新为"同源分布可拟合、真实分布误报 100%，需补数据后重测"。

## 七、边界说明（引用数字时必须连带引用）

1. **训练 loss 0.0013 不代表模型好**，本实验就是反例，任何汇报都不要单独引用 loss。
2. **CGoDial 300 条与训练集同源**，0.33% 不能当作泛化能力。
3. **30 通真人录音样本极小**，15 条正常里多错 5 条就是 33 个点的差异，只能定性说"恶化"，不能报具体提升/下降百分比。
4. **本轮只训了 1,900 条、2 个 epoch**，未做超参搜索；结论只针对这组配置。
5. **音频与文字模式的结论一致**（都是 15/15），说明瓶颈不在音频通道，而在数据分布——这一点很重要，它排除了"必须用音频才能判"的另一种解释。
6. **不能说"LoRA 无效"**：同源分布上 82%→0.33% 是真实的，模型确实学会了说"否"，只是学错了依据。
