## 一、结论先行

**三轮都跑完了。第三轮是一次真实的权衡，不是一次胜利：误报被彻底解决（真人通话两个口径全部清零、CGoDial 0/300），但召回同时下降（holdout 16/20、音频 13/15）。按老师"必须同时满足"的五条判据，第三轮没有通过，所以线上继续用原始模型。**

| 老师定的成功判据 | 目标 | base | v1 纯长对话 | v2 混短信 | **v3 三源混合** |
|---|---|---|---|---|---|
| holdout 诈骗召回 | ≥ 19/20 | 20/20 | 20/20 | 17/20 | **16/20** ❌ |
| 真人录音诈骗召回（文字） | 15/15 | 15/15 | 15/15 | 15/15 | **15/15** ✅ |
| 真人录音诈骗召回（**音频**） | 15/15 | 15/15 | 15/15 | 15/15 | **13/15** ❌ |
| 真人正常·模型结论误报 | < 10/15 | 10/15 | 15/15 | 11/15 | **0/15** ✅ |
| 真人正常·**p≥0.85** 误报（音频 / 文字） | 保持 0/15 / 2/15 | 0/15 · 2/15 | 15/15 · 15/15 | 8/15 · 11/15 | **0/15 · 0/15** ✅ |
| CGoDial 留出 300 误报 | 保持低位 | 246/300 | 1/300 | 1/300 | **0/300** ✅ |

> 上表"召回/误报"除标注 p≥0.85 的那一行外，都是**模型自己给出的结论**（`is_fraud`）口径；两个口径的完整对照见 §7.5。

**第三轮做对了什么**：误报问题在两轮里越修越差（p≥0.85 口径音频 0→15→8），第三轮直接压到 **0/15**，且不是靠"筛"出来的——模型自己给的结论就是 0/15。CGoDial 也从 1/300 到 **0/300**。文字模式召回满分 15/15。

**第三轮做错了什么**：诈骗召回同步下滑。holdout 从 20/20 掉到 **16/20**（漏 4 条），音频模式漏 2 条刷单返利。**漏报在反诈场景里比误报严重得多**，所以不能因为误报清零就算成功。

**判定：不通过。** 老师五条判据里"诈骗不漏"排第一，第三轮恰恰在这一项没做到。按老师事先约定（§7.8），到此停止调参，线上继续用原始模型。

**四条不能说的话**：

1. 不能说"LoRA 无效"——三轮都证明它确实能改变判定行为，CGoDial 246/300 → 0/300 是真实的。
2. 不能说"第三轮成功了"——误报清零的代价是漏 4 条短信诈骗、漏 2 通刷单电话，按判据就是不通过。
3. 不能说"v2 比原始模型好"——按 p≥0.85 明显更差（音频 0/15→8/15、文字 2/15→11/15），这个更正见 §4.4。
4. 不能只报"模型结论"一个口径——线上融合用的是 p≥0.85，只报前者等于藏起对 LoRA 不利的那一半事实。

### 1.1 前两轮的结论（历史记录，别和第三轮混在一起读）

- **v1（正常侧只有 CGoDial 长对话）**：模式塌缩。同源 246/300 → 1/300，但真人录音正常 15/15 全判是，30 条只输出 5 种理由。根因是正常侧只有一种文风，模型学会"认文风"而不是"认诈骗"。
- **v2（正常侧混入一半营销短信）**：塌缩消失、回到基线。holdout 正常 13/15 → 6/15，但按线上口径（p≥0.85）音频 0/15 → **8/15**、文字 2/15 → **11/15**，明显差于 base。

**这是本报告最重要的一处更正：按线上口径（p≥0.85），v2 不是"略好"，而是明显更差。**

- 音频正常误报：原始模型 **0/15** → v2 **8/15**
- 文字正常误报：原始模型 **2/15** → v2 **11/15**

而这两个口径在 v2 里几乎完全重合（音频 8/15 与 8/15、文字 11/15 与 11/15），因为判定为"是"的样本 p 值全部落在 0.9。原因是那一版数据脚本把训练答案的置信度写死成 0.9（正常侧写死 0.1），模型于是学会了"永远报 0.9"，p 值失去区分度。机理见 §4.4，第三轮已修正这一点（p 分布变成 0.03/0.06 与 0.85~0.98 两簇）。

## 四、第一轮的根因：模式塌缩 + 认文风

### 4.1 塌缩的直接证据：判定结果，不是理由种数

30 通真人录音里，15 条**正常**通话被**全部判为诈骗（15/15）**，同时 15 条诈骗也全部判为诈骗（15/15）。文字模式与音频模式完全一致。这不是"判错了一部分"，而是**对这一段分布彻底失去分辨能力**，全部输出"是"，这才是塌缩的硬证据。

> **更正：理由（reason）的种数不能当证据。**
> 本报告初版曾把"30 条只输出 5 种 reason、其中 17 条是同一句"当作塌缩证据，这个推论**不成立**。
> 原因在数据脚本：第一轮的诈骗理由是**按类别套模板**生成的，5 类诈骗就只有 5 句理由（冒充公检法 / 贷款征信 / 客服退款 / 冒充熟人 / 刷单返利各一句）。模型只是在复述它见过的模板句，**5 种恰好等于训练数据里的模板数**，既不能证明它判错了，也不能证明它判对了。
> 同理，"base 在 CGoDial 上给出 293 种 reason"也不能说明 base 更强——那是 CGoDial 原文里自带的多样性。
> **结论：reason 的多样性只反映训练数据的模板丰富度，判定能力必须看 `is_fraud` 与 `p`。** 老师已修正脚本（理由按原文内容生成），第三轮 reason 才重新具备观察价值。

### 4.2 机理

1. 训练集正常侧 100% 是 CGoDial 政务热线：长、客服腔、ASR 连续、无口语碎片。
2. 训练集诈骗侧 100% 是短信：短、模板化、必含索款或链接。
3. 在只有两类、且两类在**长度和文体上完全可分**的数据上做 SFT，最小化 loss 的最短路径是学"长文客服腔 → 否，短句 → 是"，而不是学诈骗语义。
4. 真实分布（老人收到的短信、家里人的电话）恰好落在"短句"一侧 → 一律判是。

**这不是 LoRA 的失败，是训练数据构建的失败。** 与 11-20 那次"SFT 恒答是"的性质不同：那次是负样本答案没进 loss（数据标注缺陷），这次是负样本进了 loss 但分布太单一（数据覆盖缺陷）。

### 4.3 为什么 CGoDial 上看起来完美

CGoDial 留出 300 条与训练集**同源**：同一批政务热线、同一套 ASR 输出、同样的客服腔。模型在上面 99.7% 判否，本质是**认出了熟悉的文体**，而不是判断出"这不是诈骗"。

所以"误报降到 0.33%"这个数字，**只能说明模型能拟合训练分布，不能说明它具备反诈判别力**。任何把这一行单独摘出来宣传的写法都是不诚实的。

### 4.4 p 值失去区分度的原因：训练答案的置信度是写死的

前两轮训练数据里，答案中的 `confidence` 由脚本写死：判"是"一律 **0.9**，判"否"一律 **0.1**。模型于是学会了"永远报 0.9"，从输出分布可以直接看到：

| 结果文件 | p 值分布 |
|---|---|
| v1 真人录音音频（30 条） | 0.9 × 29、1.0 × 1 |
| v1 真人录音文字（30 条） | 0.9 × 30 |
| v2 真人录音音频（30 条） | 0.9 × 23、0.1 × 7 |
| v2 holdout（35 条） | 0.9 × 23、0.1 × 10、0 × 2 |

后果有三层：

1. **两个口径退化成同一个口径。** 凡判"是"的 p 都等于 0.9 ≥ 0.85，所以"模型结论"和"p≥0.85"在 v2 上数字完全相同（音频 8/15 与 8/15、文字 11/15 与 11/15）。看起来"两个口径都报了"，实际只报了一个。
2. **线上那道闸门失效。** 融合规则要求"p≥0.85 才抬分"，本来是用来筛掉模型没把握的判断；p 恒等于 0.9 之后，这道闸门对 LoRA 的输出不再起任何过滤作用。
3. **这正是线上口径下 v2 反而更差的原因。** base 在真人正常通话上的"是"大多不自信（p≥0.85 只有音频 0/15、文字 2/15），而 v2 的"是"全部自信 —— 于是同一条误报，base 被闸门拦下、v2 直接放过。

老师已修正数据脚本：置信度随线索多少变化（诈骗 0.85~0.98、正常 0.03~0.25），理由按原文内容生成。第三轮必须把"p 值是否有区分度"作为训练前的验收项（见 §七）。

## 五、第二轮：按诊断补数据后的对照（验证"根因是不是数据"）

第四节给出的诊断是"训练数据正常侧来源单一"。**这个诊断必须被验证，否则只是猜测。** 于是当天中午立刻做了第二轮：只改一处——正常侧混入营销短信。

### 5.1 唯一变量

| | 第一轮（v1） | 第二轮（v2） |
|---|---|---|
| 正常侧 | **100% CGoDial 政务热线**（长对话，100~800 字） | **50% CGoDial + 50% 营销通知短信**（`Telecom_Fraud_Texts_8` 的 `label0`，17,048 条中可用 11,784 条，中位 85 字） |
| 诈骗侧 | 五类短信，1,000 条 | 完全相同 |
| 数据量 / epoch / 超参 / 留出集 | 1,900 × 2，其余全同 | 完全相同 |
| train_loss / 用时 | 0.1319 / 14.3 min | 0.1353 / 13.9 min |

`label0` 那批是联通、京东等营销短信，含"点击链接""限时""免费领取"这类**与诈骗短信高度相似的词**，只是意图合法——正是我们缺的"像诈骗的正常短文本"。

### 5.3 四个结论

1. **诊断被证实。** 只补正常短信、其余一个字不改，30 通真人录音里判否的正常通话从 **0 条变成 4 条（文字）/ 7 条（音频）**，塌缩不再出现。**所以根因确实是数据分布，不是 LoRA、不是音频通道、不是训练配置。**
   （这里只用判定结果作证据。理由种数不参与论证，原因见 §4.1。）

2. **短信域基本恢复，通话域只是回血——而且只在"模型结论"口径上成立。** holdout 正常（短信）从 13/15 回到 **6/15**，与 base 持平；真人录音音频从 15/15 回到 **8/15**，模型结论口径下比 base 的 10/15 略好。

3. **但按线上口径（p≥0.85），第二轮明显差于原始模型。** 音频正常误报 **0/15 → 8/15**，文字 **2/15 → 11/15**，holdout 正常 **1/15 → 6/15**。原因是训练答案的置信度被写死成 0.9，凡判"是"的 p 都过线，线上那道"p≥0.85 才抬分"的闸门对它完全失效（机理见 §4.4）。**所以"v2 比 base 略好"这个说法只在模型结论口径下、且只在音频一项上成立，不能作为整体结论。**

4. **代价是诈骗召回下降。** holdout 从 20/20 掉到 **17/20**（漏 3 条），这是加入了大量"含链接但不诈骗"的营销短信后，模型对含链接的诈骗变宽松了。真人录音的 15/15 召回没掉。

### 5.4 这说明什么

**方向对了，力度不够，而且这一轮存在两个互相独立的缺陷，必须一起修。**

**缺陷一：数据分布。** 1,900 条、2 epoch 只够把模型从"塌缩"拉回"接近原模型"（模型结论口径），不足以超过原模型。

**缺陷二：答案置信度被写死。** 训练数据把 `confidence` 固定成 0.9/0.1，模型学会了永远报 0.9，p 值失去区分度。这直接导致线上口径下 v2 显著劣于 base（§4.4）。**这个缺陷与前一个无关，即使数据分布完全修好，只要置信度还是写死的，线上口径就依然不可用。**

第三轮的修法（老师 2026-11-23 方案，见 §七）：

1. **补上计划里最关键、前两轮没用上的数据源**：TeleAntiFraud 的**对话文字**，诈骗侧与正常侧都取。它的正常对话里有订餐、快递、打车这类日常电话，正是前一版报告列为"待补"的**通话正常侧多场景**，而这类数据本机已经有了。
2. **用修正后的 `build_judge_data.py` 重新生成**：理由按原文内容生成，置信度随线索多少变化，数据自带理由时优先用自带的。
3. **训练前先验收 `summary.json` 的 answers**，不合格不开训。
4. **训练参数与第二轮完全一致**，在同样三套数据上重测，每项都报两个口径。

**仍然不能说 LoRA 成功。** 准确表述是：**v2 消除了塌缩，但按线上口径明显差于原始模型。** 第三轮的结果见 §7.5~7.8。

### 7.0 TeleAntiFraud 的数据核查（开训前必须记录）

计划第二步要求「先看 sft.zip 里有没有对话文字，没有就用 ASR 转」。核查结果如下，其中第 2 条推翻了按目录名取标签的直觉做法：

1. **`sft.zip` 里没有对话文字，也没有判定理由。** 打包内容只有 `sft/train.jsonl` 与 `sft/test.jsonl`，字段是 `messages / prompts / answers / audios`，没有 `text`、没有 `reason`（33,953 行里带 `reason` 的 **0 行**）。样例是 `<audio>` 占位符 + 任务描述 + 一个标签字符串。→ 文字只能走 ASR；老师要求的「原数据判定理由保留」**在原数据里不存在，无法字面执行**，但我们找到了更有用的东西：逐条真值标签（见第 5 条）。

   > 补一句容易读错的地方：`is_fraud` 字段确实存在（在 `messages` 第二轮 assistant 回答里），但**只覆盖 6 轮结构的 7,177 条，且全为 `true`、全在 `NEG-*` 组**；4 轮结构的 13,388 条第二轮判定**没有 assistant 答案**。所以 `is_fraud` 不能当二分类监督信号（这个结论没错）。**真正可用的二分类标签在顶层 `answers`**：4 轮结构里有 `fraud` 7,177 / `normal` 6,211，另有 7 种场景标签与 7 种诈骗细类。第 5 条就是用它反验的。

2. **`audio.zip` 的目录名 POS / NEG 与内容严格相反（官方真值 100%）。** 共 13,711 条、11 个组。先用关键词命中率量化，后用 `sft.zip` 自带的逐条标签核对，两者方向一致、后者是铁证：

   | 目录 | 条数 | 官方判定标签 | 一致率 | 关键词法（含诈骗话术 / 含日常用语） |
   |---|---|---|---|---|
   | `NEG-*`（名义「正常」） | 7,177 | **fraud 7,177** | **100.0%** | 96.1% / 2.4% |
   | `POS-*`（名义「诈骗」） | 6,211 | **normal 6,211** | **100.0%** | 20.4% / 52.6% |

   **不是「大部分相反」，是零例外地整体互换**——问题出在打包时的目录命名（POS/NEG 两个词被换），数据集本身的标注是干净的。

   原文样例——`POS-*`（目录写"诈骗"，内容其实是租车/订餐/理发预约）；`NEG-*`（目录写"正常"，内容其实是"京东客服包裹丢失办退款""中航科技年化 12% 理财""中信银行无抵押贷款"）。
   → **本轮按内容取用：正常对话取 `POS-*` 组，诈骗对话取 `NEG-*` 组**，依据写在 `tools/taf_to_judge.py` 文件头，完整证据（含核对脚本）见 `cloud/test/lora_20261123/r3/label_inversion_evidence.md`。
3. **转录方式**：`faster-whisper large-v3`（float16），`vad_filter=True`、`beam_size=5`、`language=zh`，约 1.6 s/条（音频均长 55 s）。抽样 20 条人工核对，中文转写质量可用（标点、数字、"下载 APP"等关键词均正确）。脚本 `tools/asr_transcribe.py`。容器系统只有 CUDA 11.6、ctranslate2 要 cu12，需手动指 `LD_LIBRARY_PATH` 到 `/usr/local/lib/python3.10/site-packages/nvidia/{cublas,cudnn}/lib`。
4. **残留问题：个别生成内容偏离了标注意图（不是标错）**。`POS-*`（官方标 normal）里有 **64 条（4.7%）** 文本读起来像营销诱导，典型是"积分商城客服：您的积分今晚 12 点清零"。这类官方仍标 `normal`，因为不索要转账/验证码/不引导下载——是**营销骚扰**而非诈骗。最终 5,000 条里正常侧只用到 834 条，折算约 **39 条（0.8%）**，量级不足以单独解释第三轮的漏报，但可能是"客服类判宽容"的促成因素之一（§7.7）。
5. **用官方真值反验我们自己的训练标签：100% 一致。** 按「组名 + 文件名」把转录结果对回 `sft.zip` 真值：

### 7.2 开训前验收：先看 `summary.json` 的 answers

三条**全部通过**才允许开训，任一不过先修数据：

1. **理由要有几百种**（不再等于模板数；说明理由确实按原文生成）
2. **诈骗样本的 p 落在 0.85 ~ 0.98**（不再恒为 0.9）
3. **正常样本的 p 落在 0.03 ~ 0.25**

> 这一条是第二轮教训的直接产物：上一轮就是没验这一步，训练完才发现 p 值没有区分度，白跑一轮。

**实际验收结果（`cloud/test/lora_20261123/r3/data_summary.json`）**：

| 验收项 | 要求 | 实际 | 判定 |
|---|---|---|---|
| 理由种数 | 几百种 | **2,423 种 / 5,000 条** | ✅ |
| 诈骗 p 区间 | 0.85 ~ 0.98 | **0.85 ~ 0.98**（P10~P90 = 0.872~0.945） | ✅ |
| 正常 p 区间 | 0.03 ~ 0.25 | **0.03 ~ 0.196**（P10~P90 = 0.03~0.064） | ✅ |
| 留出集泄漏 | 0 | **0**（文本级去重，不只按 id） | ✅ |
| 置信度唯一值 | 不能只有 2 个 | **34 个** | ✅ |

> **中途踩的一个坑，必须记下来**：第一版把"正常 p 0.03~0.25"直接写进了样本的 `confidence` 字段。但服务里 `p` 的定义是**诈骗概率**——判"否"时 `p = 1 - confidence`。于是训练出来的模型在正常样本上输出 `confidence=0.03` → 服务算出 `p=0.97`，全部越线，日志里出现 `normal -> normal p=0.936`。
> 发现后立刻停掉那一轮、删掉权重（`output_badconf`），改成正常侧 `confidence` 取 0.80~0.97（对应 `p` = 0.03~0.196）重新训练。**这一轮多花了 40 分钟，但如果不改，第三轮的结果会是假的全线崩盘。**

> **为什么本轮用 `--no-src-reason`（与"自带理由优先"看起来矛盾）**：老师要求"原数据自带理由就优先用自带的"，但核查后发现三个数据源里**没有一个带真实理由**——
> ① `TeleAntiFraud` 只有目录名标签，转录结果里没有理由；② `fraud_texts.jsonl` 与 `normal_sms.jsonl` 里的 `reason` 字段是**我上一轮自己用模板生成的**，正是老师批评的"5 类诈骗只有 5 句理由"那一批；
> 若保留，等于把旧模板原样喂回去，`reason_unique` 会假性退化。所以清掉旧字段、全部按原文重新生成。**"自带优先"的规则本身已实现并保留**（`--no-src-reason` 不加时生效），将来若拿到带真实标注理由的数据源，直接去掉该开关即可。

### 7.7 错例分析：漏了什么、误判了什么

这一节比总表重要——它决定了下一步该怎么补，也说明了 v3 的问题不是"随机噪声"。

**① holdout 漏掉的 4 条诈骗（全是"诱饵型短句"）**

| 原文 | 模型给 p |
|---|---|
| 宝妈兼职，手机就能做，一单一结，每天轻松赚两三百 | 0.064 |
| 老年人专属理财产品，保本保息，每月分红，比存银行划算多了 | 0.03 |
| 数字人民币内测名额，现在投入一万，三个月翻三倍 | 0.064 |
| 您打开手机设置里的屏幕录制，我这边帮您把多扣的钱退回去 | 0.064 |

共同点：**只有诱饵、没有施压、没有明确索款动作，单句看像广告**。训练集里的诈骗样本绝大多数是完整话术链（冒充身份 → 制造紧张 → 要求转账/屏幕共享），这 4 条缺了后半段。**这不是模型"没学会诈骗"，是训练数据里缺少"只有钩子的单句"。**

**② holdout 误报的 4 条正常（全是"字面含诈骗关键词"）**

| 原文 | 模型给 p | 为什么错 |
|---|---|---|
| 【派出所】温馨提示：凡是让您下载会议软件共享屏幕的都是诈骗，请相互转告 | 0.905 | 反诈宣传，含"下载会议软件/共享屏幕" |
| 【微信】验证码 908712，用于登录验证，请勿转发 | 0.907 | 含"验证码" |
| 您好，我是社区网格员，明天上门登记人口信息，请家里留人 | 0.875 | 含"上门/登记个人信息" |
| 奶奶好，我是您孙女的同学，她让我跟您说今晚晚点回家 | 0.872 | 正是"冒充熟人"的句式模板 |

**这 4 条暴露了 v3 仍在做关键词级判断**："验证码""共享屏幕""上门登记"这些词一出现就抬 p，不管上下文是在提醒、是系统通知、还是真的社区服务。**光靠堆正常样本消不掉这种误伤——需要专门构造"含高危词但合法"的负样本。**

**③ 音频漏掉的 2 条：模型自己写出了自相矛盾的理由**

| 文件 | 时长 | p | 模型给的理由 |
|---|---|---|---|
| `eval_诈骗_刷单返利_22.wav` | 36.9 s | 0.064 | "这是一通关于**刷单返利**的正常沟通，双方只确认了办理流程与相关细节，没有要求转账……" |
| `eval_诈骗_刷单返利_23.wav` | 32.4 s | 0.128 | "这是一次**刷单返利**的正常联系，只涉及办理流程……" |

模型**准确听出了这是刷单返利**，却仍然判"正常"，理由里"刷单返利"和"正常沟通"直接并列。这是典型的**理由模板过度泛化**：正常侧理由模板是"这是一通关于「业务名」的正常沟通"，模型学会了这个句式后，把任意主题词往里一塞就交卷，主题词的危害性没进入判定。

同一批 30 条在**文字模式**下召回是 **15/15**，音频却漏 2 条——**说明这两通在音频通道上丢了线索，或者 LoRA 在音频编码侧对"刷单"这一类退化了**。前两轮音频与文字结论完全一致（都是 15/15），v3 首次出现分歧，这一点必须记下来。

**④ 数据侧的一个已知噪声源**：正常侧 834 条里有约 39 条（0.8%）实为"积分清零"类诈骗（§7.0 第 4 条）。这类样本与刷单、客服类话术高度相似，**可能是"客服/返利类判宽容"的成因之一**，但 0.8% 的量级不足以单独解释 4 条漏报。

### 7.8 结论与决定

**判定：不通过。** 老师定的判据里"诈骗不漏"排在最前（holdout ≥19/20、真人 15/15），v3 两项都没达到。误报清零虽然是三轮里最好的结果，但**在反诈场景里，用漏报换误报是不能接受的交换**。

按老师事先约定（"如果第三轮还是超不过原始模型，就不再继续调了，线上继续用原始模型"）：

1. **停止调参**，不再做第四轮。
2. **线上 `SFT_URL` 继续留空**，融合链保持"规则 + DeepSeek"两票，SFT 不接入。理由更新为：**"三轮实验证明数据分布是主因，修正后误报已清零，但诈骗召回不达标（holdout 16/20、音频 13/15），不具备接入条件。"**
3. 三轮实验如实记录——这本身就是一份完整的实验过程：**发现问题（塌缩）→ 归因（数据分布单一）→ 验证（换数据，塌缩消失）→ 再归因（置信度写死）→ 再修正（p 值恢复区分度、误报清零）→ 暴露新的瓶颈（诱饵型短句漏报 + 关键词误伤）**。每一轮的失败都定位到了一个具体可修的原因，没有一轮是白跑的。

**如果将来还要继续（本轮不做，仅记录方向）**，瓶颈已经非常明确，不是"数据不够多"而是"数据不够刁"：

- 补**"只有钩子、没有索款"的短诈骗样本**（兼职、理财、内测名额、屏幕录制退款）——直接对应 ① 的 4 条漏报
- 补**"含高危词但合法"的正常样本**（反诈宣传、验证码通知、社区/物业通知、亲友代传话）——直接对应 ② 的 4 条误报
- 把正常侧理由模板从"这是一通关于 X 的正常沟通"改成必须引用**具体判定依据**（如"对方仅告知配送时间，未索要任何信息"），避免模型把主题词直接塞进模板——直接对应 ③ 的自相矛盾
- 音频侧单独验证刷单类，确认是通道丢线索还是编码器退化

**关于线上**：`SFT_URL` 留空这一点没有变。三轮里没有任何一轮通过全部判据，任何"已接入 SFT"的说法都不成立。

## 八、边界说明（引用数字时必须连带引用）

1. **训练 loss 不代表模型好坏**：v1 的 loss 是 0.0013、v3 是 0.2133，但 v1 塌缩、v3 误报清零。任何汇报都不要单独引用 loss，本实验就是反例。
2. **CGoDial 300 条与训练集同源**，0/300 不能当作泛化能力，它测的是"拟合没拟合上"。真正看泛化的是 holdout 与真人录音那两组。
3. **30 通真人录音样本极小**，15 条正常里多错 1 条就是 6.7 个点。只能定性说"改善/恶化"，不要报"提升了 X%"。
4. **三轮规模分别是 1,900 / 1,900 / 5,000 条**，未做超参搜索（rank、lr、epoch 全部沿用原模型 `args.json`，只动过 lr 与数据）。结论只针对这组配置，不能外推成"LoRA 在该任务上的能力上限"。
5. **v3 的误报清零是"训练分布覆盖到了"的结果，不是模型学会了泛化**：真人录音那 15 条正常里，亲戚家常、物业通知这类场景在 TeleAntiFraud 正常对话里有大量相似样本。换一批没见过的正常通话，误报会回升。
6. **v3 首次出现音频与文字结论不一致**（音频 13/15、文字 15/15）。前两轮两者完全一致，所以**不能把文字模式的 15/15 当作音频能力**，也不能因为文字满分就说"模型会判刷单"。
7. **不能说"LoRA 无效"**：CGoDial 246/300 → 0/300、真人正常误报 10/15 → 0/15 都是真实的。
8. **不能说"第三轮成功了"**：漏 4 条短信诈骗、漏 2 通刷单电话，按老师判据就是不通过。误报清零不能抵消漏报。
9. **不能说"v2 比原模型好"**：同一批数据按 p≥0.85 是音频 8/15 对 0/15、文字 11/15 对 2/15，线上口径下明显更差。
10. **holdout 那 15 条正常与 20 条诈骗都是人工构造的短信**，不是真实用户收到的消息，只能证明"分布匹配与否"，不能当线上误报率/漏报率。
11. **reason 的种数不是质量指标**（见 §4.1）：v3 有 2,423 种理由，但仍然漏了 4 条、误报了 4 条。判定能力只看 `is_fraud` 与 `p`。
12. **p 值必须能和 `is_fraud` 分开看**：v1/v2 的 confidence 被写死，两个口径退化成同一个（§4.4）。引用任何一轮数字时，若只给一个口径，等于隐去了对 LoRA 不利的一半。
13. **"关键词误伤"是 v3 仍然存在的真实缺陷**：反诈宣传短信、验证码通知、社区上门登记、亲友代传话这 4 类会被判诈骗（p 0.87~0.91）。这不是样本太少的偶然现象，是关键词级判断的必然结果。
