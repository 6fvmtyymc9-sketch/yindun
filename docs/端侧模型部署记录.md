# 端侧模型部署记录（2026-11-11）

对应 [模型选型](模型选型.md) 4.1「部署」一栏：
> 转 MindSpore Lite，放进 App，和规则引擎并联：任一判为可疑即提醒

从训练好的 `finetuned.ckpt` 到手机上能跑，中间有四道坎。这份记录写清楚每道坎的
现象与解法，一是留证据，二是换台机器重做时不用再踩一遍。

---

## 一、整条链路

```
tools/train_tinybert_ms.py        训练（MindSpore，GRAPH_MODE）
```

这步不做，后面所有数字都不可信。

## 二、四道坎

### 1. Windows 版 converter 跑不起来（卡最久）

`mindspore-lite-2.11.0-win-x64.zip` 里的 `converter_lite.exe` 双击报错，退出码一路变：

| 阶段 | 退出码 | 现象 |
|---|---|---|
| 初始 | `0xC000007B` | 无效映像 → 缺 `libssp-0.dll` |
| 补 libssp | `0xC0000139` | 入口点找不到 → 缺 C++11 ABI 符号 |
| 换 Anaconda 的 MinGW | `0xC0000139` | 还是缺 |

**用 objdump 逐符号对账**才定位到根因：

```bash
objdump -p converter_lite.exe | awk '/DLL Name: libstdc\+\+-6.dll/,/^$/' | grep -oE '\b_Z[A-Za-z0-9_]+'
```

`converter_lite.exe` 要 108 个、`libmindspore_converter.dll` 要 265 个 C++ 符号，
本机两套 MinGW（Dev-C++ 的 GCC 8.1、Anaconda 的 MinGW）合起来只缺 **4 个**：

```
_ZNSt6thread15_M_start_threadESt10unique_ptrINS_6_StateESt14default_deleteIS1_EEPFvvE   （GCC 11+ 才有）
_ZNSt6thread6_StateD2Ev
_ZNSt7__cxx1118basic_stringstreamIcSt11char_traitsIcESaIcEEC1Ev
_ZNSt7__cxx1119basic_ostringstreamIcSt11char_traitsIcESaIcEEC1Ev
```

`_ZNSt7__cxx11…` 前缀说明 MindSpore 是用**新 ABI** 编的，而 Anaconda 那套是老 ABI。

**解法**：补一套 GCC 15 的运行时。MSYS2 的 `gcc-libs` 包在新版本里被拆空了
（16.2.0 的包只有 2.3 KB 元数据），要用 **15.2.0-14** 那个：

```bash
# 1 MB 左右，解压出 mingw64/bin/{libstdc++-6,libgcc_s_seh-1}.dll
curl -O https://mirrors.tuna.tsinghua.edu.cn/msys2/mingw/mingw64/mingw-w64-x86_64-gcc-libs-15.2.0-14-any.pkg.tar.zst
# .zst 用 python 的 zstandard 解（本机没有 7z / zstd 命令）
python -c "import zstandard,tarfile; ..."
# libwinpthread-1.dll 也要换新的
curl -O https://mirrors.tuna.tsinghua.edu.cn/msys2/mingw/mingw64/mingw-w64-x86_64-libwinpthread-git-12.0.0.r747.g1a99f8514-1-any.pkg.tar.zst
```

把这几个 DLL 拷到 `converter_lite.exe` 同目录，`PATH` 指过去即可。
**换完符号缺口归零**，转换一次通过：

```
CONVERT RESULT SUCCESS:0
tinybert_cls.ms  45,240,216 字节
```

### 2. 模型加载返回 -3（`Device info list is empty`）

第一次装到手机上，日志：

```
E MS_LITE : VerifyDeviceInfo] Device info list is empty!
E MS_LITE : Java_com_mindspore_Model_buildByPath] Error status -3 during build of model
```

不是架构问题，是 **`MSContext` 只 `init()` 不够，必须 `addDeviceInfo()`**：

```java
MSContext ctx = new MSContext();
ctx.init();                                                    // 只有这行会报 -3
ctx.addDeviceInfo(DeviceType.DT_CPU, false, CpuBindMode.MID_CPU);   // 这行才是注册计算设备
ctx.setThreadNum(2);
```

注意 `MSContext.init(int, int, boolean)` 的第三个参数是 boolean，不是 `CpuBindMode`，
写错了 Java 直接编译不过。

### 3. ARM 翻译层让模拟器也能跑

官方 Android 包**只有 aarch64 / armeabi-v7a，没有 x86_64**。
本来以为 x86_64 模拟器上一定跑不了，实测 `google_apis x86_64` 的 Android 11 镜像
带 ARM 翻译层，`libmindspore-lite-jni.so` 能加载、推理能出正确结果：

```
I NativeLibrary: loadLibrary mindspore-lite-jni success
I YindunTinyBert: 端侧模型就绪，用时 3351ms，输入 [ids(1,64), add_mask(1,1,64,1)]，输出 [Default/classifier-Dense/BiasAdd-op0(1,2)]
```

所以模拟器可以当功能验证环境，只是慢（真机 arm64 原生跑会快得多）。

代码里仍然保留 ABI 判断：`Build.SUPPORTED_ABIS` 里没有 arm 就直接放弃，
**不让它在不支持的机器上假装在跑**。

### 4. 输入张量的 shape 和训练时不一致

日志里 `add_mask` 的 shape 是 `(1,1,64,1)`，而训练时构造的是 `(1,1,1,64)`。
一开始担心是导出时被转置了、会导致 mask 广播错误。

**结论是没影响**，因为两边都是 64 个 float 顺序铺开，而实测分数与 PC 端一致
（见下表）就是最硬的验证。但这是个需要记住的点：**靠 shape 维数区分输入（2 维是 ids、
4 维是 mask），不要靠名字或具体维度顺序。**

## 三、实测验证

### 与 PC 端逐条对拍

同一条文本，PC（MindSpore 原模型）和手机（Lite）分别打分：

| 文本 | PC | 手机 | 差 |
|---|---|---|---|
| 【工商银行】您账户异常，请点击 http://icbc-verify.top 验证身份 | 0.762770 | 0.7620 | 0.0008 |
| 阿姨，我是您家附近超市的，刚才帮您领优惠券，您手机收到的数字告诉我一下 | ~1.000 | 0.9982 | 0.0018 |

差异来自浮点精度与 Lite 的算子实现，量级 `1e-3`，不影响阈值判断。
**这一步是整件事的关键**：分数对不上，就等于装了个会算错的模型。

### 并联效果（规则漏、模型抓）

选一条规则完全抓不到的样本，走完整链路：

```
短信 from=13900008888 who=stranger 验证码=false
     分数=45 阶段=S1 级别=warn 模型分=0.9982
     命中=优惠券(-10)、陌生号码(+15)；端侧小模型判为可疑（99%）
轻提醒已弹出（warn）：疑似诈骗短信
```

读法：
- 规则只算了 **5 分**（优惠券 -10 + 陌生号码 +15），落在 `none`，**不会打扰老人**
- 模型给 **0.9982**，判可疑 → 按并联规则抬到 `warn`（分数抬到门槛 45）
- `why` 里写清楚是谁抬的：`命中=…；端侧小模型判为可疑（99%）`

这正是「任一判为可疑即提醒」要的效果，也是答辩时最有说服力的一段：
**同样的短信，只靠规则会被放过去。**

### 正常短信不误伤

| 文本 | 规则 | 模型 | 结果 |
|---|---|---|---|
| 妈，我今天加班，晚饭别等我 | 0 / none | 0.000431 | 不打扰 |
| 我是社区的张医生，明天上午九点来老年大学做免费体检，记得空腹 | 词库命中 | 0.004227 | 不打扰 |
| 张三您好，您订的报纸本月到期，续订请到邮局窗口办理 | 0 / none | 0.021807 | 不打扰 |

## 四、代码落点

| 文件 | 职责 |
|---|---|
| `app/assets/tinybert_cls.ms` | 模型（45.2 MB），首次启动拷到 `filesDir`，之后按大小复用 |
| `app/assets/tinybert_vocab.txt` | 词表 21128 行，与训练脚本同一份 |
| `app/jniLibs/{arm64-v8a,armeabi-v7a}/` | `libmindspore-lite.so` + `-jni.so`（训练库没放，省 3 MB） |
| `app/libs/mindspore-lite-java.jar` | Java 接口 `com.mindspore.*` |
| `TinyBert.java` | 加载、分词、推理、状态上报 |
| `Judge.withTinyBert()` | 并联规则：只抬不降，模型缺席时原样返回 |
| `GuardService.onCreate` | 子线程预热，别等第一条短信才现加载 |
| `build.gradle` / `build2.sh` | `jniLibs.srcDirs` + 打包 `.so` 进 `lib/<abi>/` |

**分词的坑**：Java 的 `encode()` 必须和 Python 的 `CharTokenizer` 逐字一致 ——
ASCII 连续字母数字合成一个 token（`10086`、`ETC` 不拆散），其余按单字切，
`[CLS]` 在头、`[SEP]` 在尾、补 `[PAD]` 到 64。差一点，分数就飘。

## 六、还没做到的

1. **真机实测**：目前只在 x86_64 模拟器（ARM 翻译层）上验证过，
   真机 arm64 的加载耗时和推理延迟还没量。
2. **模型缺席时的界面提示**：现在只在日志和 `why` 里体现，界面上没有独立状态行。
   短信判定链本身不受影响（`modelScore = -1` 时原样返回规则结论）。
3. **`collect_normal.csv` 那 80 条真实正常短信还没填**，模型误报 6.7% 主要靠这批数据往下压。
