## 三、三个坑（每个都卡了一次，别再踩）

### 坑 1 · 最新 ms-swift 会毁掉环境

`pip install ms-swift` 装到 4.6.1，它依赖 `transformers>=5.x`。
这台机器上还有 `sft_server.py` 用着 transformers 4.49，一升级就废。
→ 锁 3.12.6 + 独立 venv。

### 坑 2 · 装完还要手动降 transformers

3.12.6 声明 `transformers<4.58`，pip 就挑了 4.55.4。
但 `swift sft` 跑起来第一行就警告：

```
Please install the package: pip install "transformers>=4.45,<4.49" "librosa" -U
```

声明的约束和实际代码要的约束不一致。→ 装完必须补 `transformers==4.48.3`。

### 坑 3 · Python 3.10.0 的 lzma 缺陷（最坑，和数据集无关）

`swift sft` 一启动就崩在这：

```
AttributeError: '_lzma.LZMADecompressor' object has no attribute 'needs_input'
```

追栈的结果：

```
datasets/download/download_manager.py:326  download_and_extract
  → extract() → 对每个文件调 tarfile.is_tarfile()     ← 只是"探测是不是压缩包"
    → tarfile.xzopen → _compression.read
      → self._decompressor.needs_input                 ← 炸在这里
```

**本机 `lzma.LZMADecompressor` 实测 `hasattr(d,'needs_input')` 为 `False`**
（Python 3.10.0 是 2021 年的早期版本，这个属性后来才补上）。

训练数据全是 jsonl，根本不需要解压任何东西，它只是在**探测**。
→ 在 venv 的 `sitecustomize.py` 里包一层 `tarfile.is_tarfile`，捕获
`AttributeError/OSError/EOFError` 返回 `False`。已验证生效。

> 这一条不是 datasets 的 bug，也不是我们的数据有问题。换台 Python 3.10.13+
> 的机器就不会遇到。排查时不要往数据格式上想。

## 四、smoke test 实测数据

### 纯文本（102 条训练 / 18 条验证）

```
PeftModelForCausalLM: 8417.0834M Params (19.9885M Trainable [0.2375%])
loss  0.6445 → 0.0525 → 0.00307      token_acc 0.667 → 1.0 → 1.0
eval_loss 0.1089   eval_token_acc 0.9444
显存 17.7 GiB      ≈ 1.18 s/it
```

### 带音频（16 条训练 / 4 条验证，25 秒切片）

```
loss  0.7631 → 0.01267
eval_loss 0.0059
显存 18.06 GiB     ≈ 1.5 s/it
```

有一条提示 `Expanding inputs for audio tokens in Qwen2Audio should be done in processing`，
是 transformers 的常规提醒（ms-swift 在 forward 里做扩展），不影响训练。

### LoRA 落在哪（这是老师那条硬要求的证据）

```
adapter_config.target_modules =
  ^(language_model(?=\.).*\.(down_proj|up_proj|k_proj|o_proj|v_proj|q_proj|gate_proj))$

448 个 LoRA 张量 → language_model 448
                   audio_tower     0
                   multi_modal_projector 0
```

正则在结构上排除了音频编码器，`--freeze_vit true` 再保一层。
**"只训 LM、冻结音频编码器"这条已经实证成立，不是靠参数名猜的。**

## 五、数据盘点：真缺口在负样本

| 来源 | 可用正常样本 | 能不能用 |
|---|---|---|
| MagicData 真人对话 | **9 通** | 真人、真口音，但内容是电影/会议闲聊，不像来电 |
| `cloud/test/collect_normal.csv` | **1 条** | 81 行里只有 1 条示例——**真实正常短信收集从来没做过** |
| `cloud/test/synthetic.json`（normal） | 147 | DeepSeek 合成。用它训、再和 DeepSeek 比＝循环论证 |
| `cloud/test/cases.json` + `holdout.json` | 55 | **规则调参/留出集，拿来训练会污染评估** |
| `外部数据集/hf_sms`（text_zh） | 3852 | **机翻垃圾**，实测样本：`"Ma 头 dey 肿胀 oh. 谢谢你做我的日子"` |

**真实可用的正常样本合计 10 条。**

顺带查出两个数据集的真实形态（都会直接影响后面的实验设计）：

1. **Fraud-R1 的两份文件完全重复。** `FP-base-Chinese.json` 与
   `FP-levelup-Chinese.json` 各 1070 条，`generated text` 逐字相同（实测交集 1070）。
   合并会变成 2138 条副本，等于偷偷给正样本加权。脚本已按文本去重。
2. **MagicData 是 9 通不是 5 通。** 5 通是 `_SPK002/003` 双路（须按时间归并），
   4 通是 `20200327_2P_*` 单文件混录（自成一通）。只认双路会少掉四成负样本。
3. **每段录音 20 分钟。** 音频编码器上限约 37 秒，必须切片，否则只听开头就被截断。

## 六、下一步（按依赖顺序）

1. **等真人录音**：30 通（15 骗 + 15 正常）。这是阶段 D 的唯一卡点，
   也是老师明确写了"不许 TTS"的部分。录音不到位，任何微调数字都没意义。
2. 录音到位后：`split_audio.py` 切片 → `build_sft_data.py` 造数据 → 先跑
   3 通试打确认格式与转写 → 再全量。
3. 基线表（老师第 2 步）：在**冻结评估集**上跑未微调模型，这个数字本身
   就是成果，即使微调没效果也要报。
4. 微调后回到同一评估集，只评不训。

**一句提醒**：11-19 已实测原模型对任意输入恒答"是"（静音 0.6225、白噪声 0.5312、
440Hz 正弦 0.8520，14 段正常通话 14/14 全判诈骗）。所以微调要验证的核心指标不是
"诈骗命中率"，而是**正常样本的误报有没有降下来**。评估表必须按这个设计。
