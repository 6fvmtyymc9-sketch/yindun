## 二、必须改的 6 处

### ① 基线数字过期：353 条告警 / 7 条上报 → 我实测是 428/32，但**现在也别抄这个数**

清单第三步写「迁移完核对：353 条告警、7 条上报，一条不能少」。我 11-18 查线上库是 `428 / 32`。
但 11-19 上午它已经变成 `1581 / 1225`——同学乙在跑评估集，每轮灌一千多条，`elder_id` 全是 `demo`。

**所以正确做法不是换成另一个数字，而是不写死**：迁移前现查一次存档，迁移后现查一次，逐项相等即成功。
已写进 `deploy/README.md` 第八节与 `云上操作清单_v2.md` 〇-1。

> 附带口径：`/api/health` 的 `stats` 是 `WHERE elder_id='demo'` 的计数（`Db.js:426`），
> 不是总条数。核对总数只认不带 `WHERE` 的 `SELECT COUNT(*)`。

### ② 迁移顺序反了：先建表 + 跑迁移，最后才导 dump，等于白跑

清单现在的顺序是：`schema.sql` → `migrate_event.sql` → 导入 backup。

问题在 `mysqldump --databases` 的导出文件里带 `DROP TABLE IF EXISTS` 和 `CREATE DATABASE IF NOT EXISTS`。
最后一步导 dump 时，会把前两步刚建的表**全删掉、按 dump 里的结构重建**，前面跑的迁移全部作废。

今天这份 dump 是从已经迁移过的库导出来的，重建后结构碰巧一样，看不出问题。
但只要 dump 来自更老的库，结果就是「服务启动报缺列」，而且报错信息完全不指向迁移顺序。

正确顺序（已写进 `deploy/README.md` 第八节）：

```
建库 → 导入 dump → schema.sql（IF NOT EXISTS，补新表）→ callaudio 迁移 → event 迁移
```

### ③ 漏了一整个迁移文件：`migrate_20261110_callaudio.sql`

`sql/` 下有**三个**文件，清单只提了两个。

```bash
sql/schema.sql                        # 建表
sql/migrate_20261110_callaudio.sql    # ← 清单漏了这个
sql/migrate_20261111_event.sql        # 事件回放
```

漏掉的那个是给 `yd_report.reporter` 的 ENUM 加 `callaudio` 值。文件头自己写着后果：

> 不改这里，MySQL 会直接把这个值截断成空串，数据静默丢失（不报错、不提醒）。

也就是说，漏跑它的表现不是「报错」，是**录音复盘功能看着正常、上报数据一条都没落库**。
这种故障比报错难查十倍。三个都要跑，两个迁移都可重复执行。

### ④ 阶段三：`scp .env 到新机器` 会带过去 `127.0.0.1`

线上 `.env` 现在是：

```ini
RDS_HOST=127.0.0.1
REDIS_URL=redis://:...@127.0.0.1:6379/0
```

因为数据库就装在老 ECS 上。**照抄到新机器，新机器会去连自己的 localhost，连不到任何东西**。
表现是 `health` 里 `rds:false / redis:false`，但服务照常启动（`.env` 连不上就降级内存存储），
看起来「部署成功」，其实数据全在内存里，重启就没。

新机器上这两行必须换成 RDS / DCS 的**内网地址**，且新机器要在同一个 `vpc-default` / `subnet-default` 里。
验收只有一条：`curl /api/health` 里 `"rds":true,"redis":true`，且重启后告警记录还在。

### ⑤ 阶段三：新机器内网 IP 变了，RDS 的 3306 白名单会把它挡在外面

③ 里那条 `192.168.0.211/32` 只放行了**这一台** ECS。新开的演示机器内网 IP 不是这个，
于是新机器连 RDS 直接超时。

两个办法选一个：

- 演示前把新机器内网 IP 加进 RDS 安全组（干净，但每换一次机器要加一次）
- 或者把源地址放宽成整个子网 `192.168.0.0/24`（省事，但权限没那条紧）

**别在录屏现场才想起来**，那是最容易当场卡住的地方。

### ⑥ 停掉本机 mysql 之后，重启 yindun 会把它又拉起来

清单第四步最后：`systemctl stop mysql redis-server` + `disable`。
但 systemd 单元里原样写着：

```ini
After=network.target mysql.service redis-server.service
Wants=mysql.service redis-server.service
```

`Wants` 是**显式依赖**，跟 `enable/disable` 没关系。只要这两行还在，**每次 restart yindun
都会把 mysql 和 redis 重新拉起来**：白吃四百多兆内存，而且旧库还在被写，迁移就没算完。

那份 systemd 模板本身没错——它是「数据库和代码装在同一台」阶段的正确写法。
错在迁移完之后没有摘掉。所以 `deploy/install.sh` 改成了**运行时探测**：
本机真有 mysql/mariadb/redis 才写 `After/Wants`，没有就只依赖 `network`。
迁完之后在新形态下重跑一次 `install.sh`，这条依赖自动消失。

## 四、一条铁律：老机器上别跑 `install.sh` 覆盖现网代码

`install.sh` 第 5 步是 `rsync` 覆盖 `/opt/yindun`。他手上的代码快照是 11-18 之前的，
而线上现在还是规则 3.4、我本地已经改到 3.6（关键词 212 → 220）。

**在老机器上跑一次 `install.sh --src 他的目录`，就会把规则打回 3.4，把今天补的词全冲掉。**

所以：

- `install.sh` **只用于阶段三的新机器**（那台机器是干净的，覆盖无所谓）
- 老机器上要更新代码，走另一条路（我这边推，推完 `/api/health` 看 `rules.version` 对不对）
- 他的 README 里也写了「方式C：代码已经在 /opt/yindun」，这条在老机器上等于自杀，别用

## 五、答辩可能被问的两点（提前想好）

### 1. 服务为什么以 root 跑？

线上单元确实没有 `User=`，脚本里 `chown -R yindun:yindun` 之后服务仍是 root 起的，`yindun` 用户形同虚设。
真实原因是早期为了省事（要绑 8080、要读 `.env`）。**如果评委问，答"已知问题，下一步改成
`User=yindun` + `AmbientCapabilities=CAP_NET_BIND_SERVICE`"，别答"这样更方便"**。
顺带一句：这台机器 `PermitRootLogin yes` + 密码认证开着，`lastb` 记了四万多次失败登录，
这属于运维债，不是功能缺陷，能答清楚就行。

### 2. 为什么部署脚本不代填 `.env`？

这是刻意的：脚本一旦能代填密码，密码就会出现在脚本参数、shell history、`ps` 输出里。
所以脚本只检查「有没有填」，填不填是人的事。这条是加分项，主动讲。
