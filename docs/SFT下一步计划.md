# AntiFraud-SFT 下一步计划

> 写于 2026-11-18。前提是你已经测完的结果：文本模式下没有一个阈值能兼顾两头；
> 音频和文字的得分几乎一样；物业停水这类正常电话会被判成诈骗；三份外部数据集都补不上缺口。
> 结论我们一致：**缺的是真人数据。** 下面按顺序做，前一步没做完不进下一步。

---

## 第 0 步：先改融合规则（今天就能做）

**问题：** `cloud/src/CallAudio.js` 第 177 行现在是 SFT 的 p ≥ 0.85 且 stage < 2 时，直接把 stage 抬到 2，
等级变成 `warn`，第 214 行随即**推送提醒**。也就是说，规则和 DeepSeek 都判"没事"时，
SFT 一票就能让老人收到警告。

所以「只抬不降，最多没帮上忙」这句不成立：只抬不降挡住的是漏报，挡不住误报。
你测的文本结果里，15 条正常短信有 10 条超过 0.85。按这个比例，接上 SFT 后会多出很多误报。

**改法（二选一，你来定）：**

- **A. 需要第二票：** SFT ≥ 0.85，并且 DeepSeek 至少判到 stage 1（可疑），才抬到 2
- **B. 单票只记录，不推送：** SFT 单独高分时，只在子女端的复盘记录里标一句"专用模型认为可疑"，不推送给老人

**验收：** 物业停水那段录音（以及把它的 p 手动改成 0.95 的模拟情况），老人端都**不弹**提醒；
两段诈骗录音的结果不变。改完补一条测试。

## 第 1 步：建评估集（最重要，1~2 天）

**目标：** 30 通真人电话录音，**冻结**之后只用来打分，**永远不拿去训练**。

| 类别 | 条数 | 场景（每个场景录 1~2 通，换人、换说法） |
|---|---|---|
| 正常 | 15 | 物业通知（停水、停电、缴费）、快递、外卖、社区网格员、银行客户经理（存单到期）、医院复诊提醒、保险回访、老年大学、亲戚家常、子女打电话、维修师傅约上门、送水送奶、村委通知 |
| 诈骗 | 15 | 冒充公检法、冒充子女或孙子、客服退款、刷单返利、养老理财、医保卡异常、冒充领导、中奖、贷款前期费、屏幕共享 |

**录制要求：**

- 两个人用手机互打，开通话录音。**真人说，不要用 TTS**
- 照着场景**即兴说**，不要逐字念稿。念稿的语气和真实通话不一样，而语气恰恰是我们想测的
- 正常通话里要**故意放一些"像诈骗"的词**：「您尽快处理一下」「需要核实一下身份」「这边帮您登记」。
  只有这样才测得出误报
- 每通 20~90 秒，导出成 mp3 或 wav（m4a 服务端解不开）
- 命名：`eval_正常_物业停水_01.mp3`、`eval_诈骗_公检法_01.mp3`
- 每条配一份人工转写 `.txt`（ASR 识别出来再人工校对），用来对比文本模式和音频模式

**放哪：** 建 `cloud/test/calls_eval/` 目录，加一份 `labels.json`，记录文件名、标签、场景、录音人、日期。

**冻结：** 录完提交一次，commit message 写上「评估集冻结」。之后这个目录**只读**，
训练脚本里要显式排除它。

## 第 2 步：测基线（半天）

用评估集把三路（规则、DeepSeek、SFT 音频模式）各跑一遍，SFT 再加跑一遍文本模式，出一张表：

| | 抓到诈骗（/15） | 正常被误报（/15） | 平均耗时 |
|---|---|---|---|
| 规则 v3.5 | | | |
| DeepSeek | | | |
| SFT 音频（p ≥ 0.5 / 0.85） | | | |
| SFT 文本（p ≥ 0.5 / 0.85） | | | |
| 融合（第 0 步改完之后） | | | |

- **写原始计数，不要只写百分比。** 15 条里错 2 条，就写「2/15」
- 把每条的 p 值存成 JSON（`cloud/test/out-sft-eval.json`），后面微调完要逐条对比
- 这张表就是**微调前的基线**，直接放进 `docs/模型对比实验.md`

## 第 3 步：准备训练数据（2~3 天）

**训练数据必须和评估集是不同的录音。** 同一个人用同一套说法也不行，要换人、换说法。

| 数据 | 条数 | 来源 |
|---|---|---|
| 正常通话（重点） | 60~100 | 和第 1 步同样的方法另外录，场景覆盖要比评估集更广 |
| 诈骗通话 | 60~100 | 一半另外录，一半从 TeleAntiFraud 里抽（防止模型把原来会的忘掉） |

格式整理成 `jsonl`，每行一条：

```json
{"audio": "train/正常_快递_03.mp3", "label": "否"}
```

先只用这些数据跑通流程。数量不够就继续录，**不要用 TTS 合成的正常通话来凑数**。
TeleAntiFraud 正是因为用了 TTS 才学不到真人语气的，再用 TTS 等于重蹈覆辙。

## 第 4 步：LoRA 微调（GPU 上，1~2 天）

**环境：** 学校 GPU 容器，登录方法见 [GPU 容器 SSH 使用说明](GPU容器SSH使用说明.md)。

**训练前先停推理服务**（它常驻 18 GB 显存，和训练一起跑会爆显存），停之前在群里说一声；
训练完再启动。

**建议做法：**

- 工具：用 ModelScope 的 **ms-swift**，它直接支持 Qwen2-Audio 的 LoRA 微调，比自己写训练循环省事
  （`pip install ms-swift`，用清华镜像）
- 只在**语言模型部分**加 LoRA（q/k/v/o 投影层），**冻结音频编码器**
- 起步参数：rank 16、学习率 1e-4、2~3 个 epoch、bf16。显存预计 25~35 GB，L40 放得下
- **训练格式要和 `/judge` 一致**（2026-11-20 更正）：两轮对话，第一轮判场景，第二轮写分析并输出
  `{"reason","confidence","is_fraud"}`，提示词照抄 `tools/sft_server.py` 里的 `NATIVE_Q1` / `NATIVE_Q2`。
  **不要再用「只回答一个字：是或否」的格式**：模型原本不是这么训练的，用旧格式训练等于换了一个任务，
  而且 `/risk` 那种比较第一个字概率的打分方式已证实不可信（见 [SFT 接口说明](SFT接口说明.md)）。
  正常样本的 reason 写清楚「为什么不是诈骗」，例如「物业通知停水，没有要钱、没有要验证码」
- 训练命令用 `nohup ... &` 放到后台跑（容器里没有 tmux），日志写到自己的目录 `~/work/<名字>/`
- **训练完立刻把 LoRA 权重拷回本地。** 平台一删除容器，磁盘就会清空

**检查点：** 训练 loss 下降不代表变好了，只有第 5 步的结果算数。

---

## 第 5 步：回到评估集上打分（半天）

- 推理服务加载「原始权重 + LoRA」，在**同一份冻结的评估集**上重跑第 2 步，表格加一行「SFT + LoRA」
- 逐条对比 p 值：哪些正常通话降下来了，**有没有诈骗跟着漏掉**
- 如果误报降了、漏报没升，就把 LoRA 接进线上服务，并重新确定融合阈值

**报告里必须写清楚：**

1. 训练集和评估集是两批不同的录音，各是谁录的、录了多少
2. 微调前后的原始计数，不只写百分比
3. 30 条样本误差很大，结论是「有改善的迹象」，不是「准确率提升了 X%」

## 不要做的事

- 不要拿评估集里的录音去训练，也不要照着评估集的错例补数据，再在同一份评估集上报分
- 不要用 TTS 或大模型生成的正常通话来训练
- 不要在别人训练的时候启动训练，开训前先跑一下 `nvidia-smi`
- 不要覆盖 `~/models` 里的原始权重
