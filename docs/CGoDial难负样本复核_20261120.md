## 一、一句话结论

我们的规则 3.6 在这批数据上的误报率**与老师 v3.5 几乎完全一致**（3,936 条真实对话误报 460 条 = 11.7%），
说明 11-20 上线的冒充亲属与 ETC 两个新判据**没有加剧误报**；
但同一轮跑出了一个 README 里没写的数字：**111 条真实对话被判到 block（会盖红屏）**。

## 二、数据是什么

来源：CGoDial（EMNLP 2022）的 flow-based dialog 子集，杭州、绍兴**政务热线智能客服**通话。
协议 MIT，仓库只放了转换脚本与打分脚本，数据本体不进版本库。

| 场景 | 内容 | 真实 | 模拟 |
|---|---|---|---|
| gov | 公积金、医保、社保 | 3,010 | 12,548 |
| jiaoguan | 公安：户籍、身份证、出入境、车驾管 | 436 | 2,616 |
| etc | 高速 ETC 办理、通行、收费 | 336 | 2,016 |
| zhubao | 房管：租赁备案、公租房 | 154 | 924 |
| 合计 | | **3,936** | **18,104** |

每条含 `text`（人工转写）与 `text_asr`（ASR 识别第一份结果，带口语与识别噪声）。
线上走 SIS 转写，所以**一律用 `text_asr`** 打分。

**方向要注意**：这是市民打进热线、机器人客服应答，和「陌生机构打给老人」方向相反。
它的价值在于机构一方的话术（自报业务、引导办理、「已短信发送给您、请注意查收」）
和「公积金/医保卡/社保卡/ETC/注销/冻结」这些词，正好是诈骗最常冒充的由头。

## 三、复核方法（完全对齐老师口径）

老师脚本 `scripts/cgodial_rules.js` 的做法：`text_asr` 去掉「客服：/来电人：」前缀，
**整通对话拼成一条文本**，喂 `Judge.scoreSms(body, '', false)`，`level` 到 `warn` 及以上算误报。

本机脚本 `cloud/test/cgodial-fp.js` 一字不改照搬这个口径，只把 `ROOT` 换成本仓路径。

## 五、新发现：111 条真实对话被判 block

老师 README 只报了「warn 及以上」的合计，没有拆 level。拆开看是这样：

| 场景 | high | block |
|---|---|---|
| gov / real | — | **106** |
| etc / real | — | 2 |
| jiaoguan / real | — | 3 |
| 合计 | 13 | **111** |

**3,010 通正常的公积金/医保咨询里，有 106 通（3.5%）会被我们的产品直接盖全屏红屏。**
这在线上意味着：老人如果接到的是真社保局的电话（或自己打 12333 录音复盘），会被误拦。

这条要如实写进报告，不能只报 11.7% 的总数和睦的解读。

## 六、ETC 判据无罪的证据（这条对答辩最有用）

11-20 刚上线的 3.7 步判据是：**陌生号 + 非验证码 + 文本含链接 + 停用/过期/失效/冻结/注销 → +15 抬 S3**。
最担心的是把正常的 ETC 咨询判成诈骗——毕竟 etc/real 有 336 条，而且里面有 2 条落到了 S4。

逐条看这 11 条的命中词，**没有一条触发 3.7 判据**：

| 分数 | 等级 | 命中词 |
|---|---|---|
| 52 | high S3 | 退款、注销、ETC、注意查收 |
| 50 | high S3 | 退款、客服、ETC、注意查收 |
| 52 | high S3 | 退款、注销、ETC、注意查收 |
| 50 | block S4 | 客服、ETC、帮我转 |
| 30~40 × 7 | warn S2 | ETC、扣费、换新号、转人工 |

原因很直接：**3.7 判据的前置条件是文本里有 URL**，而正常的 ETC 热线对话里根本没有链接。
误报全部来自基础词表——`ETC(+10)`、`退款`、`注销`、`客服`、`转人工`、`帮我转`、`注意查收`、`扣费`。

**由此可以讲三句话（答辩口径）：**
1. 新判据是精确的，只在「有链接 + 停用话术」时触发，不会误伤正常业务咨询；
2. 真正敏感的是业务词本身，这是设计使然——诈骗正是拿这些词当由头；
3. 要区分真假客服，靠的不是词，是「谁打给谁 + 有没有要钱要验证码」。

## 七、这份数字不能直接当线上误报率

老师自己也写了「规则是按短信设计的，整通长对话命中词更多，所以这个数字偏严，只能说明方向」。
补充三点我们这边的边界：

1. **长度口径不同**：线上 `SmsReceiver` 处理的是一条短信（几十字），这里是一通 11 轮的对话（几百字）。
   词表按命中计分，长文本天然占便宜，11.7% 是被放大后的数字。
2. **通话复盘链路才是真对应**：`/api/callaudio` 确实是把整段 ASR 转写喂给 Judge，
   所以这 11.7% 对**复盘链路**是真实风险，对短信链路不是。
3. **场景不会撞上**：老人不会主动打 ETC/公积金热线。真正撞上的是「冒充社保局」的诈骗电话，
   那时候拦下来是对的。所以这份数据的用途是训练负样本，不是调阈值。

## 八、用法（老师给的三条，我们照做）

1. **训练负样本**：从 `real` 按场景分层抽样，优先抽规则误报的那 460 条（最难的那批）。
   SFT 的 LoRA 与端侧 TinyBERT 都可以用。
2. **辅助误报检查**：每个场景留 100 条 `real` **不参与训练**，
   在报告里单独写「政务热线误报率」，和 30 通自录评估集**分开写，不混表**。
3. `simu` 是模拟生成，只补量，不用于评估。

**数据本体不进仓库**，仓库只放拉取与打分脚本。
