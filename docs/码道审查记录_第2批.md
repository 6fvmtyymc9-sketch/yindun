## 逐条判定

### 第 1 条 · `/api/call/events` 的鉴权 —— **担心合理，但漏洞实际不存在**

**它说**：`callId` 是「36 进制毫秒时间戳 + 3 位随机（46656 种）」，攻击者知道大致时间就能枚举；更关键的是 `elderId` 由调用方传入且默认 `demo`，可以拿任意 `elderId` 配合猜到的 `callId` 拉别人家的事件。建议不要让调用方传 `elderId`，从子女端凭证里解出来。

**我的核查**：它建议的机制我们**已经有了**，只是它在另一个文件里 ——

```
cloud/src/server.js:179    app.use(pairing.guard);        // 全局中间件
cloud/src/Pairs.js:165     guard(req, res, next) {
                              const want = req.body.elderId || req.query.elderId;
                              if (req.yd.elderId) {       // 认证过 → 强制覆写
                                req.body.elderId = req.yd.elderId;
                                return next();
                              }
                              if (want && want !== DEMO) return 401;   // 匿名只能 demo
                              next();
                            }
```

本地起服务实测三种路径：

| 请求 | 结果 |
|---|---|
| 匿名 `?callId=xxx&elderId=demo` | 200，`elderId: demo` |
| 匿名 `?callId=xxx&elderId=zbaba01` | **401**「需要老人端身份或子女端配对凭证」 |
| 匿名不传 `elderId` | 200，`elderId: demo` |
| 带 `X-Yd-Child: <token>` 但 URL 故意写 `elderId=demo` | 200，`elderId` 是**凭证所属的那位**（`zreviewe01`） |

**所以攻击路径是通的吗？不通。** 攻击者猜到别人的 `callId` 之后：

- 匿名查 → 只能查 `demo` 这一桶 → 真实家庭的数据在别的桶里 → 空
- 用自己的子女凭证查 → 中间件把 `elderId` 覆写成**他自己**那位老人 → 还是空

`elderId + callId` 是双条件查询，缺一个都拿不到数据。

**处理**：**部分采纳**。做了两件事，都是为了"不依赖别的文件里的隐式约定"：

1. `/api/call/events` 里显式写明身份来源（`const authed = req.yd.role === 'child' || 'elder'`），不再靠 `req.query.elderId || 'demo'` 这种"反正 guard 会处理"的写法。行为实测与原来完全一致，只是把兜底从别人那里挪到自己家里。
2. `CallSession.newId()` 的随机段从 3 位 base36（46656 种）扩到 **6 位（21.7 亿种）**，并把 `Math.random` 换成 `SecureRandom`（前者是线性同余，序列可预测）。这是**边际加固**，不是修 bug —— 因为即使猜中 `callId` 也拿不到数据。

**为什么不采纳它的原话**：它说"不让调用方传 elderId"——我们本来就允许传，但传了不作数（被覆写），删掉这个参数反而会让接口在演示环境里失去区分能力。

### 第 2 条 · `CallSession` 的线程安全 —— **不采纳，但它指出的现象是真的**

**它说**：`begin()` 先写 `id` 再写 `beganAt`（两条语句），`id()` 不同步地读这两个字段，存在"读到新 id、旧 beganAt"的窗口。但它自己判断"实际后果极小"，两种可能（误判过期 / 旧 id 多活一会儿）都不会串场，**结论是可以不改**。

**处理**：**采纳它的结论（不改行为），但顺手把 `id()` 也加了 `synchronized`。**

理由：这些方法一秒最多被调几次，加锁的代价可以忽略；而"理论上存在但无害"的窗口留着，以后每读一遍这段代码都要重新论证一次"它真的无害"。用一行 `synchronized` 换掉这个反复论证，值得。

### 第 3 条 · `reuseOrBegin` 的空值处理 —— **真问题，已修，实测通过**

**它说**：

```
电话 A 响铃，系统送空串 → begin(null)，number = null
电话 A 通话中，系统后送号码 13900001111 → reuseOrBegin → blank(number)=true → 复用 ✓
电话 B 响铃（呼叫等待），系统又送空串 → reuseOrBegin("") → blank(number)=true → 复用 ✗ 串了
```

根因一句话：**空串意味着"不知道号码"，代码却把它当成了"和任何号码都匹配"。**

**这条是整批最有价值的意见**，因为它直接指出了我们自己代码注释里的矛盾 —— 类注释写着"下一通电话来了要换新 id"，而 `blank()` 分支让这件事在某些情况下不成立。

**它给了两个方案**：
- 方案 A：在 `CallSession` 里记通话状态，`IDLE` 状态下收到空号码就开新场
- 方案 B：空号码时只在 `beganAt` 距现在很近（如 5 秒）时才复用

**我采纳方案 A，不采纳方案 B。** 理由：

- 方案 B 的阈值是它自己承认"猜的"（它的原话：我没有你们的实测日志来确认系统送空串的时间窗口到底有多长）。**而我们有日志**：响铃 `15:20:59` → 接通 `15:21:03`，约 4 秒。用 5 秒刚好卡在边缘，一旦系统慢一点就会劈成两场 —— 这个坑我们在 11-11 上午刚踩过（`来号=13900001111 存号=` 那次）。
- 方案 A 用状态而不是用时间，不依赖任何猜出来的常数。挂断就是挂断，这是个**事实**，不需要阈值。

**实现**：

```java
private static final int RINGING = 0, OFFHOOK = 1, IDLE = 2;

static synchronized String reuseOrBegin(String number) {
    boolean blankNum = blank(number);
    if (phase == IDLE && blankNum) return beginOffhook(number);   // ← 新增的守卫
    ...
}

static synchronized void end() {      // 新增，由 Guard 的挂断分支调用
    if (id == null) return;
    phase = IDLE;
    Log.i("YinDun", "会话=" + id + " 已挂断，id 保留 30 分钟");
}
```

**关键：`end()` 只改状态、不删 id。** 骗子最爱说"您先挂了，去银行 App 里操作"，真正转账那一步发生在挂断之后。删掉 id 等于把时间轴最关键的最后一格切掉。

**实测**（模拟器）：

```
19:33:19  通话开始 who=stranger num=13900006666 会话=cmwc1irhd58ysfz
19:33:31  级别升到 block（触发源=bank）原因=通话中打开银行
19:38:30  会话=cmwc1oyj0nx572n 已挂断，id 保留 30 分钟
19:35:45  通话开始 who=stranger num=13900005555 会话=cmwc1m0d2rqdvci   ← 挂断后新号码 → 新场 ✓
```

线上 RDS 核对同一场内的三条上报：

```
watch | ring       | cmwc1irhd58ysfz | 妈妈收到陌生号码来电
block | bank       | cmwc1irhd58ysfz | 妈妈正在进行高风险操作
high  | call_child | cmwc1irhd58ysfz | 银盾已自动呼叫家人
```

**没验到的部分，如实写**：方案 A 真正要防的是"挂断后号码为空"这一格，而模拟器的 `gsm call` 每次都送号码，**造不出这个场景**。所以这段逻辑只经过代码审查，没有实跑证据。真机上系统延迟送号时才可能命中，到时候看日志里有没有"已挂断"这条来确认 `end()` 被调到。

### 第 4 条 · `call_child` 的 60 秒去重 —— **不采纳（同意它的判断）**

**它说**：进程被杀重启后 `lastCallChildAt` 归零，但两条触发路径（判定阻断立即拨 + Shield 6 秒兜底拨）间隔只有 6 秒，进程不太可能在 6 秒内被杀又重启；即使发生，子女端看到两条"已自动呼叫家人"只是冗余不是错误。不值得为这个引入持久化。

**处理**：不改。它说得对，而且它主动提到了一个我们没做的事 —— 子女端可以按 `callId + kind` 去重。这个建议留给子女端，不过目前时间轴已经按 `callId` 归组展示，视觉上不会重复成两条独立事件。

### 第 5 条 · `Guard.kindOf` 的误分类 —— **部分采纳**

**它说**：新增触发源（比如 `"sms"`）时 `kindOf` 没有对应分支，会静默落进 `K_JUDGE`，子女端时间轴把"短信风险"画成"组合判据升级"；字符串比较没有编译期检查，拼写错误（`"bnak"`）也不报错。建议改用枚举，或至少把映射集中到一处并在 default 分支打日志。

**处理**：**采纳"集中 + 打日志"，不采纳"改枚举"。**

改枚举要动 `evaluate(String trigger)` 的全部 6 个调用点（`call` / `bank` / `install` / `a11y` / `code` / `tick`）和 `Judge` 的接口，改动面比问题本身大得多。折中方案：

```java
private static final String[] JUDGE_TRIGGERS = { "call", "install", "a11y", "tick" };

private static String kindOf(String trigger) {
    if ("bank".equals(trigger)) return Notifier.K_BANK;
    if ("code".equals(trigger)) return Notifier.K_CODE;
    for (String t : JUDGE_TRIGGERS) if (t.equals(trigger)) return Notifier.K_JUDGE;
    Log.w(TAG, "kindOf：未登记的触发源「" + trigger + "」，暂按通用判定上报");
    return Notifier.K_JUDGE;
}
```

要点是：把"**已知**走通用判定"的四个显式列出来，这样"没登记过"和"登记过"就分开了 —— 原来这两种情况都返回 `K_JUDGE`，无法区分。新增触发源忘了登记时，日志里会出现一条警告，而不是静默显示错图标。

（调用点只有判级升级时才走到，tick 每 5 秒一次但 `rank <= lastRank` 会提前 return，所以不会刷日志。）

### 第 6 条 · SQL 迁移的兼容性 —— **不采纳（确认我们写对了）**

**它说**：`information_schema.COLUMNS` / `STATISTICS` + `PREPARE`/`EXECUTE` 在 MySQL 5.7 和 8.0 都成立；`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 是 8.0.29+ 才有，5.7 不支持，所以"如果需要兼容 5.7 就没有更简单的纯 SQL 方案，当前写法已经是可重复执行迁移的最简方案"。

**处理**：不改。这条对我们最重要 —— **它验证了我们的选择是对的**，而且没有像 10-28 那次那样给出一个 MariaDB 语法。这段结论可以直接写进答辩材料。
