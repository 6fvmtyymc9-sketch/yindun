## 一、总评

**它做对的三件事**

1. **做了逐字比对，不是通读**。它把 App 端 `Judge.java` 和云端 `Judge.js` 并排放，指出 `toLowerCase`、验证码分值、负分钳位三处差异。这三处都是"看代码能看出来、跑起来才发现"的类型。
2. **敢说不确定**。文末列了 8 项"代码没给、无法确认"（`norm` 实现、`TinyBert.threshold`、`PER_EXTRA` 等），没有硬编结论。这比 10-28 那次强很多。
3. **指出了我自己的半个修复**。问题 10 说得准：上午我把"一律说别点链接"改成了"按内容分支"，但分支里的 URL 判据还带着"点击"两个字 —— 病根没除，只是换了个触发条件。

**它错的地方**

问题 7 判断方向错了：它以为 App 走云端 `/api/review`（返回 `isFraud`），实际 App 是**直连 MaaS**，提示词里要的就是 `scam`，两端本来就自洽。它没看 `Pangu.java` 的 `reviewSms` 实现就下了结论。

## 三、采纳的四条，具体改了什么

### 第 2 条 · 双端同源（最硬的一条）

它指出的三处差异逐条核实，全部成立：

| 差异 | App 端 | 云端（改前） | 后果 |
|---|---|---|---|
| 大小写 | `body.toLowerCase()` 后逐词 `contains(w.text.toLowerCase())` | `String(body)`，`text.includes(k.word)` | 「您的 ETC 已停用」在手机上命中 `ETC(+10)`，云端命中不了 |
| 验证码 | 非服务号 +45 | +30 | 同一条陌生号验证码：手机判 block、云端判 high |
| 负分钳位 | 有（`score < 0 → 0`） | 无 | 快递短信云端显示 -45 分，手机上显示 0 分 |

改完全部落在云端 `cloud/src/Judge.js`，因为 App 端的行为是对的、且已被真机验证过。

**改的过程中又抓到一个自己埋的坑**：第一次只把 `text` 小写化了，没有小写化词表里的词 —— 词表里 `ETC` 是大写，于是改成小写文本后反而谁都匹配不上。对拍时这条差 10 分（手机 63、云端 53），才发现。现在两端都做小写。

**对拍结果（同一批文本，两端各跑一次）**：

| 文本 | 云端 | 手机端 |
|---|---|---|
| 我是警察，你涉嫌洗钱…不要告诉子女 | 210 · block · S4 | 210 · block · S4 |
| 您的快递已到楼下驿站，取件码 8812 | 0 · none · S0 | 0 · none · S0 |
| 您账户于11月17日支出128.50元 | 0 · none | 0 · none |
| 请点击屏幕上的确认按钮完成设置 | 23 · watch · S1 | 23 · watch · S1 |
| 验证码 384912，请勿泄露给他人 | 45 · block · S4 | 45 · block · S4 |
| 您的 ETC 已停用，请点击 t.cn/Etc9 认证 | 63 · warn · S2 | 63 · warn · S2 |

六条逐分一致。

### 第 4 条 · 送审门限太宽

成立。`shouldReview` 的条件是「陌生人 + 正文 ≥15 字」，快递取件、社区体检、医院预约全部满足；而这条路径下模型一旦说 `scam=true`，会直接 `pushAlert("warn")` 弹到老人脸上。留出集里这三类正常短信被模型打出 0.711 / 0.996 / 0.980，也就是说误报是必然发生的。

改法不是收窄门限（那会漏掉真的），而是**改投递对象**：

- 本地判到 `watch` 以上 → 模型说可疑，照旧弹老人浮条
- 本地判 `none`（毫无把握） → **只推子女**，浮条标题写「妈妈收到一条短信，AI 觉得可疑」，由人来判断

理由写在代码注释里：老人被误报几次就会去关悬浮窗权限，而红屏依赖同一个权限，关掉等于整条防线废掉。

### 第 9 条 · 累计加成封顶

成立。原来是纯线性 `(count-3+1)*15`，第 8 条就是 +90，陌生人（新加的快递员、房东、装修工）连发八条正常消息就能被推到 block。

现在封顶 60（相当于最多认四条额外加成）。模拟器实测八条连发：

```
第 3 条 加成=15   第 4 条 加成=30   第 5 条 加成=45
第 6 条 加成=60   第 7 条 加成=60   第 8 条 加成=60
```

### 第 10 条 · 提醒文案

成立，三点全采纳：

1. **URL 判据里去掉"点击""点此"**。只认 `http`、`www.`、`t.cn`、`.cn/`、`.com/` 这类真正的网址形式，不拿动词猜。
2. **同时命中"转钱"和"回拨"时，不给"去核实"这个可执行动作**。因为「请拨打 021-xxxx 核实您的账户」里那个号码就是骗子留的 —— 教她"先打电话核实"，等于把她送进骗子设计的入口。这种情况只说「别按短信说的做，先问问家里人」。
3. **"核实"改口语**：「先打电话跟本人核实，别急着转钱」→「先问问家里人，别急着转钱」。

把方法单独抽出来跑了六组：

| 输入 | 输出 |
|---|---|
| 请点击屏幕上的确认按钮完成设置（无链接） | 别按短信里说的做，先问问家里人 |
| 您的 ETC 已停用，请点击 t.cn/Etc9 认证 | 请勿点击短信中的链接 |
| 请拨打 021-12345678 核实账户，把资金转入安全账户 | 别按短信说的做，先问问家里人 |
| 王叔，我手机丢了换号了，急用先转5万到这个卡上 | 先问问家里人，别急着转钱 |
| 您的快递已到驿站，取件码8812 | 别按短信里说的做，先问问家里人 |
| 点击链接 www.bank-verify.com 领取补贴 | 请勿点击短信中的链接 |

## 四、部分采纳的四条

### 第 1 条 · 去重会不会吞掉强信号

它担心：如果短词是弱信号、长词是强信号，短词被吞掉会漏判。

**逐对核过词表的 15 对包含关系，不存在这种情况**（脚本遍历，不是目测）：

| 短词 → 长词 | 权重 |
|---|---|
| 警察 → 我是警察 | +20 → +30 |
| 验证码 → 把验证码 / 验证码报 | +25 → +35 / +40 |
| 征信 → 征信黑名单 / 征信修复 | +20 → +25 |
| 点击 → 点击链接 / 点击下载 | +8 → +20 / +40 |
| 不要告诉 → 不要告诉子女 / 不要告诉家人 | +25 → +45 |
| 别告诉 → 别告诉家里人 / 别告诉我 / 别告诉子女 | +15 → +45 / +30 |
| 扣费 → 自动扣费 | +20 → +20（同分，不损失） |
| 公安 → 公安局 | +15 → +15（同分，不损失） |

**15 对里短词权重全部 ≤ 长词权重，去重不会让任何一条的分数变低。** 另外去重只作用于正向词（`hitList`），反例是单独一轮计算的，不会被吞。

它说的前两项（词义重载误报、反例钳位后可被利用）确实成立，但都不改：

- 词义重载（"到期""办理""续存"）需要看上下文，`contains` 做不到。这是规则法的边界，不是 bug。
- 反例钳位后最多把分数压到 0，压不成负数；骗子塞反例词最多把 90 压到 60，仍有 high。可接受。

### 第 3 条 · 端侧模型"只升不降"

成立，但**改不了**，原因要说清楚：

它以为阈值在 0.7 附近。实际 `TinyBert.THRESHOLD = 0.5`，所以那三条误报（0.711/0.996/0.980）全部会抬升。但留出集上把阈值从 0.5 调到 0.9，误报和漏报**一条都没变** —— 说明问题在模型本身（训练集只有 11 条"陌生人主动联系、事情本身正常"的样本），不在阈值。

换阈值只会让 0.711 那条侥幸躲过，0.996/0.980 照样抬升。所以这条等老师的 GPU 换模型，现在改阈值属于自欺。

它提的"`r.score` 与 `r.ruleScore` 别混用"是对的，现状已经分开（累计只用 `ruleScore`），写进维护注意事项。

### 第 6 条 · 点认识不能关防护

它的担心方向对，但结论要修正：

- **App 端是干净的**：`Acquaint.askIfNeeded` 只防"同一次响铃重复弹"，`onClick` 只做 `hide` + `toast` + `pushKnown`，没有改任何判定状态。这一条它判断正确。
- **云端确实在写窗口**：`Guard.markKnown(elderId, 15)` 会写 `known.until = now + 15 分钟`。但翻遍判定链，**没有任何代码读这个字段**（`grep known` 只找到写入点），所以行为上并没有真的违反铁律。
- **但这是个地雷**：一个叫 `known`、带 `until` 的字段摆在那儿，早晚有人接进判定，到那时铁律就在云端被推翻了，而且不会报错。

已改：`markKnown` 只记 `{marked, at}`，没有到期时间；`State.blank()` 同步去掉 `until`；接口提示语从「只免打扰 15 分钟」改成「已记录。不设免打扰」。

**另外查出一处它没提到的真问题**：`cloud/public/index.html`（评委看的演示页）里还留着真的 15 分钟免打扰 ——

```js
function showAcquaint(){
  if(knownMark && Date.now()-knownMark < 15*60*1000) return;   // ← 就是这条
```

后果有两个：评委点过「认识」再重跑一遍流程，第 1 步的弹层就不出来了，现场看起来像"点按钮没反应"；页面上还写着「15 分钟内不再询问」，跟我们对外说的铁律自相矛盾。已删掉抑制，文案改成「已记录：你认识这个号码（不会因此免打扰，动钱照样拦）」。

### 第 8 条 · 模型没有结论时

现状已经是对的：`Pangu.reviewSms` 直连 MaaS，失败走 `fail()` 回调，只记一条日志，不动任何本地状态 —— 符合"模型缺席时本地规则结论不被覆盖"的原则。它担心的 `ok:false` 是云端 `/api/review` 的形态，App 现在不走那条路。

它的另一条建议采纳：**界面上不并排显示"模型概率 71%"和"规则分数 45"**。两个量纲不同却都表示可疑度，老人和子女只会困惑。现在界面只显示规则分，AI 那一栏写结论不写数字。

## 五、不采纳的两条

### 第 5 条 · `score + 20` 是假分数

不成立——它看的是旧版代码。当前 `SmsReceiver.java` 第 541 行写的是：

```java
EventBus.pushAlert("warn", "AI 复审：" + reason, stage, -1);
```

上面还留着当初为什么改的注释（"这个 20 是拍出来的…传 -1 表示这条没有分数"）。它在文末自己也写了"可能是旧版"，判断是对的，只是材料里给的是旧片段。

**教训**：送审材料里贴代码要贴当前版本。这次 A1、B1 是脚本按行号重抽的，A4 那段是 11-12 版留下的，忘了替换 —— 白让它查了一遍。

### 第 7 条 · 字段名不匹配

它的推理链是对的（读 `scam`、返回 `isFraud` → 永远 false → 整层失效），但前提错了：**App 不经过云端 `/api/review`，而是直连 MaaS**（`Pangu.DEF_URL = https://api.modelarts-maas.com/v2/chat/completions`），`Pangu.reviewSms` 自己写的提示词要求模型返回的就是 `{"scam":...}`。两端是同一个文件定的，本来就自洽。

不过它的顾虑值得防一手：将来若改走云端，那边序列化的是 `isFraud`，这里会静默拿到 false，整个云端复核失效而且不报错。已加兼容：

```java
boolean scam = o.has("scam") ? o.optBoolean("scam", false)
                             : o.optBoolean("isFraud", false);
```

两个名字都认，哪天换路径都不会静默失效。

## 八、验证与遗留

**已实测**

- 双端六条文本打分逐分一致（见第三节表格）
- 浮条文案六分支（单测，方法抽出后跑）
- 连发加成封顶：八条实测停在 60
- 回归：陌生来电仍弹熟人询问卡、接听开银行仍红屏（号码 137 0000 2222，「暂停转账」）

**未实测，需要条件**

- 「本地判 none + 模型说可疑 → 只推子女」：需要构造一条本地 0 分、模型判诈骗的短信，模拟器上不好造。逻辑只有一处分支，但**没有跑过的代码就是没有跑过**，下次真机上遇到快递类短信时看子女端是否收到、老人端是否安静。
- 云端四处改动要部署到 ECS 才生效，目前只在本地。
- 演示页改动要在浏览器里点一遍（点认识 → 重跑第 1 步 → 弹层应照常出现）。
