## 三、DCS（Redis 6.0 单机 1G）

| 项 | 值 |
|---|---|
| 接口 | `POST https://dcs.cn-north-4.myhuaweicloud.com/v2/{project_id}/instances` |
| 实例名 | `yindun-redis-1119` |
| 实例 ID | `fc5524c5-ca55-4ca7-a1fd-bd39e3282a69` |
| 规格 | `redis.single.xu1.large.1`（1G，0.29 元/时） |
| 内网地址 | `192.168.0.138:6379`，密码鉴权 |
| 返回 | HTTP 200，`status=CREATING` → 约 2 分钟 `RUNNING` |

**踩坑 2（这次真正的坑）**：DCS v2 的可用区参数名是 **`az_codes`**，不是 `available_zones`。
传 `available_zones: ["cn-north-4a"]` 会报 `HTTP 400 DCS.4042 This AZ does not exist`——
**报错说"可用区不存在"，其实可用区没问题，是字段名不对**，换 4a/4b/4c/4g 全一样报错。
改成 `"az_codes": ["cn-north-4a"]` 立刻 200。

**踩坑 3**：`GET /v2/{project_id}/flavors` 返回 944 条规格，但**没有 `product_id` 字段，`az_codes` 也全是空数组**；
`GET /v2/{project_id}/products` 直接 404（`APIGW.0101`）。所以"先查 product_id 再创建"这条路走不通，
**创建时不要传 `product_id`，服务端自己匹配**。

**连通性实测（同一安全组内）**：

## 六、KooCLI 接线实测（2026-11-19 20:05，为包 C 做准备时发现）

包 C 要甲用码道 Skills 开通，前提是 KooCLI 能跑。实测出三个必须知道的东西。

### 6.1 `--password` 与 KooCLI 系统参数同名，命令行走不通

RDS 和 DCS 的创建接口都有 `password` 参数，而 KooCLI 自己也有一个系统参数叫 `password`。
直接写 `--password=xxx` 会立刻退出：

```
目标API中存在与KooCLI系统参数password同名的参数,无法识别--password的位置.
请确认该参数为:KooCLI系统参数(a);目标API参数(b);兼为两者(c):
```

**解法：用 `--cli-jsonInput=<file>` 传整个 body**，密码写在 JSON 里就绕开了。
（`huawei-rds` 的 SKILL.md 也记了这条，并说明 `printf "b\n"` 那个管道绕法在 7.2.12+ 已失效。）

### 6.2 两份 CreateInstance 的 JSON 结构已用「非法名探测」验证

把 `name` 故意写成 `"1"`（不满足 4~64 位、字母开头），让服务端先报名字错——
**错误落在名字上，就说明其余参数（VPC/子网/安全组/规格/可用区/密码/计费）全部被正确解析了**。
且名字非法会被直接拒绝，**不会真的创建实例、不产生费用**。

| 服务 | 实测返回 |
|---|---|
| RDS | `{"error_msg":"Invalid instance name length.","error_code":"DBS.280649"}` |
| DCS | `{"error_msg":"Invalid DCS instance name...","error_code":"DCS.4010"}` |

两份可直接用的 JSON 见 `docs/包C_给甲_码道开通RDS与DCS.md` 附录 A / B。

### 6.3 三个参数名细节

| 项 | 正确写法 | 错误写法会怎样 |
|---|---|---|
| DCS 可用区 | `--az_codes.1=cn-north-4a` | 写成 `available_zones` → `DCS.4042 This AZ does not exist`（**报错说可用区不存在，其实是字段名错**，换哪个区都一样） |
| RDS 区域 | body 里 `"region"` 与 `--cli-region` 必须同为 `cn-north-4` | 缺 body 的 region → `DBS.280243` |
| RDS 单机 | JSON 里 `"ha": {"mode": "single"}` | 不传会按默认走 |

### 6.4 顺带修正一处文档笔误

`docs/开通清单_RDS_DCS.md` 里子网 ID 原写作 `9bb53754-4e4c-4e00-b368-61059c9fbbe9`，
用 `hcloud VPC ListSubnets` 实测为 **`9bb53754-4a4c-4e00-b368-61059c9fbb9e`**（中间两位错位）。
照旧文档填会报"子网不存在"，已修正。

## 七、建受限数据库账号 `yindun` 并切换线上（2026-11-19 20:32）

对应老师原文 **C2-5**「建数据库账号 `yindun`，只授权给 `yindun` 库」（原文第 301 行）。
原文第 313/314/316 行后续所有命令都用 `-uyindun`，所以这条不是可选项，是 C4/C5 的前提。

### 7.1 为什么必须做（两个理由，都不是形式）

1. **不建，老师给的命令跑不通**：他后面写的 `mysql -uyindun -p yindun < ...` 会认证失败
2. **`root` 是真实风险**：能删任何库、能建用户、能改权限。`.env` 里明文存着这个密码，
   一旦泄露（误提交/截图/日志），整个实例可被删库。换成 `yindun` 账号，最坏只能动 `yindun` 一个库

### 7.2 建的账号与授权范围

```sql
CREATE USER IF NOT EXISTS 'yindun'@'%' IDENTIFIED WITH mysql_native_password BY '<密码>';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, INDEX,
      CREATE TEMPORARY TABLES, LOCK TABLES, CREATE VIEW, SHOW VIEW
  ON `yindun`.* TO 'yindun'@'%';
FLUSH PRIVILEGES;
```

**为什么用 `mysql_native_password` 而不是默认的 `caching_sha2_password`**：
node 的 `mysql2` 在**非 SSL** 连接下用 caching_sha2 需要 RSA 公钥交换，容易失败；
而老师 C2-3 明确要求「不要开启强制 SSL」。两者叠加，用 native 最稳。

**没给的权限**（都是有意不给）：`GRANT OPTION`（不能自我提权）、`FILE`（不能读服务器文件）、
`*.*` 上的任何权限（不能跨库）、`PROCESS`/`SUPER`（看不到别人的连接）。

### 7.3 权限边界实测（四项正向 + 四项负向）

| 测什么 | 结果 |
|---|---|
| 读 `yindun.yd_alert` | ✅ 1581 |
| 建表 → 插入 → 读回 → 更新 → 删除 → 删表 | ✅ 全通 |
| 业务写入路径（`POST /api/report` 非 dryRun） | ✅ `reports` 1225 → 1226，随后删除恢复 1225 |
| 读 `mysql.user` | ✅ 被拒 `ERROR 1142 SELECT command denied` |
| `CREATE DATABASE should_fail` | ✅ 被拒 `ERROR 1044 Access denied` |
| `GRANT ALL ON *.* TO 自己` | ✅ 被拒 `ERROR 1045 Access denied` |
| `SELECT load_file('/etc/passwd')` | ✅ 返回 `NULL`（无 FILE 权限） |
| `SHOW DATABASES` 可见范围 | 只有 `yindun` + `information_schema` + `performance_schema` |

### 7.4 切换后确认（不靠 health 那个 true）

- `information_schema.processlist` 里 3 个连接的 `user` 字段全部是 **`yindun`**，`db=yindun`
- `ss -tnp` 见 node 进程与 `192.168.0.90:3306` 的三条 ESTAB
- `health` 的 `statsAll` 仍是 `{events:0, alerts:1581, reports:1225}`
- 回滚备份：`/opt/yindun/.env.bak.dbuser_2032`（改回 `RDS_USER=root` + 原密码即可）

### 7.5 脚本已入库：`tools/setup_db_user.sh`

```bash
bash tools/setup_db_user.sh <RDS内网地址> <root密码> [新账号密码]
```

幂等（重复跑只重设密码），自带四项边界检查，**甲开新实例后一条命令复用**。

> ⚠️ **脚本曾有一个 bug，已修，记在这里防复发**：脚本开了 `set -o pipefail`，
> 而负向检查原本写成 `if mysql ... | grep -q denied` —— `mysql` 报错退出码为 1，
> `pipefail` 取管道最后一个非零退出码，导致 `grep` 明明匹配成功了，整个 `if` 仍判为假，
> 输出「竟然能读系统表，权限过大」的假警报。
> **修法**：先 `OUT=$(...)` 取输出到变量，再 `echo "$OUT" | grep -q` 判内容，不看管道退出码。
> 这类写法在 `pipefail` 下普遍成立，以后写带负向判断的脚本都要注意。
