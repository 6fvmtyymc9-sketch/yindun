## 4. 必须说清的局限（答辩/材料里不许省略）

1. **样本量 9/30，比例 4:5 不代表真实分布。** 真实场景里诈骗来电占比远低于此，本次是刻意配平的评估集，不能据此推"日常误报率"。
2. **只有 4 个诈骗类型，且同类型只有 1~2 条。** 更隐蔽的类型（刷单返利、养老理财、医保卡、屏幕共享、ETC 过期）一条都没有，漏报一定会在补齐后出现。
3. **同一对人、同一版脚本。** 语速、口音、用词高度相似，实际表现可能优于陌生人对陌生人的真实通话。
4. **外录 ≠ App 端采集。** 评估集是 iPhone 免提外录 44.1 kHz，App 真机采集是安卓系统内录（通常 8k amr）。外录更清晰，**分数可能偏乐观**，不得表述为"等价线上输入"。
5. **未冻结。** `frozen: false`，随时可改；按老师要求，冻结前不得用于训练，也不得对外报分。
6. **纪律边界**：本评估集自始至终只用于打分，**没有拿它调过任何规则或阈值**——`docs/微信合并通知漏报修复`、判定链 3.6 / 3.7 等改动都发生在本批录音之前。这一点是这份基线可信的前提。

## 6. 一次严重的标注事故（留证，防再犯）

第一版跑出来是"误报 100%、召回 0%"，看着像判定链完全坏了。实际是**标签整体反了**：

- 我先按"文件序号 = 脚本场次"推场景，用户又口述过一次映射，两者叠加后我直接采信；
- 逐条 ASR 核对后发现用户是**倒着录的**——先倒录诈骗（文件 6→2 = 脚本 16→20），再倒录正常（文件 10→7 = 脚本 02→05），文件 1 是试录短版。

**改正后指标从 0% 翻成 100%。** 也就是说，标签错一位，结论就完全相反。

**由此定下的规矩（写进流程，不再破例）：**

1. 场景与标签 **一律以 ASR 转写核对为准**，不按序号推、不按口述填；
2. 每批录音入库后必须跑 `tools/verify_labels.py`，不一致按实际内容改名，矛盾就报；
3. `labels.json` 的 `_确认` 字段记录"谁、何时、确认了什么"，便于回溯。
