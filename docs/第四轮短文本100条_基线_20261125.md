## 三、三个发现

### 发现一：A 组 36 条落在 S1「套近乎」，这是**分级正确**，不是失败

分级定义（`server.js:64`）：`S1 套近乎(15分) → S2 吓唬(40) → S3 隔离(70) → S4 要钱(90)`。

A 组的题按老师要求**只有诱饵、不含任何索款动作**，因此它们客观上确实只到「套近乎」这一级。
模型没有把它们硬抬到 S4，是**判对了级别**，不是「识别力度不够」。

> 推论：A 组能证明的是「模型提前看到了苗头」，**不能用来证明「拦得住」**。
> 拦截靠通话链路（`/api/callaudio` 三票），不靠短文本。写材料时这两个不能混。

### 发现二：5 条漏报里，模型给的理由是对的 —— 暴露了「诱饵与正常信息同构」的不可判边界

| 编号 | 类型 | 正文 | 模型理由 |
|---|---|---|---|
| A17 | 贷款提额 | 综合评估你的个人资质，可授予一笔信用额度，可用于日常消费或者经营周转使用。 | 贷款营销短信，无威胁或索要信息 |
| A19 | 贷款提额 | 针对个人用户推出无抵押授信方案…可以获得对应的可借贷额度。 | 贷款营销短信，无威胁诱导转账 |
| A20 | 贷款提额 | 你的个人信用评估更新完成，平台给到备用金额度… | 贷款营销短信，无恐吓或索要信息 |
| A22 | 贷款提额 | 平台针对存量用户重新测算授信，部分用户可以拿到比原先更高的可借贷额度。 | 贷款平台营销短信，无诈骗话术 |
| A35 | 冒充熟人 | 我更换了号码，原先的号码不再使用，后续联系会使用这个新的号码。 | 仅告知换号，无索财或恐吓 |

**这 5 条判「无风险」，在文本层面是站得住的。**
「可授予一笔信用额度」和正规银行的贷款营销短信字面同构；「我换了号码」和真实的换号通知字面同构。
真正的区别在**之后会发生什么**（收手续费、发来收款码），而 A 组规则禁止写后续动作 —— 于是这两类在单条文本上**客观上不可判**。

按类型看得很清楚：

| 类型 | 召回 | 为什么 |
|---|---|---|
| 兼职刷单 / 投资荐股 / 冒充客服 / 公检法 / 中奖 / 婚恋 | 8/8、8/8、6/6、6/6、5/5、5/5 | 诱饵自带异常（「点赞赚钱」「圈内渠道」「名下订单异常」「牵扯案件」「幸运用户」） |
| **贷款提额** | **2/6** | 诱饵与正规营销同构 |
| **冒充熟人（换号类）** | **5/6** | 换号本身是完全正常的社交行为 |

> 这个边界不是模型缺陷，是**短文本判定的物理上限**。产品设计里「对原号回拨核实」这条兜底，正是为它准备的。

### 发现三：判诈骗率 52%（理想 50%），校准正常 —— 与 SFT 单模型形成鲜明对照

同一批 B 组 50 条真短信，两个对象判诈骗的比例差 5 倍以上：

| 对象 | 判诈骗 | 背离理想值（0%） |
|---|---|---|
| 产品链路（规则 + DeepSeek） | 5~7/50 = 10%~14% | 10~14 个点 |
| **SFT 单模型**（`/judge`，直接喂短信） | **38/50 = 76%** | **76 个点** |

而 100 条平衡集上，产品链路判诈骗 52%（理想 50%）——**几乎没有系统性偏向**。

> 注意：那个 76% **不能当产品指标**。49/50 条理由在分析「通话」，3 条凭空编出「左声道/右声道」「受害方紧张语气」，
> 且 `mergeSft` 只在 `CallAudio.js`，**短信链路根本不调用 SFT**。详见 `第四轮短文本B组50_基线_20261125.md` 第四节。

### 发现四：A 组那 36 条 S1，在 App 端是「watch」级 —— **不弹窗、不推子女端**

这条必须主动说清，否则「召回 90%」会被误读成「90% 都被拦住了」。

App 端分级规则（`Judge.java:914-919`）：

```
S4 → block（一律盖屏）
S3 → score >= 70 ? block : high
S2 → score >= 70 ? high  : warn
S1 → score >= 45 ? warn  : watch      ← lvWarn 默认 45
```

而 S1 的分数区间是 **15~39**（到 40 才进 S2），**永远够不到 45** → **S1 必然是 watch**。

watch 在短信路径上的处置（`SmsReceiver.java:171`）：

```java
if (!"none".equals(r.level) && !"watch".equals(r.level)) {
    EventBus.pushAlert(...);      // 只有 warn/high/block 才推子女端
}
```

→ **watch 不推预警、不弹通知**，只在本地留一条底层记录。

| 所以「A 组召回 90%」的准确含义 | 不是 |
|---|---|
| 模型**读懂了** 45/50 条钩子短信在铺垫什么 | 不表示 45 条都被用户看到或被拦住 |
| 衡量的是**语义理解能力** | 不是**保护效果** |

这不是缺陷。只有诱饵、不索款的短信，本来就不该弹窗骚扰用户 —— 真弹了才是误报。
它的价值在于「模型心里有数」，等通话真的打进来、出现"吓唬/隔离/要钱"时，分级自然升上去。

**但这也暴露了第四轮真正的设计题**：要让这种钩子短信在**短信阶段**就起作用，
只能降低阈值或改分级 —— 而 B 组那 10%~14% 误报会立刻上升。
**「提前预警」和「不打扰」在短文本上是一对硬矛盾**，不是调参数能两头都占的。

## 四、这 100 条在项目里的定位

| 它是什么 | 它不是什么 |
|---|---|
| 第四轮的**验收尺子**：改之前多少分、改之后多少分，同一套题量 | **不是训练数据**。一条都没进训练集，对模型准确率提升的贡献是 0 |
| 回答「优化有没有用」的唯一证据 | 不能拿去微调 —— 进了就是「对着考题训练」，老师明令禁止 |
| 支撑「规则永远分不清『我要你转账』和『别信那些让你转账的』」这句结论的原始数据 | 不能替代通话链路的评估（音频侧基线见 `第四轮基线_TAF200_20261124.md`） |
