# 通话中的自动拨号：为什么不能硬拨

> 2026-11-12 实现并实测。对应提交见 `git log --grep="通话中"`。

## 一、原来的行为，和它为什么不行

判定为阻断级时，`Notifier.callChild` 会直接：

```java
Intent i = new Intent(Intent.ACTION_CALL, Uri.parse("tel:" + num));
ctx.startActivity(i);
```

老人正在和骗子通话时，这行代码换来的是安卓的一个**英文系统框**：

```
Cannot place a call at this time.
There are already two calls in progress.
```

2026-11-11 在模拟器上实拍到。三个问题：

1. **老人看不懂。** 整句英文，主角又是一个 70 岁的人。
2. **它盖在通话界面上。** 本来在盖屏和提示卡之外又糊一层，比不弹更慌。
3. **拨了也没用。** 骗子正在电话里指挥她转账，我们这通电话根本接不通。

第 3 点是最要紧的：**这个动作在物理上就不可能成功。** 失败的方式还很难看。

## 二、改成两条路

`Notifier.callChild` 先问一句 `CallSession.inCall()`：

| 情形 | 处理 |
|---|---|
| 空闲 | 照旧立刻拨（`dialChild`） |
| 通话中 | ① 立刻推一条高优告警请子女**主动回拨**；② 记下这通呼叫，挂断后补拨 |

### 为什么让子女回拨，而不是我们挂断后再打

子女回拨走的是**呼叫等待**，能在骗子还在说话的时候插进去。我们等老人挂断再拨，
往往已经是十几分钟以后，钱可能已经转出去了。

所以通话中那一刻，真正有价值的是那条推送，不是那通电话。

### 为什么补拨要等 3 秒

刚挂断时立刻发 `ACTION_CALL`，系统有一小段时间还认为通话没结束，会直接拒掉。
3 秒是实测能过的最小值。

### 为什么挂断后仍然要补拨

推送只是通知，不是行动。老人那只手机放在桌上、子女在开会没看见，都是常事。
一通真的打进她手机的来电，比任何通知都难忽略。

## 三、文案为什么改了

原来一律上报「银盾已自动呼叫家人」。改动之后，通话中那一格**电话并没有打出去**，
再这么说就是让子女看到一件没发生的事，他甚至会以为妈妈已经被叫到了。

所以分成两种说法：

| 时刻 | 标题 | 正文 |
|---|---|---|
| 通话中（没拨出去） | 老人还在通话中，银盾打不进去 | 银盾已记下这通呼叫，挂断后会自动拨给您（号码）。这通电话请您现在就主动回拨，越快越好。 |
| 真的拨出去了 | 银盾已自动呼叫家人 | 已自动拨出：号码 |

时间轴上会因此出现两条 `kind=call_child`，这是如实反映——"想拨但打不进去"和
"已经拨出去"是两件事，合成一条就是撒谎。

## 四、实测暴露的第二个坑：连环拨号

第一版改完，日志是这样的：

```
19:23:56.532  会话=cmwdgjq99oeie9f 已挂断
19:23:56.532  通话结束，3 秒后补拨给家人（这通呼叫等了 58 秒）
19:23:59.735  已自动拨给子女 13800138000        ← 补拨成功
19:24:02.698  正在通话中，本次不硬拨，改记下来等挂断后补拨  ← 又排队了
19:24:09.334  正在通话中，本次不硬拨，改记下来等挂断后补拨  ← 又排队了
```

原因：补拨出去之后，**我们自己就处在通话中**；而老人的假银行 App 还留在前台，
`AppWatcher` 每秒都在报「前台出现银行类 App」，每报一次就调一次 `callChild`，
于是每报一次就排一次队。女儿那通一挂断，`flushQueuedChildCall` 又拨一次。

**结果是连环拨号，老人的手机永远占线。**

同一场诈骗里只该拨一次。没接通是家人那边的事，不该拿老人的电话去重试。

两处护栏：

```java
// 1) 冷却：拨出去之后 5 分钟内不再排队
if (lastCallChildAt > 0 && since < QUEUE_COOLDOWN_MS) { ... return; }

// 2) 去重：已经有一通在排队，就不重复记、也不重复推子女端
if (queuedChildCallAt > 0) { ... return; }
```

注意 `lastCallChildAt`（拨出时刻，用于冷却）和 `lastCallChildPushAt`（上报时刻，
用于 60 秒去重）是**两个变量**。混成一个的话，60 秒内重复拨号不会刷新冷却时间，
冷却窗口就形同虚设。

## 六、已知边界（如实记）

1. **排队状态是内存态，没有持久化。** 进程被杀就丢。之所以不落盘：能走到排队这一步，
   说明老人正在通话中、子女已经收到高优告警；这种情况下再多一份磁盘状态，
   复杂度不划算。码道对 60 秒去重也是同样的判断（见 `码道审查记录_第2批.md` 第 4 条）。
2. **排队最多等 10 分钟。** 超过就作废——十几分钟后突然拨出去比不拨更吓人。
3. **"刚挂断又接了一通"会再延后 3 秒。** 骗子回拨、呼叫等待进来都属于这类，
   这时不能硬拨，`flushQueuedChildCall` 里会把排队重记一次。
4. **真机上没验。** 以上全部是模拟器实测。真机上如果 `ACTION_CALL` 需要额外权限
   （部分 ROM 的"后台弹出界面"），补拨可能被拦，届时日志会出现
   `自动拨号失败（缺 CALL_PHONE 权限？）`。
