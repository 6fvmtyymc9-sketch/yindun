## 二、第一条线：把模型接进线上（最优先）

### 2.1 前置条件（老师负责）

- ECS 恢复可用（欠费或续费处理完）。**ECS 不恢复，这条线无法开始。**
- 问学校管理员：GPU 容器长期主动往外连一条 SSH 隧道是否允许。

### 2.2 步骤

按 [`改造方案.md`](改造方案.md) 阶段 A 的 A1～A7 做，命令都写在那里。要点：

1. **测连通（A1）**：在 GPU 容器上测能否连到 ECS 的 22 端口。连不上就让 ECS 的 sshd 同时监听 443，再测。
2. **ECS 建隧道专用账号（A2、A3）**：账号不给 shell，`authorized_keys` 里限制成 `restrict,port-forwarding,permitlisten="127.0.0.1:8099"`，只能做这一个端口转发。
3. **SFT 服务只在容器本机监听（A4）**：`sft_server.py` 改用 `--host 127.0.0.1`，不再对校园网开放。自己测试改用 SSH 端口转发。
4. **起隧道并保活（A5）**：`tools/sft_tunnel.sh` 循环重连，nohup 后台运行，日志写 `~/tunnel.log`。
5. **ECS 接入（A6）**：ECS 的 `.env` 填 `SFT_URL=http://127.0.0.1:8099`，重启 Node。**先接原始模型**，不设 `SFT_LORA`。
6. **调等待时间**：`cloud/.env.example` 里 `SFT_WAIT_MS=8000`，但原始模型 `/judge` 单次要 3～60 秒（见 [`SFT接口说明.md`](SFT接口说明.md)），8 秒会大量超时，等于没接。用 `demo/calls` 三段录音实测每通耗时，按实测值设 `SFT_WAIT_MS`，并把实测表写进文档。
7. **一键恢复脚本（A7）**：新建 `tools/school_gpu_setup.sh`。容器被重建后，一条命令把依赖、模型权重、LoRA、SFT 服务、隧道全部拉起来。要在一个干净的新容器上真跑一遍才算完成。
8. **演示当天检查清单**：写进本文末尾，至少包括：容器在线、`/health` 正常、隧道在、ECS 上 `curl 127.0.0.1:8099/health` 通、一通 demo 录音结果里带 SFT 的 p。

### 2.4 实测耗时与 `SFT_WAIT_MS` 的依据

`/judge` 是原生两轮问法（判场景 → 写分析 → 出 JSON），不是 0.15 秒的 `/risk`，耗时必须实测。

| 测试集 | 样本 | 单次耗时（SFT 部分） |
|---|---|---|
| `demo/calls` 三段 | 13600003333（正常） | **4.1s** |
| | 13700002222（诈骗） | **4.5s** |
| | 13900001111（诈骗，最长） | **29.9s** |
| 冻结评估集 30 通（11-21，代码注释留档） | 中位 / P90 / 最长 | **8.0s / 45.1s / 70.6s** |

**取 `SFT_WAIT_MS=60000`**：覆盖两组 P90 有余量；最坏 60 + 大模型约 5 = 65 秒，仍在手机端 90 秒读超时以内。30 通里那条 70.6 秒的会被放弃，**这是有意的**——为一条长录音把所有复盘拖到 75 秒不划算。

> ⚠️ `.env.example` 里原来的 `SFT_WAIT_MS=8000` 和"线上必须留空"都是 `/risk` 时代的结论（那时只比第一个 token，114~148ms）。11-20 改 `/judge` 之后 8000 会让每通都超时，等于白接。已一并改掉。

**第 3 条验收的原始数据**（`dryRun=true`，口径与正式调用一致但不落库）：

| 录音 | 端到端 | SFT p | SFT 结论 | stage | 与标签 |
|---|---|---|---|---|---|
| 13600003333 | 3.7s | 0.100 | normal | S0 | ✅ |
| 13700002222 | 4.5s | 0.980 | fraud | S4 | ✅ |
| 13900001111 | 30.1s | 0.980 | fraud | S4 | ✅ |

第三票 3/3 与人工标签一致，理由也是对的（"冒充公安人员，以洗钱案件为由诱导提供身份证号码，并制造紧急氛围阻止受害人联系家人"）。

### 2.5 A4：服务已收到回环

`sft_server.py` 原来监听 `0.0.0.0`，对校园网开放。已改为 `127.0.0.1`（`~/start_sft.sh` 同步改，原文件备份为 `start_sft.sh.bak_20261124`）。

验证：容器对外 IP `10.42.9.178:8000` 现在连不上（`000`），隧道与线上判定不受影响。同学以后要自己测，用 SSH 端口转发。

### 2.6 踩到并修掉的一个坑：两套隧道守护抢端口

`tools/sft_tunnel.sh` 是"断了就 5 秒后重连"的循环，所以**只杀 `ssh -N` 不杀守护脚本，它自己会连回来**。于是新旧两套守护抢同一个 `127.0.0.1:8099`，抢输的那套在日志里刷：

```
Error: remote port forwarding failed for listen port 8099
```

**2026-11-21 那次"隧道起不来"很可能就是这个**（日志里同样是这一行，不是 `permitlisten` 配错）。现在的处理：

- `sft_tunnel.sh` 的 `-R` 显式写 `127.0.0.1:8099:127.0.0.1:8000`（`permitlisten` 只认这个，不写 host 会被拒）
- `school_gpu_bringup.sh` 启动前数守护脚本，**多于 1 份就全清再起**；`--restart` 先杀守护再杀 ssh（顺序反了会被重连抢回端口）
- 匹配串写成 `[s]ft_tunnel\.sh` / `[1]27\.0\.0\.1:8099:`——否则 `pgrep -f` 会匹配到执行它的 shell 自己，把命令杀了

### 3.2 训练数据怎么改

按第三轮报告 §7.8 总结的三个方向，再加音频：

1. **补只有诱饵、不索款的短诈骗**：兼职、理财、内测名额、屏幕录制退款这一类，从 `Telecom_Fraud_Texts_8` 里挑短条目，不够再人工补。
2. **补含高危词但合法的正常样本**：反诈宣传、验证码通知、社区与物业通知、亲友代传话。
3. **正常侧理由不许再套「这是一通关于 X 的正常沟通」**：必须写出具体依据，比如「对方只告知配送时间，没有索要任何信息」。
4. **加入音频样本**：TeleAntiFraud 那部分拿一部分原始录音直接作为音频样本训练（原模型就是音频训练出来的），其余仍用转写文字。音频与文字的比例写进报告。
5. **leak_check 同时对旧测试集和新测试集做**，包括 TAF-200 的文件编号和短文本-100 的文本去重。
6. 开训前照旧验收 `summary.json` 的 answers：理由几百种、诈骗 p 0.85～0.98、正常 p 0.03～0.25。

训练参数沿用第三轮，只改数据。若音频样本导致显存或时长超限，在报告里写明调了什么、为什么。

### 3.3 成功标准（按线上口径：音频，p≥0.85）

- [ ] TAF-200：诈骗召回**不低于**原始模型，正常误报**不高于**原始模型

- [ ] 每通耗时记录在案（LoRA 输出短，应明显快于原始模型）
