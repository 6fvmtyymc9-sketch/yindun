## 一、必须改（会被当场问穿）

### 1.1 行号错：`597` → **614**，`635` → **658**

他在这四个地方写了行号：`run.js:18`、`run.js:21`、`README.md:72`、`README.md:79`、
`评估终报(1).md:52`、`:72`、`:196`。

实读结果（`grep -n` 于 `cloud/src/server.js`）：

```
614:  const isFraud = ai ? ai.isFraud : local.level !== 'none';
658:    if (result.isFraud && result.stage >= 3) {
702:    wouldAlert: !!(result.isFraud && result.stage >= 3),
```

**正确写法**：判定 `server.js:614`，推送子女端 `server.js:658`，试跑预演 `server.js:702`。
（这两个数我 11-19 上午给过他 597/635，是我的错。647 行那次改动把整段往后推了 17 行。）

### 1.2 `levelOf` 映射记错：S3 不一定是 block

他三处都写「S1=watch / S2=warn / S3+=block」。实读 `Judge.js:337-353`：

```js
switch (stage) {
  case 'S4': return 'block';
  case 'S3': return score >= (L.high || 70) ? 'block' : 'high';   // ← 这里
  case 'S2': return 'warn';
  case 'S1': return 'watch';
  default:  return 'none';
}
```

`levels = {watch:25, warn:45, high:70, block:90}`。所以 **S3 且分数 <70 时是 `high`，不是 `block`**。

这条错本身不影响结论（评估用的是 `stage`，不是 `level`），但它说明「level 和 stage 一一对应」这个
隐含假设是错的。答辩时只要有人翻到这一行，前面所有"等价推导"都会被要求重新论证一遍。

**正确写法**：`S0→none、S1→watch、S2→warn、S3→block 或 high（看分数是否 ≥70）、S4→block`。
「非 S0 即非 none」这个等价仍成立，可以保留，但推理链要写成"因为只有 S0 落 none"，而不是"S3 就是 block"。

### 1.3 「融合」不是融合，是 **DeepSeek 单路**

这是最重的一条。他（和我）一直说「融合 = 规则 + DeepSeek 的最终结论」，写了五处
（`run.js:278` caveat2、`README.md:168`、`评估终报:105`、`:134`、`:49`）。

实读源码，三层证据：

```
server.js:589   const ai = await pangu.analyzeSms({ text, imageBase64: ..., mime: ... });
                ↑ 只传了这三样，没有 rules、没有 local
Pangu.js:237    const { text = '', imageBase64 = null, mime = 'image/png' } = input;
                ↑ 函数内部也只解这三样
server.js:614   const isFraud = ai ? ai.isFraud : local.level !== 'none';
                ↑ 模型在的时候，isFraud 完全取自 ai，规则一点没参与
server.js:613   const stage = ai ? ai.stage : (...local.stage...);
                ↑ stage、type、reason、advice、signals 同理，全是 ai 的
```

**规则在线上只做两件事**：模型不可用时兜底；把 `localScore` 落库留痕。它**不参与**模型的判断，
模型也**看不到**规则命中了什么词。

所以 `14.6%` 的正确名字是「**DeepSeek 单路判定漏报**」，不是「融合」。这反而是个更硬的结论
——模型不靠规则提示也能干到 14.6%——但名字必须改，否则老师一问"融合的增益从哪来、规则贡献了几个点"
就答不上来。

> 顺带：这也解释了为什么 `who="stranger"` 那组数字（4.2%）在线上测不出来——
> 那是规则层的加权，而模型的判断根本不看 `who`。

### 1.4 「识别层」这个名字与"推送子女"不符

他写「识别层 = `local.level !== 'none'`，含义：子女端收到提醒」（`run.js:112`、`README.md:78`、
`评估终报:40`）。

但 `server.js:658` 写得很清楚：

```js
if (result.isFraud && result.stage >= 3) { await db.addAlert(...); pushTo(...); }
```

**S1、S2 不会推给子女端，一条都不会。** 真正推的门槛是 `isFraud && stage >= 3`。

于是那两行要改名：

| 现在的名字 | 实际是什么 | 规则漏报 | 
|---|---|---|
| 识别层 18.9% | **判定层**（判它为诈骗，`isFraud`） | 18.8%（本地） |
| 拦截层 50.0% | **推送层**（真推到子女端，`isFraud && stage>=3`） | 49.8%（本地） |

「18.9% → 14.6%」这个对比仍然成立（两边都是 `isFraud` 判定口径），**只是标题要改成「判定层」**。
而「推送层」目前只有规则一列（49.8%），**DeepSeek 那一列还没算**——因为结果文件里没有存
`pred_online && stage>=3`。这个数必须补出来，不然"模型把漏报降到 14.6%，其中多少真推送出去了"
答不上来。

## 二、九个正常样本这件事，必须摆在明面上

这是整套评估最脆的一环，现在被写成了「误报 0%」，太干净了，干净到会被追问。

### 2.1 分母是 9，一条误报就是 11.1%

1070 条诈骗 + **9** 条正常。`误报 0.0%` 的实际含义是 `0/9`。
答辩时说「误报率 0%」，评委只要问一句「正常样本多少条」，这个数字就废了。

**建议写法**：「9 通真人正常对话，**0 条误报（0/9）**；样本量小，只能作为定性结论，
扩大样本是下一步」。把 9 写进句子里，比藏起来安全。

### 2.2 这 9 条不是"来电"，是 30 分钟的会议录音

`labels.json` 里 9 条全是 MagicData 的会议/闲聊语料，单条 **4,216–6,884 字**，
而 Fraud-R1 诈骗样本中位 **701 字**，真实短信 **几十字**。

而规则 `scoreSms` **不截断**（`Judge.js:144` 直接 `String(body).toLowerCase()` 全量 `includes`），
所以 6642 字的文本被整篇扫一遍词表 —— 命中概率天然高于短信。
（模型那边反而截断了：`Pangu.js:252` `String(text).slice(0, 1200)`。）

**两路口径不一致**，这是事实，写进局限即可；但别说成"真实通话误报率"。

### 2.3 「全部 S0 / 0 分」—— 分数不是 0

`README.md:116`、`评估终报(1).md:66` 写「全部 S0 / 0 分 / 非诈骗」。

实测（`who=''`，即评估脚本的默认，因为 `run.js:148` 只传 `text`）：
9 条全部 S0 ✅，但**最高分是 7 分**（magic-003，命中「急需」+12 与「工资」−5 抵消后）。
`0 分`应改为「全部 S0，最高 7 分」。

### 2.4 一旦带上 `who='stranger'`，9 条里 6 条进 S1

这条最容易被抓。他终报第 67 行写「队长本地脚本按陌生号码 +15 分计，级别是 none/watch，结论一致」
—— **结论不一致，是 6/9。**

本地复算（`cloud/test/threshold-audit.js`）：

```
■ who=（空）      判定层漏报 201/1070 = 18.8%   误报 0/9 = 0.0%    正常样本落级 {none:9}
■ who='stranger'  判定层漏报  45/1070 =  4.2%   误报 6/9 = 66.7%   正常样本落级 {none:3, watch:6}
                  推送层漏报 448/1070 = 41.9%   误报 0/9 = 0.0%
```

原因是词表里「陌生号码 +15」，这 15 分让任意陌生来电阻力直接跨过 `watch=25` 那条线。

**但请注意一个能救场的细节**：`who='stranger'` 下**推送层误报仍是 0/9**——因为这 6 条只到 S1，
够不上 `stage>=3`。所以正确的回答是：

> App 带陌生号加权时，判定层会有 6/9 进 S1，但推给子女端的门槛是 S3，**实际推送 0 条**。
> 也就是说不会打扰子女，但会在老人端的"待确认"里多几条。

这句话现在报告里没有，但评委大概率会问。**补上比被问出来强。**

## 三、脚本里的真问题

### 3.1 `callaudio-evidence.py` 在污染生产库（**最急**）

`POST /api/callaudio` **没有 dryRun**（`CallAudio.js:96` 整段没有这个分支）：

- `CallAudio.js:238` 判到 `warn` 及以上 → `db.addAlert()` + `pushTo()` 推给子女端
- `CallAudio.js:287` 判到 `high` 及以上 → `db.addReport()` 号码网入库

这个证据脚本每次跑 3 段，只要有一段被判 warn+，数据库就涨。
**而网上 `reports` 从同学甲 10:48 采样的 1219 涨到 11:25 的 1225，涨的这 6 条大概率就是这么来的。**

后果：同学甲的基线永远在动，"迁移前后逐项相等"这个验收方法会失败。

**怎么办**：`/api/callaudio` 加 `dryRun` 是我的活，我今天补上（见第五节）。
在补上之前，**这个脚本不许再跑**。

### 3.2 `labels.json` 里的音频路径是悬空的

9 条 magicdata 的 `audio` 字段指向 `../../magicdata/...`，但包里**没有** `magicdata/`
（2.1 MB 装不下 300 MB 音频）。别人拿到包直接跑 `callaudio-evidence.py` 会 `✗ 找不到`。

`README.md` 里要写一句：「本包不含 MagicData 音频，需自己 `bash 下载数据.sh ./magicdata`」。

### 3.3 `build-labels.js` 的标签正则会误伤

`build-labels.js:119`：

```js
if (typeof v === 'string') return /fraud|诈骗|scam|1|true|yes/i.test(v) && !/normal|正常|benign|0|false|no/i.test(v);
```

两个坑：`1` 能匹配任何含数字 1 的字符串；`no` 能匹配 `none`、`notice`、`normal` 里的 `no`。
Fraud-R1 没有这个字段所以现在没炸，但换成别的数据集就会静默错标。
建议改成白名单：`['1','true','yes','fraud','诈骗']` 全等比较。

### 3.4 `callaudio-evidence.py:47-53` 的抽稀没有抗混叠

16k→8k 用 `samples[::2]` 直接隔点取，会有混叠。SIS 能忍（实测 143/126/61 字转写正常），
但这是"能跑"不是"正确"。注释里也说明白就行，不必改。

### 3.5 `run.js` 不传 `who`，但线上已经支持了

`run.js:148` 只有 `{ text: sample.text }`。而 `server.js:555` 早已支持：

```js
const who = ['stranger', 'contact', 'service'].includes(b.who) ? b.who : '';
```

（11-18 上线并实测过：同一句不传 75 分、传 stranger 90 分。）

所以他终报第 161 行「线上 `/api/report` 把 `who` 写死为 `''`」、第 203 行「线上接口暂不支持 `who`」**两句都已过期**。

**建议**：`run.js` 加 `--who stranger`，并把 `who` 写进 `meta`。这样 4.2% 那组数就是线上实测，
不用再标"队长本地脚本"。
