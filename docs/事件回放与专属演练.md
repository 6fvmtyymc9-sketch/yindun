## 一、⑤ 一次事件的完整回放

### 要解决什么

单看一张卡片，"妈妈收到一条验证码短信"只是一条提醒。
串起来才看得出这是一条完整的作案链：

```
陌生号响铃 → 接通 → 满 5 分钟复问 → 通话中收到验证码
→ 挂断后打开手机银行 → 红屏拦住 → 自动打给女儿 → 挂断后录音复盘
```

上面这 8 件事可能横跨 20 分钟，中间还夹着一条无关短信。
**按时间戳猜归组会猜错**，所以给每一通电话一个 id。

### 怎么实现的

| 环节 | 做法 | 文件 |
|---|---|---|
| 生成 id | 陌生号**响铃那一刻**生成 `c` + 36 进制时间戳 + 3 位随机 | `app/src/com/yindun/guard/CallSession.java`（新增） |
| 接通复用 | `reuseOrBegin(number)`：号码相同且未过期就复用，否则新建 | 同上 |
| 事件类型 | 上报时带 `kind`（见下表） | `Notifier.java` |
| 上报 | `/api/alert` 的 body 增加 `callId` / `kind` / `elderId` / `number` | `Notifier.pushToBackend` |
| 落库 | `yd_alert` 新增 `call_id`、`kind` 两列 + `idx_call` | `cloud/sql/migrate_20261111_event.sql` |
| 查询 | `GET /api/call/events?callId=...` 返回该组事件（按发生时间正序） | `cloud/src/server.js` |
| 展示 | 卡片底部出现「🔗 这一次的完整过程」，点开是时间轴 | `cloud/public/index.html` |

### 为什么通话结束后不清空 id

骗子最常说的是"您先挂了，去银行 App 里操作"。**最要命的一步发生在挂断之后**，
所以 `CALL_STATE_IDLE` 之后仍要能归组。这里用**有效期 30 分钟**而不是"结束即清"，
避免两小时后一条无关预警被错挂到上午那通电话上。

### `kind` 取值

| kind | 含义 | 触发点 |
|---|---|---|
| `ring` | 陌生号码打进来 | `Guard.onCallState` state=1 |
| `offhook` | 接通 | `Guard.startNewCall` |
| `ask5` | 通话满 5 分钟的复问及回答 | `Notifier.pushInCallAnswer` |
| `code` | 收到验证码短信 | `SmsReceiver` |
| `bank` | 打开银行 / 支付类 App | `Guard.onBankForeground` |
| `judge` | 组合判据升级 | `Guard.evaluate` |
| `call_child` | 自动拨给子女（**拨号真的发出去之后**才发这条） | `Notifier.callChild` |
| `review` | 挂断后录音复盘结论 | `CallAudio.js` |
| `sms` / `install` | 可疑短信 / 非应用商店 App | `SmsReceiver` / `Guard` |

### 顺带修掉的一个真 bug

`pushToBackend` 原来**没有带 `elderId`**，云端一律按 `demo` 落库 ——
多老人场景下所有人的预警会串进同一个桶。这次一并补上（取 `Pair.id(ctx)`）。

### 实测（2026-11-11）

一次真实通话（模拟器拨入 `13900002222`，投放演示录音后挂断）：

```
15:20:59.940  陌生号码响铃 → 立刻通知子女 13900002222
15:21:03.169  通话开始 who=stranger num=13900002222 会话=cmwbsidydj1r
```

响铃与接通**用的是同一个会话 id**，这正是设计目标。

线上 `yd_alert` 里同一 `callId` 的两条记录：

| id | kind | level | 标题 |
|---|---|---|---|
| 103 | `ring` | watch | 妈妈收到陌生号码来电 |
| 104 | `review` | block | 妈妈接听的陌生来电疑似诈骗（冒充熟人） |

`GET /api/call/events?callId=cmwbskzugpkh` → `count=2, level=block`。

子女端时间轴：7 步（用测试事件铺满），时间从 14:55 递增到 15:09，
断网补发的记录按**真实发生时间**排序，正文里那句"（断网补发，实际发生于 …）"
在时间轴里被抹掉（左边已经显示时间，再重复一遍是干扰）。

## 二、④ 被骗套路 → 专属演练

### 要解决什么

每周一那句"该做一次反诈演练了"对老人没有意义。
**刚被骗过的那套话术才是她记得住的**，第二天练一遍效果远好于随机剧本。

### 怎么实现的

| 环节 | 做法 | 文件 |
|---|---|---|
| 记下套路 | 复盘判为 `high`/`block` 时存 `type` + `stage` + 时间 | `DrillPending.java`（新增） |
| 次日提醒 | 单独排一个"明天 10:00"的闹钟（`REQ_TOMORROW=9526`，不覆盖每周那个） | `DrillAlarm.scheduleTomorrow` |
| 通知文案 | 「上次那通「冒充熟人」，陪您练一遍」 | `DrillReceiver.java` |
| 点进来 | Intent extra `drill_mode=case`，页面自动开局，不用她再点一次 | `DrillActivity.EXTRA_MODE` |
| 用完即清 | 开局时 `DrillPending.clear()`，避免每周重提同一件事 | `DrillActivity.onCreate` |
| 台词来源 | 云端 `mode:'case'` 从 `yd_report` 取最近一条案例，重写外壳 | `Drill.js` / `CaseBank.js` |

### 三个刻意的取舍

1. **只记类型，不记原话。** 原话里有对方姓名、卡号、金额。演练本来就要重编台词，
   存"冒充公检法"这一层就够，多存一个字都是多余的隐私风险。
2. **3 天过期。** 两周后再弹"上次那通电话"，老人已经想不起来是哪通了。
   超过 3 天退回通用提醒——宁可少一点针对性，也不能让她觉得这 App 在说胡话。
3. **文案区分来源。** 录音复盘自动记下的案例，老人**没有做过"上传"这个动作**，
   原来统一写成"你上传的那条「…」"是在编事实。现在按 `yd_report.reporter` 区分：
   `callaudio` → 「上次那通电话的套路「冒充熟人」」，其余 → 「你上传的那条「…」」。

### 实测

复盘跑通后的日志：

```
15:23:19.945  录音复盘判为 block，30 分钟内打开银行将直接盖屏
15:23:19.946  DrillPending: 记下待演练套路：冒充熟人 S4
15:23:19.948  DrillAlarm: 复盘后次日提醒已排：Thu Nov 12 10:00:00 GMT+08:00 2026
```

把模拟器时间推到次日 10:01，通知栏出现：

```
android.title = 上次那通「冒充熟人」，陪您再练一遍
```

点进去（等价于 `am start --es drill_mode case`）直接开局，
来源显示「上次那通电话的套路「冒充熟人」」，第一句台词：

> 妈，是我啊，您听不出来啦？我手机摔坏了，这是借同事的电话给您打的。

开局后 `yindun_drill_pending.xml` 变成空 `<map />` —— 标记已清，不会重复骚扰。

## 三、怎么复验

```bash
# 1. 数据库加列（可重复执行）
ssh root@<ECS>
cd /opt/yindun
PASS=$(grep '^RDS_PASS=' .env | cut -d= -f2-)
mysql -h127.0.0.1 -uyindun -p"$PASS" yindun < sql/migrate_20261111_event.sql

# 2. 造一场事件，看归组
curl -X POST http://<ECS>:8080/api/alert -H 'Content-Type: application/json' \
  -d '{"elderId":"demo","callId":"ctest001","kind":"ring","level":"watch","title":"妈妈收到陌生号码来电","body":"正在响铃"}'
curl "http://<ECS>:8080/api/call/events?elderId=demo&callId=ctest001"

# 3. 演练：按案例开局
curl -X POST http://<ECS>:8080/api/drill/start -H 'Content-Type: application/json' \
  -d '{"elderId":"demo","mode":"case"}'
#   返回里的 from 能看出案例是"上次那通电话"还是"你上传的"
```

模拟器上验证 ④ 的前置条件（复盘要能读到录音）：

```bash
adb shell appops set com.yindun.guard MANAGE_EXTERNAL_STORAGE allow
# 开关在首页「通话录音复盘」，也可以直接改 shared_prefs 里的 rec_on
adb push 某段录音.mp3 /data/local/tmp/yt.mp3
adb shell cp /data/local/tmp/yt.mp3 /storage/emulated/0/Sounds/CallRecord/yt.mp3
adb shell touch /storage/emulated/0/Sounds/CallRecord/yt.mp3   # 时间必须是"这通电话期间"
```

`CallRecord` 只认**修改时间晚于接通前 10 秒**的音频，直接 `adb push` 会保留原时间戳，
必须 `touch` 一下，否则会看到"等了 60 秒没找到录音"。

## 四、已知边界

- **时间轴第 1 格可能缺失**：极短通话如果系统没给号码，`CallSession.begin(null)` 仍会生成 id，
  但响铃那一步已经在 `Guard` 里被 `NumberInfo.STRANGER` 过滤，不会上报。
- **子女端页面的 `elderId` 目前写死 `demo`**（`/api/stream?elderId=demo`），
  多老人场景要跟着改，见交付文档已知缺陷「子女端多老人」。
- **不再按 `id` 排序**：`listEvent` 用 `created_at` 升序，因为断网补发的入库顺序不等于发生顺序。
  代价是手机时钟被改过时顺序会乱——`/api/alert` 已有"7 天内、未来 5 分钟内"的时间戳边界检查兜底。
- 演练页的 `mode=case` 依赖云端 `yd_report` 里**有案例**；没有时会自动退回热点剧本，
  不会报错，但文案会变成"本周热点"。
