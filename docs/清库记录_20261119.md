## 三、清库后 health 会显示 0 —— 这不是丢数据

清完当场查的：

```json
"stats":    {"events":0, "alerts":0,  "reports":0}     ← demo 口径，必然全 0
"statsAll": {"events":0, "alerts":61, "reports":0}     ← 全库口径，这才对
```

**`stats` 为什么会变 0**：`server.js` 里写的是 `db.stats('demo')`，即
`SELECT COUNT(*) ... WHERE elder_id='demo'`。demo 都没了，当然是 0。

**所以迁移验收不能只看 `stats`**：迁前 0、迁后 0 也叫"相等"，真出事看不出来。
现在 health 同时返回 `statsAll`（不带 `WHERE` 的全库计数），**对账用 `statsAll`**。

## 七、这条教训写进答辩

> **评估流量和生产数据必须隔离。**
>
> 11-18 之前，评估脚本直接打生产接口、直接写生产库，结果是：
> 1,520 条 demo 告警 + 1,225 条 demo 上报把真实数据淹了；
> 迁移基线每跑一轮评估就变一次，甲方永远采不到稳定数字；
> 而`stats` 里看着"有 1,500 多条告警"，其实**真实用户一条都没有**。
>
> 解法不是"事后清库"，是让评估**默认不写库**（`dryRun`）。
> 清库只是补救，`dryRun` 才是根治。
