## 三、两处原文与代码对不上（照抄会失败）

### 3.1 `RDS_DB=yindun` 这个键代码完全不读

原文 C5 的 `.env` 片段里有：

```
RDS_DB=yindun
```

实测：`grep -rn "RDS_CA" cloud/src/ cloud/*.js` **零结果**。`server.js` 的 `createPool` 只读
`RDS_HOST` / `RDS_PORT` / `RDS_USER` / `RDS_PASS` / `RDS_DB`，**没有任何 SSL 配置**。

这个键来自 `.env.example`（历史遗留占位）。填不填都不影响连接。
**但不能把它当"我们配了 SSL 证书"写进材料**——那是假的。

### 3.2 部署机路径不是 `cloud/sql/`、`cloud/src/`

原文 C4 写 `cloud/sql/schema.sql`，C5 隐含 `cloud/src`。部署机上实测：

```
/opt/yindun/sql/schema.sql          ← 不是 /opt/yindun/cloud/sql/
/opt/yindun/src/server.js           ← 不是 /opt/yindun/cloud/src/
```

`deploy/install.sh` 把仓库 `cloud/` 下的内容同步到 `/opt/yindun/` 根，所以多了一层路径差。
**在 ECS 上照抄仓库路径会 `No such file or directory`。**

## 四、本次已修的（都有实测证据）

### 4.1 `TZ=Asia/Shanghai`（C5-2）

**为什么这条真重要**：RDS 服务端时区是 `SYSTEM` = **UTC**（实测 `select now()` 返回 12:06，
本机 20:06，差 8 小时）。`server.js` 的 `createPool` 没有设 `timezone` 选项，mysql2 按**进程本地时区**
把 `new Date()` 转成字符串写库。

目前没出错，是因为 ECS 系统时区本来就是 CST，且所有 INSERT 都显式传 `created_at`（`Db.js` 里
`created_at: new Date()`），没有任何 SQL 用 `CURDATE()` / `NOW()`。
**但这是运气不是设计**——换台系统时区是 UTC 的机器，写进去的时间就整体偏 8 小时，而且很难发现。

改了三处：

| 位置 | 改动 | 验证 |
|---|---|---|
| 线上 `/opt/yindun/.env` | 追加 `TZ=Asia/Shanghai`（单行） | `grep -c` = 1 |
| 线上 `/etc/systemd/system/yindun.service` | 加 `Environment=TZ=Asia/Shanghai` | `/proc/<pid>/environ` 里能看到 `TZ=Asia/Shanghai` |
| 仓库 `deploy/install.sh` | 模板同步加 `Environment=TZ=Asia/Shanghai`，并写清理由 | 下次部署不会丢 |

重启后 `ok:true`，`statsAll` 仍是 `{0, 1581, 1225}`，一条没动。

### 4.2 顺手挖出一个会让 C5-4 失败的陷阱

原文 C5-4 要求 `systemctl disable --now mysql redis-server`。但线上单元原来写着：

```ini
After=network.target mysql.service redis-server.service
Wants=mysql.service redis-server.service
```

**`Wants=` 会在每次 `systemctl restart yindun` 时把这两个服务拉起来，哪怕已经 disable 过。**
也就是说：按原文停掉 MySQL 之后，下次重启银盾，MySQL 又活了、又吃四百兆内存，
而它的数据已经不该再被写——而且不报错，看不出来。

仓库里的 `deploy/install.sh` 早在 11-18 就改成"本机真有这俩服务才写依赖"，但**线上单元是旧版，从没按新脚本重生成过**。

已做：线上单元去掉 `After/Wants` 里的 mysql/redis（只留 `network.target`），`daemon-reload` + 重启，
服务 active。这样后面停 MySQL / Redis 才不会反弹。

> ⚠️ 线上单元其余部分仍是旧版（以 `root` 跑、没有 `User=yindun`、没有 `MemoryMax` / `ProtectSystem` 等加固），
> 与仓库 `install.sh` 生成的版本不一致。这一项留到 C7「用 Skills 重走部署」时一并重生成，不在今晚动运行用户。

## 五、最关键的问题：原文的阶段顺序在当前条件下走不通

原文第六节「顺序与分工」是硬依赖链：

```

4  C6~C8 OCR + CodeArts 部署        （甲，1~2 天，**依赖 B 完成**）
```

原文第 5 行还写死了一条：

> **前一个阶段的验收没过，不要开始依赖它的下一个阶段。**

而实际情况是：

- **阶段 A 的验收过不了。** 2026-11-19 复核确认 AntiFraud-SFT **恒答「是」**：
  静音 0.6225、白噪声 0.5312、440Hz 正弦 0.8520、14 段正常通话 **14/14 全判诈骗**，
  AUC 仅 0.763，最优阈值下仍有 93% 误报。阈值 / prompt / 校准都救不了，是权重问题。
  详见 `docs/SFT模型可用性复核_20261119.md`。
- **所以 A6（把 `SFT_URL` 接到隧道）绝对不能做**，手上线就是拿一个恒真票去抬告警。
  线上 `sft.enabled` 保持 `false`。
- **A 过不了 → B 不能开始 → 按原文 C6~C8 也不能开始。**

如果严格照原文，现在**除了 C2~C5，什么都做不了**。这显然不是老师想要的结果——
老师写"不要依赖未验收的阶段"是为了防止在错误基础上堆功能，不是为了让整条链停摆。

## 七、这次核对纠正了什么（记账）

1. **之前以为 `RDS_CA` 是显示错位，其实是 `.env.example` 里真实存在的死键** —— 代码不读，别当有效配置。
