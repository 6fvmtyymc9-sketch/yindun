## 1. 微信里要验证码，银盾不盖屏 【P0 · 阻断缺口】

**位置**：`app/src/com/yindun/guard/NotiGuard.java` —— 全文搜不到 `onCodeInCall` /
`callStartAt` / `isCode`，即这条链路在微信侧根本不存在。

**短信侧的正确做法**（`SmsReceiver.java` 第 5 步）：

```java
Guard g = Guard.get(ctx);
if (isCode && g.callStartAt > 0 && NumberInfo.STRANGER.equals(g.st.callWho)) {
    Log.w(TAG, "★ 通话中收到验证码 —— 阻断级");
    g.onCodeInCall();                                    // 置 st.codeInCall = true
    EventBus.pushAlert("block", "通话中收到验证码", "S4", 100);
}
```

`Guard.onCodeInCall()`（`Guard.java:367`）本身很短：置标志位 → `evaluate("code")` 进判定链。

**现象**：老人正在和陌生号码通话，骗子在微信里说「阿姨，您把刚收到的那 6 位数字念一下」。
银盾只弹一条 9 秒橙色浮条，**不盖屏**，验证码照念照给。

**为什么这是最严重的一条**：现实里骗子更常用微信而不是短信要验证码（微信能发语音、能发假截图）。
短信那条链是完整闭环，微信这条是空的。

**改法**：在 `NotiGuard.judgeWechat` 判出结果后，加一段和短信等价的判断：

1. 这条微信内容像不像在「索要验证码 / 索要密码 / 索要身份证号」——不能只看有没有「验证码」三个字，
   要区分「我把验证码发你」和「你把验证码告诉我」两种方向。建议单独写一个小方法
   `looksLikeCodeRequest(body)`，词表里加「发给我 / 告诉我 / 念一下 / 报给我 / 几个数字」这类动词搭配。
2. `Guard.get(app).callStartAt > 0` 且当前通话对方是陌生人 → 调 `Guard.onCodeInCall()`，
   同时 `EventBus.pushAlert("block", ...)` 让网页端盖屏。
3. 这条要走 block 级，**不能**沿用 `MIN_RANK` 那道 warn 门槛（见 `NotiGuard.java:160`）。

**风险**：`Guard` 是老人端的单例，`NotiGuard` 拿到的是 application context，直接 `Guard.get(app)` 可行，
但要在后台线程里调用（`judgeWechat` 已经在新线程里，OK）。**改完必须确认没有引入主线程阻塞**——
`NotiGuard` 之前就因为同步判定把主线程塞满过 ANR（见该文件 116~120 行注释）。

**怎么验**：模拟器上装不了微信 → **只能真机**。真机上要造：陌生号码打进来并接通 → 微信收到
「把验证码告诉我」→ 看是否盖屏。没有真机就只能静态核对代码路径，不能声称验证过。

## 2. 106 / 95 号段的诈骗短信，永远进不了 AI 复核 【P0 · 结构性漏报】

**位置**：`SmsReceiver.java:214`

```java
private boolean shouldReview(Context ctx, String who, Judge.Result r, String text) {
    if (NumberInfo.SERVICE.equals(who)) return false;    // ← 这一行
    ...
}
```

**根因**：`NumberInfo.classify`（`NumberInfo.java:56`）判断服务号只看号码长相：

```java
if (num.length() <= 6 || num.startsWith("95") || num.startsWith("106")) {
    return SERVICE;
}
```

于是「106 开头 = 服务号 = 不用复核」。可现实里大量诈骗短信正是从 106 号段发出来的
（违规短信通道、伪基站）。一条 106 号诈骗短信如果不命中词表（换个说法），
本地给 0~15 分、模型永远看不到——**两道防线同时失效，且不会再有任何补救**。

**为什么比留出集那 60% 更值得先说**：留出集漏报是「规则不够聪明」，这条是「结构上就没打算看」。

**改法**：把「服务号一律跳过」改成「服务号 + 没有任何可疑信号才跳过」。建议：

```java
if (NumberInfo.SERVICE.equals(who)) {
    // 服务号默认不送，除非正文自己露出了马脚
    boolean suspicious = containsUrl(text)          // 带链接
            || hasAny(text, "转账", "汇款", "安全账户", "验证码", "冻结", "解冻", "征信");
    if (!suspicious) return false;
}
```

理由：真的银行/快递短信不带「转账到这张卡」，而诈骗短信即使伪装成 106 也一定会要钱或要码。

**改完要重跑**：`node cloud/test/ai-review.js holdout.json`，看复核条数涨了多少、误报涨没涨。
预估复核量会上升，**注意每日 120 条那道闸**（`AI_REVIEW_PER_DAY`）会不会被撞到——
如果撞到，就等于高峰期把复核关掉了，这比不放开更糟。

## 3. 短信判 block 会自动拨号，把浮条整个盖掉 【P0 · 阻断自伤】

**位置**：`Notifier.java:163`

```java
// 阻断级：直接拨号（这才是真正能叫醒人的那一招）
if ("block".equals(level)) {
    callChild(ctx);
}
```

**这是 2026-11-15 22:34 实测抓到的**：

```
22:34:32.706  短信 ... 分数=240 阶段=S4 级别=block
22:34:32.859  已自动拨给子女 18183254040       ← 0.15 秒后就开始拨
22:34:34.232  轻提醒已弹出（block）：疑似诈骗短信   ← 浮条这时才弹（延迟 1.2 秒）
22:34:35.954  通话开始 who=contact
```

老人端屏幕最后停在**通话界面（Nver 02:15）**，那条「疑似诈骗短信」一个像素都没看见。

**为什么这条拨号是错的**（不是"少做一步"，是"做了反效果"）：

- 短信里的骗子不在通话里，拨给女儿也打断不了什么；
- 真正该立刻打断的是「通话中 + 打开银行」，那条链已经单独有了；
- 拨号把唯一的视觉提醒盖住，老人只知道手机自己打了个电话，不知道刚才那条短信是诈骗。

**改法**：拨号只对「正在发生的资金动作」生效，不对「一条到站的短信」生效。
在 `alertChild` 里按 kind 分流：

```java
if ("block".equals(level)
        && (K_BANK.equals(kind) || K_CODE.equals(kind))) {
    callChild(ctx);
}
```

`kind` 已经是这个方法的第三个参数（`Notifier.java:125`），调用方 `SmsReceiver.java:142`
传的是 `K_CODE` / `K_SMS`，改起来只是加一个判断。

**注意**：`K_CODE`（通话中收到验证码）必须保留拨号——那个场景骗子正在电话里等着念数字，
真的只剩几十秒。判断依据是它同时满足「在通话中 + 陌生号」。

**怎么验**：模拟器 `emu sms send` 重发第 3 条短信，确认：浮条看得见 + 不拨号 + 子女端仍收到 block。

## 4. 含「验证码」的 block 短信，老人端被降级成 warn 【P1】

**位置**：`SmsReceiver.java:165`

```java
if (isCode) {
    alert(ctx, "warn", "收到验证码短信", "请勿向任何人透露验证码");   // 固定 warn
} else if (!"none".equals(r.level) && !"watch".equals(r.level)) {
    alert(ctx, r.level, "疑似诈骗短信", "请勿点击短信中的链接");
}
```

**问题**：`isCode` 的分支优先于级别。一条 240 分的 block 诈骗短信，只要正文里有「验证码」
三个字，老人端就只弹黄色 warn 浮条。而同一条短信，子女端收到的是 `r.level` = block
（`SmsReceiver.java:142` 传的是 `r.level`，不是硬编码）——**两端说的不是同一件事**。

配合问题 3 更荒诞：老人看到黄条「别告诉任何人验证码」，同时手机在自己拨号出去。

**改法**：取两者的较高级别。

```java
String shown = isCode ? higher(r.level, "warn") : r.level;
if (!"none".equals(shown) && !"watch".equals(shown)) {
    alert(ctx, shown,
          isCode ? "收到验证码短信" : "疑似诈骗短信",
          isCode ? "请勿向任何人透露验证码" : "请勿点击短信中的链接");
}
```

这样验证码短信至少是 warn（原来的行为不变），规则判到 block 时不再被压回去。

**怎么验**：发一条「您的验证码是 882911，正在向陌生账户转账 5 万元，请勿泄露」——
预期：老人端橙色/红色浮条，子女端 block。

## 5. 家庭群聊到「验证码」会误报 【P1 · 误报】

**位置**：`NotiGuard.java:154`

```java
Judge.Result r = Judge.get(app).judgeSms(body, NumberInfo.STRANGER, false);
```

**问题**：微信群通知的 title 是群名、text 常是「张三: 内容」。这一步把**任何微信消息**
都按「陌生人发的短信」判，起手 +15 分（`Judge.java` 第 3 步）。家里人聊一句
「我收到个验证码，不知道是谁的」，加上「验证码」本身的权重，够到 45 线 → 弹浮条 + 推子女。

老人的家庭群是高频场景，这个误报几乎一定会撞上。撞一次，老人就会觉得银盾乱弹。

**改法**（两条，建议都做）：

1. **群消息降权或不判**。判断依据：微信单聊通知的 title 是联系人名，群聊的 title 是群名，
   text 里带「:」或「：」。检测到「名字+冒号」前缀时，优先按群消息处理——群消息里出现
   「验证码」多半是聊天，不是诈骗。最保守的做法：群消息只在命中 S4（要钱/要码）词时才报。
2. **去掉微信的 +15 陌生人加成**。微信本来就没有号码可查，一律 +15 等于给所有微信消息
   白送 15 分。改成 0，让词表自己说话。

**改完要重跑**：微信没有留出集，只能靠真机人工试 20~30 条真实聊天记录，看误报有多少。

## 6. AI 复核报出来的分数是硬凑的 【P1 · 数据不真实】

**位置**：`SmsReceiver.java:303`

```java
EventBus.pushAlert("warn", "AI 复审：" + reason, stage, score + 20);
```

**问题**：模型只给「可疑/不」和一个理由，不给分数。这个 `score + 20` 是凭空的，
会原样显示在子女端时间线上（`EventBus.pushAlert` 直接带过去）。

这跟我们自己定的「不写没发生的事」是冲突的——老人和子女看到「得分 65」，会以为模型算出了 65。

**改法**：二选一，我倾向第二个。

- 方案 A：不传分数（传 `-1`），界面上不显示数字，只显示「AI 复核判定可疑」。
- 方案 B：**让模型真的给一个概率**。云端 `Pangu.riskSms()` 已经在返回 `{p, type, stage, why}`
  （`cloud/src/Pangu.js`，2026-11-09 加的那套），把 `p` 接过来用，界面标「模型概率 78%」。
  这个更实在，但要动云端 + 端侧两处，且云端得部署。

**注意**：如果改方案 B，界面上不要同时显示「规则分 45」和「概率 78%」——码道第 8 条提过这个，
两个量纲并排会让老人和子女都困惑。要么只显示一个，要么明确标成两回事。

## 7. 浮条只挂 9 秒，老人端又没有通知栏兜底 【P2 · 体验】

**位置**：`TipBar.java:48` + `Notifier.java:157`

```java
private static final long AUTO_HIDE_MS = 9000;                       // TipBar:48
if (nm != null && !isElderPhone(ctx)) nm.notify(NOTIFY_ALERT, n);    // Notifier:157
```

**现象**：老人端是**故意不弹通知栏的**（`isElderPhone` 判真就跳过 notify，理由是这条通知
本来是写「妈妈可能正在被骗」给子女看的，放老人机上很怪）。于是 warn 级提醒唯一的载体是
那条 9 秒浮条——她低头干活的这 9 秒，就等于没提醒过，而且事后无处可查。

（2026-11-15 实测：手机放在桌面、人在别处，9 秒后屏幕干干净净，只有短信图标上一个未读圆点。）

**改法**（两条可以分开做）：

- **按级别分时长**：warn 9 秒 → 建议 15 秒；block/high 不自动消失，等老人点掉或 60 秒兜底。
  `TipBar` 里 `AUTO_HIDE_MS` 现在是常量，改成按 level 传入。
- **给老人端补一条通知**：不是复刻子女那条文案，而是单独写「银盾：刚才收到一条可疑短信，
  点这里看」。这样错过后还能顺着通知找回来。注意老人端通知要和盖屏共存，不要又盖掉红屏。

**怎么验**：发 warn 短信后立刻锁屏再解锁，看浮条还在不在（当前行为是 9 秒后就没了）。

## 8. 短信浮条没有频率上限 【P2 · 骚扰】

**位置**：`SmsReceiver.java:257` 的 `alert(...)`

**问题**：`aiQuota`（`SmsReceiver.java` 的 `aiQuota`，120 条/天）只限了 AI 复核次数，
**浮条一条都没限**。老人被短信轰炸 20 条，就弹 20 次浮条，越弹越烦，最后她会去关悬浮窗权限——
关掉之后红屏拦截也跟着废了（都依赖 `Shield.canOverlay`）。

**改法**：加一个「同类浮条 60 秒内只弹一次」的节流，计数放内存即可（进程重启就清，无所谓）。
被节流掉的不丢：仍然计入 `EventBus.push` 和子女端推送，只是不再打扰老人。

**怎么验**：连续 `emu sms send` 5 条同样的诈骗短信，预期浮条只弹 1 次、子女端收到 5 条。

## 9. 判出微信诈骗后，微信那条通知还挂在通知栏 【P2】

**位置**：`NotiGuard.java:90` —— `cancelNotification(sbn.getKey())` 只在 `Shield.showing()` 时执行。

**问题**：微信浮条弹了「疑似诈骗消息」，但通知栏里那条诈骗消息还在，老人一点就进微信、
一进就看见骗子的话。等于提醒和入口同时存在。

**改法**：判出 warn 及以上时，顺手 `cancelNotification(sbn.getKey())`。

**注意**：这么做会「替老人删掉一条消息通知」，属于介入比较深的动作。我的意见是只清 block 级，
warn 级不动（warn 可能只是误报，把通知删了她反而收不到家人正常消息）。
**这条需要你拍板**，因为它涉及"银盾能不能替用户清通知"的产品边界。

## 11. 指纹带 postTime，微信刷新会让同一条重复弹 【P2】

**位置**：`NotiGuard.java:143`

```java
final String fp = sbn.getKey() + "#" + body.hashCode() + "#" + sbn.getPostTime();
```

**问题**：`postTime` 是加进去解决「演示重跑第二遍弹不出来」的（注释写得很清楚）。
代价是微信对同一条通知任何一次更新（「对方正在输入」、多设备同步、撤回重发）都会改 postTime，
指纹就变了，同一条消息会被判第二次、弹第二次浮条。而 `DEDUP_MS` 10 分钟的初衷正是"只弹一次"。

**改法**：指纹去掉 postTime，改用 `key + 正文 + 5 分钟时间桶`：

```java
long bucket = System.currentTimeMillis() / (5 * 60 * 1000L);
final String fp = sbn.getKey() + "#" + body.hashCode() + "#" + bucket;
```

这样同一条消息在 5 分钟内只判一次，跨时间桶重新出现才算新的——演示重跑（隔几分钟）照样能弹。

**怎么验**：真机上让同一个微信号连发两条一模一样的话，确认只弹一次。

> **2026-11-17 推翻上面的改法**
>
> 真机反馈：同样一段话（「我临时遇到急事，不方便打电话，先转3000到…」）
> 第一次发会弹警告，第二次再发就**什么都不弹**。5 分钟窗口里，同样的内容
> 指纹完全相同，被当成"刚判过"直接跳过。
>
> 这不只是演示问题：骗子重复催同一句话是最常见的施压手法，第二次不提醒等于漏防。
> 上面那种改法（怕重复弹而加宽窗口）方向错了——**漏弹的代价远大于多弹一次**。
>
> 最终按 `key + 正文 + 通知自身的 postTime` 判新旧：
>
> ```java
> long stamp = sbn.getPostTime();
> if (stamp <= 0) stamp = System.currentTimeMillis() / DEDUP_BUCKET_MS;  // 兜底
> final String fp = sbn.getKey() + "#" + body.hashCode() + "#" + stamp;
> ```
>
> - 系统把**同一个通知**重复回调给我们（列表重建、设备恢复）→ postTime 不变 → 跳过
> - 微信真的**又收到一条**，哪怕一个字都没改 → 通知重新 post，postTime 前进 → 重新判
>
> 判"这是不是又一条新消息"，权威答案是系统记的通知时间，不该由我们的时钟猜。
>
> **模拟器实测**（假微信壳 `com.tencent.mm` 连发三条同样的话）：三条全部弹了浮条，
> 日志三次都是 `分数=45 级别=warn → 已向老人弹浮条、向子女推送`。
> 回归同时确认：诈骗短信仍 195 分 block、陌生来电仍弹熟人询问卡、接听开银行仍红屏。

## 12. 反例扣分无下限 【P2 · 数据异常】

**位置**：`Judge.java:327`

```java
for (Word w : negatives) {
    if (text.contains(w.text.toLowerCase())) {
        score += w.weight;      // weight 是负数，累加无下限
```

**实测证据**：正常快递短信被判 **-45 分**（命中「快递已到」-15、「驿站」-15、「取件码」-15）。

**这条是码道第 1 条指出的，我一直没改**，因为它会改变误报率，必须重跑留出集 35 条。
现在有了实测数字，可以更准确地说它的危害边界：

- 负分**不影响判定**（`stage=S0`、`level=none` 都正确），所以不是功能 bug；
- 但它会显示在界面上（子女端时间线、判据看板），老人/子女看到「-45 分」会困惑；
- 而且是「可被利用」的：骗子在诈骗短信里塞「取件码」「驿站」就能白拿 -30 分。

**改法**：给反例扣分设一个下限，比如最多扣到 `score` 不少于 0：

```java
score += w.weight;
if (score < 0) score = 0;
```

**注意**：这一改会**抬高**所有带反例词的分数，可能让那 3 条误报（书法班、存单到期、报纸续订）
更严重。**改之前先拿留出集 35 条跑一遍现在的分数分布**，改完再跑一遍对比，两个数字一起给。
