# 开机自启与冷启动漏判

> 2026-11-15 晚。对应交接文档「后续开发」里的 ① 和 ②。
> 两个问题的共同点：**都不影响演示，都会让真机上的产品悄悄失效。**

---

## 一、为什么这两件事比"加功能"更要紧

演示的时候，银盾是刚刚装好、刚刚打开、正在前台跑着的。这种状态下一切都对。

真机上的老人不是这么用的：

- 手机没电关机，第二天充上电开机 —— **守护不会自己回来**
- 系统更新重启 —— 同上
- 国产 ROM 半夜清后台，早上她打开手机 —— 进程是新的，**前台应用监听从零开始**

第一种情况下，桌面上那个图标还在，老人以为银盾在守着。真到被骗那一刻，手机上什么都不会发生。
**这比压根没装更坏** —— 她会因为"我装了银盾"而放松。

## 二、开机自启

### 2.1 两端都是空白

改动前的事实（不是猜的，是 `grep` 出来的）：

| | 权限 `RECEIVE_BOOT_COMPLETED` | 接收器 |
|---|---|---|
| 老人端 `com.yindun.guard` | **没有声明** | 没有 |
| 子女端 `com.yindun.child` | 声明了 | **没有对应类**（等于空写） |

全仓 `grep BOOT_COMPLETED --include=*.java` 零命中。

**注意区分**：老人端原来有一个 `MainActivity.openAutostart()`，那是**引导用户去系统设置里开"自启动"**（按品牌试 9 个候选组件）。
那是"求用户帮忙"，不是"自己站起来"。两件事都要有，缺一个都不成：
- 只有引导、没有接收器 → 用户开了自启，系统给广播，我们没接，照样不起
- 只有接收器、没有引导 → 用户没在系统设置里放行，ROM 直接把广播拦掉

### 2.2 改法

新增两个类，都叫 `BootReceiver`：

- `app/src/com/yindun/guard/BootReceiver.java` → 拉起 `GuardService`
- `app/childapp/src/com/yindun/child/BootReceiver.java` → 拉起 `WatchService`

manifest 各加权限 + 接收器，`exported="true"`（系统广播来自别的进程，写 false 永远收不到），
除标准 `BOOT_COMPLETED` 外**额外接了 `QUICKBOOT_POWERON`**（小米/vivo/OPPO 自家那套快速开机广播，
标准广播在它们身上有时不发）。

### 2.3 一个刻意的判断：不是"装了就开始自启"

老人端 `MainActivity.startGuard()` 是无条件调用的（`onCreate` 第 124 行），
所以光看"有没有启动过服务"分不出两种人：真的要用的人和只是点开看了一眼的人。

对后者来说，每次开机常驻一条"银盾守护中"，跟流氓软件没区别。
所以加了一个标记 `Pair.enabled`（`shared_prefs` 里的 `guard_enabled`），
`startGuard()` 时写，`BootReceiver` 读 —— **只有她真的开通过守护，才配得上自启**。

子女端用的是已有的 `Conf.paired()`（配对凭证非空），道理一样：没配对时连上去只会 401。

### 2.4 实测踩到的坑（子女端第一次是崩的）

第一次重启后，老人端起来了，子女端**没有**。日志里是：

```
Start proc: com.yindun.child for broadcast {com.yindun.child/com.yindun.child.BootReceiver}
E AndroidRuntime: Unable to start receiver com.yindun.child.BootReceiver:
    java.lang.NullPointerException: Attempt to invoke interface method
    'java.lang.String android.content.SharedPreferences.getString(String, String)'
    on a null object reference
    at com.yindun.child.Conf.elders(Conf.java:92)
```

根因：`Conf` 是单例，`SharedPreferences` 是**懒加载**的，平时由 `MainActivity` / `WatchService`
的 `init()` 初始化。而开机广播**先于它们**执行，这时候 `sp` 还是 null，直接问 `paired()` 就是空指针。

修法是一行：`onReceive` 里先 `Conf.get().init(ctx)`。`init` 本身幂等（`if (sp == null)`），重复调无害。

> 这个坑值得记一笔：**单例 + 懒加载 + 广播入口** 这三样凑在一起必然踩。
> 凡是"进程可能从广播冷启动"的入口，都要先确认依赖的单例已经初始化。

### 2.5 实测结果

模拟器 `adb reboot` 整机重启，**全程不打开任何 App**，只等广播：

```
20:21:34.450  I YinDunChild: 开机自启：预警监听已拉起
20:21:35.785  I YinDun     : 开机自启：守护服务已拉起
20:21:35.786  I YinDun     : 守护服务启动
20:21:35.834  I YinDun     : 通话监听已启动
20:21:35.835  I YinDun     : 前台应用监听已启动
20:21:35.835  I YinDun     : 子女指令通道已启动
```

交叉验证（防止"只有日志没真起来"）：

| 检查项 | 结果 |
|---|---|
| `ps -A \| grep yindun` | `com.yindun.child`、`com.yindun.guard` 两个进程都在 |
| `dumpsys activity services com.yindun.guard` | 1 条 ServiceRecord |
| `dumpsys activity services com.yindun.child` | 1 条 ServiceRecord |

**一次额外发现**：`BOOT_COMPLETED` 从 post 到真正投递到我们，在模拟器上延迟了**约 73 秒**
（20:14:40 post，20:15:53 才投递）。原因是广播队列被前面的应用阻塞（日志里有 10 秒超时记录）。
我第一次查早了以为失败，实际是还在排队 —— 以后验开机自启，等 90 秒再下结论。

## 三、冷启动漏判

### 3.1 问题出在哪

`AppWatcher.foreground()` 原来只问系统："最近 **10 秒**有哪些界面来到过前台？"

这条问法依赖一个前提：**前台是「变化」出来的**。

可老人一直停在银行界面上不动的时候，10 秒内一个事件都没有 —— 那个事件是 5 分钟前发生的。
此时银盾进程被 ROM 杀掉又被拉起来（或者手机刚重启完），查出来就是空，
这一轮直接 `return`，**"她在银行"这件事整个漏掉**。

真机上这不是小概率：国产 ROM 一天杀好几次后台，开机自启的瞬间也正好是冷启动。

### 3.2 改法

10 秒查不到，再往前看 60 秒兜一次：

```java
private String foreground() {
    String pkg = latestForeground(10000);
    if (pkg != null && pkg.length() > 0) return pkg;
    return latestForeground(60000);   // 冷启动兜底
}
```

**为什么放宽是安全的**（这三条是想清楚才改的，不是试出来的）：

1. 她若已经切到别的 App，那个 App 一定有更新的前台事件，取到的还是它 —— 不会误判成银行；
2. 她若锁屏不动，取到的是最后一个前台 App，那正是"屏幕最后停在哪儿"；
3. **多查一次不会导致误盖屏**：真正决定盖屏的是「通话中」或「风险窗口」，
   这两个条件在 `Guard.onBankForeground` 内部判（第 319 行），跟窗口宽度无关。
   没有风险时，放宽窗口只是多打一行日志。

### 3.3 怎么测的（这个场景不太好造）

要在"前台是银行"的同时让服务冷启动。`am start-foreground-service` 被 manifest 的
`exported="false"` 挡住了（这是对的，服务不该对外暴露），最后用 `adb root`（root uid 免 exported 检查）绕过去：

```
T+0s     打开假银行 com.icbc.mobile（成为前台）
T+20s    am force-stop com.yindun.guard（模拟 ROM 清后台）
T+43s    adb root; am start-foreground-service -n com.yindun.guard/.GuardService
T+49s    日志：前台出现银行类 App: 中国工商银行 (com.icbc.mobile)
```

银行事件发生在 **43 秒前**，早就超出 10 秒窗口。旧代码在这个时刻必然返回空，
新代码靠 60 秒兜底扫到了。

## 四、顺带改的两处（同一批）

### 4.1 模型返回的 stage 加白名单（码道第 7 条）

`SmsReceiver.aiReview` 里 `o.optString("stage", "S0")` 原样透传，而这个值会
**直接显示在子女端时间线上**。模型输出 "S1阶段"、"stage1"、中文"初期" 都会原样出现在界面上。

加了 `saneStage()`：认不出就按本地分数反推（≥70→S2，≥40→S1，否则 S0），并打一条 `Log.w`。
**只影响显示，不影响判级** —— 级别在调用处写死是 `warn`。

### 4.2 银行包名白名单扩表（③）—— 扩表时发现一个更严重的 bug

`Judge.BANK_WORDS` 从 30 条补到 44 条，新增的都在注释里写明理由：

- 英文包名关键词：`chinamworld`（中行）、`bankcomm`（交行）、`ecitic`、`cgb`（广发）、`hxb`（华夏）、`xwbank`、`aibank`
- 中文说法：`邮储`、`村镇银行`、`农村商业`、`农村信用`、`农合`、`信用合作联社`、`电子银行`、`银联`

**故意没加的**：微信(`com.tencent.mm`)、抖音、美团。它们确实能转账，但老人通话中刷微信
是极常见的事，加进来等于把"聊着天看手机"全判成"正在转账"，会被她当成乱弹，直接卸载。
**这是取舍，不是遗漏** —— 答辩要能把这句话说清。

#### 扩表之后才发现：中文词一个都没生效

`isBank(pkg, label)` 的签名一直有两个参数，但**全仓唯一的调用点传的是 `null`**：

```java
if (Judge.isBank(pkg, null)) {                          // 改动前
    g.onBankForeground(pkg, InstallReceiver.label(ctx, pkg));   // 应用名取了，但只用于显示
}
```

后果：词表里那 18 个中文词（`银行`/`支付`/`信用卡`/`农商`/`农信`/`邮储`/`村镇银行`…）
在唯一一条判定路径上**全部失效**，只有包名里的英文字母算数。

而地方银行、农商行、村镇银行的包名常常是 `com.xxx.mobile` 这种，一个字母关键词都不带 ——
等于她在那些银行里转钱时，根本没有拦截。这是"漏判 = 钱没了"那一类。

修法是把应用名一起传进去（应用名只在包名变化时查一次，`lastPkg` 去重挡着，开销可忽略）：

```java
String label = InstallReceiver.label(ctx, pkg);
if (Judge.isBank(pkg, label)) {
    g.onBankForeground(pkg, label);
}
```

#### 实测（这处必须验，因为它是"漏判"）

在 `D:\华为ict\app\fakebank_zd\` 造了一个测试壳，**包名故意不含任何关键词**：

| | 值 |
|---|---|
| 包名 | `com.zdemo.mobile`（`zdemo`/`mobile` 都不在词表里） |
| 应用名 | 幸福村镇银行 |

```
20:54:02.573  YinDun: 前台出现银行类 App: 幸福村镇银行 (com.zdemo.mobile)
```

完全靠应用名命中中文词「村镇银行」。

反向对照（防止"什么都认成银行"）：打开系统「设置」App，日志里**没有** `前台出现银行类 App` —— 正确。

> 测试壳留着没删（`D:\华为ict\app\fakebank_zd\`），以后改词表可以直接复验。
> 重编时注意 `build_bank.sh` 里那行 `rm -rf build_*` 会把脚本自己也删掉，得先备份。

## 五、补验：远程锁到期会不会自己放开

11-12 那次远程锁只验了"锁上会盖屏"，到期失效一直没验（造不出场景）。这次云端恢复后补上了。

### 怎么造的

`riskUntil` 只存在静态字段里、不落盘，所以只能靠下发指令。云端 `/api/command` 对 minutes
有夹取：`Math.min(120, Math.max(5, Number(b.minutes) || 30))` —— 传 1 会被抬到 5。
所以实际窗口是 **5 分钟**，不是 30 分钟。

```
20:55:46  下发 lock（原始意图 1 分钟，云端夹取为 5 分钟）
20:55:46  老人端：子女远程锁定转账 5 分钟（女儿）
20:55:52  打开假银行 → 子女远程锁定的窗口内打开银行 → 盖屏
21:00:46  （窗口到期）
21:01:09  再次打开假银行 → 只打「前台出现银行类 App」，没有再盖屏
```

**对照是干净的**：两次都是同一个进程（pid 5548），`riskUntil` 是同一个静态变量，
中间没有重启。差别只有时间。

### 顺带复验了 11-12 那个修复

盖屏 6 秒无人操作 → 自动拨号 → 接通那一刻：

```
20:56:03  模拟器上未绑定子女号码，改用演示号码拨出 13800138000
20:56:09  这通电话是银盾自己拨出的（13800138000），按呼出处理，不当作陌生来电
20:56:09  通话开始 who=contact num=13800138000
```

没有再出现 11-12 那种"自己拨的电话被判成陌生来电、导致重复盖屏 + 假警报"。

## 七、一个真机隐患，先记着

`GuardService` 的 `foregroundServiceType` 是 `dataSync`。
**Android 14（API 34）起，`dataSync` 类型的前台服务有每日累计时长上限（6 小时）**，
超时会被系统停掉。模拟器是 API 30，测不出这个问题。

临时对策（不做改动也能说明）：`GuardService.onStartCommand` 返回 `START_STICKY`，
被杀后系统会尽量拉回；加上开机自启，至少重启能恢复。
根治要改前台服务类型（比如 `specialUse`）或改常驻策略 —— 等真机到手、确认目标机型版本再动。
