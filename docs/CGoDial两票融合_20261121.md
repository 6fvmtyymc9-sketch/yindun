# CGoDial 两票融合实测：规则误报 11.7% → 推算 2.9%，红屏 111 条 → 1 条

> 2026-11-21。本机数据 `D:\华为ict\外部数据集\cgodial\`（**按老师要求不进仓库**）。
> 全部数字由 `node cloud/test/cgodial-fusion.js` 实跑得到，可复现。
> 逐条原始返回：`cloud/test/out-cgodial-fusion.jsonl`（660 条，含 AI 的 stage/type/reason）。

---

## 一、一句话结论

在 CGoDial 3,936 条真实政务热线上，**加上 DeepSeek 这一票把规则误报从 11.7% 压到推算 2.9%
（救回 74.8%），把「盖红屏」从 111 条压到 1 条**。

但残余的 116 条误报里 **111 条不是 AI 判错，是规则 S4 托底锁住的**——
AI 已经明确说「正常客服、未涉及钱款」，代码仍强制把它抬回 warn 并推送。

---

## 二、为什么要做这一步

11-20 只测了**规则单票**（见 [CGoDial难负样本复核](CGoDial难负样本复核_20261120.md)）：
3,936 条真实对话误报 460 条（11.7%），其中 111 条判到 block。

**但线上跑的不是规则单票。** `CallAudio.js` 第 160~180 行的融合是：

```js
stage = ai.stage;                                   // AI 说了算
if (localStage >= 4 && stage < 2) stage = 2;        // 只有规则 S4 时托底
// AI 调用失败才退回规则单票
```

所以真正该问的是：**规则那 460 条误报，DeepSeek 能不能救回来？**
这是线上两票的真实表现，从来没测过。本报告就是补这个数。

## 三、方法（口径照抄线上，不自己另定）

| 项 | 取法 | 理由 |
|---|---|---|
| 数据 | 只跑 `kind=real`（3,936 条） | `simu` 是模拟生成，只补量不用于评估 |
| 输入 | `text_asr`，去掉「客服：/来电人：」前缀 | 线上走 SIS 转写，与老师口径一致 |
| 规则 | `scoreSms(body, '', false)` | `who` 传空，与老师口径一致 |
| AI | `Pangu.judgeCall()` | **通话链路用的就是它**，不是 `reviewSms` |
| 融合 | 逐字照抄 `CallAudio.js` | 包括规则 S4 托底 |
| 误报口径 | 最终 `stage >= 2`（warn 及以上） | 与老师 README 一致 |

**分组设计**（两组都要，否则只能看到「救回」，看不到「新增」）：

- **fp 组**：规则已判 warn+ 的 **460 条全跑**，不抽样 —— 这是全部 population
- **base 组**：规则判 S0 的 3,024 条里按场景分层抽 **200 条** —— 看 AI 会不会**自己**抬上去

## 四、结果

### 4.1 fp 组：规则已误报的 460 条

| 最终等级 | 条数 | 说明 |
|---|---|---|
| none（放行） | **344** | AI 救回来了 |
| warn（推送提醒） | 115 | 全部是规则 S4 托底，不是 AI 判的 |
| block（盖红屏） | **1** | 唯一一条 AI 也判诈骗 |

| 指标 | 数值 |
|---|---|
| AI 救回 | **344 / 460 = 74.8%** |
| 融合后仍误报 | 116 / 460 = 25.2% |
| 融合后仍 block | **1 / 460 = 0.2%**（规则单票是 111 条） |

**AI 在这 460 条上给出的 stage 分布**：0 → 455 条、2 → 4 条、4 → 1 条。
也就是说 **AI 有 99% 的时候正确识别为「正常客服」**。

| 场景 | 误报样本 | 融合后仍误报 | 仍 block |
|---|---|---|---|
| gov | 438 | 111 | 1 |
| etc | 11 | 2 | 0 |
| jiaoguan | 11 | 3 | 0 |

### 4.2 base 组：规则判 S0 的 200 条对照

**AI 独自误报 0 条**（200 条 AI 全给 stage 0，最终全是 none）。

这条很重要：它说明上面那 116 条误报**没有一条是 AI 自己造出来的**，
全部来自规则那 460 条里没被清干净的部分。

### 4.3 全量推算

| | 规则单票 | 两票融合 |
|---|---|---|
| 误报 | 460 / 3,936 = **11.7%** | **116 / 3,936 ≈ 2.9%** |
| 盖红屏（block） | 111 条 | **1 条** |

推算方式：fp 组 460 条全测（实测 116），base 池 2,510 条抽 200 条零误报（推算 0 条）。
**这是推算，不是全量实测**，误差来源见第六节。

## 五、真正的发现：规则 S4 托底是最大误报来源

把 116 条按融合依据拆开：

| 依据 | 条数 | 含义 |
|---|---|---|
| `ai+rule-floor` | **111** | **AI 判 0（正常），但规则判 S4，被强行抬回 warn** |
| `ai` | 5 | AI 自己判到 ≥2（其中 4 条 warn、1 条 block） |

**95.7% 的残余误报不是模型判错，是那段托底代码造成的。** 典型例子（原文来自 jsonl）：

```
[gov] 规则 4 → AI 0 → 最终 2 warn
     AI 理由：「智能客服引导公积金医保咨询，无诈骗特征」
[gov] 规则 4 → AI 0 → 最终 2 warn
     AI 理由：「医保客服正常应答，未涉及钱款或个人信息」
```

托底的设计初衷是对的——**防 AI 漏报**（AI 判 0 但规则判 S4 时别直接放行）。
但它分不清两种冲突：

- 规则对、AI 漏了 → 托底救命
- 规则错、AI 对 → 托底制造误报

### 30 通评估集上，托底一次都没用上

对照 `cloud/test/calls_eval/out-fusion.json`：30 条的融合依据**全部是 `ai`，没有一条
`ai+rule-floor`**。也就是说在这批真实诈骗录音上，AI 自己就判到了 stage 4，
**托底从未触发过**；而在 CGoDial 上它制造了 111 条误报。

## 六、这份数字的使用边界（材料里不许省略）

1. **方向相反，不能当线上误报率。** CGoDial 是**市民打给政务热线**（机器人客服应答），
   不是「陌生机构打给老人」。它的价值是用机构话术（自报业务、引导办理、公积金医保 ETC）
   给规则做压力测试，**不是估计真实场景的误报**。
2. **长对话超纲使用。** 每条是 10 轮以上、数百字的整通对话，而 `judgeCall` 的提示词
   是照「一通电话的录音转写」写的。真实通话也长，但话题密度不同。
3. **全量数字是推算。** fp 组全测、base 组只抽 200 条，所以 2.9% 有抽样误差；
   严格说法是「推算约 2.9%」。
4. **只测了误报，测不出漏报。** 这批数据没有诈骗样本，漏报要另一套数据（30 通评估集）来看。
5. **AI 缺席 0 条是限速换来的。** 见第七节，正常不限速调用时会偶发坏 JSON 与 429。
6. **`simu` 18,104 条没测**，不用于评估。

## 七、踩过的坑（留给下一次）

### 7.1 并发打爆了 DeepSeek 的限流，第一轮结果全部作废

第一次用 **8 并发**跑，660 条里 **466 条的 AI 票根本没调成功**（HTTP 429：
「4 per second」「100 per minute」两条限制），退回规则单票后，误报率被算成 **48%**——
那个数是并发造成的假象，不是模型表现。

修正：全局节流到 **1.4 次/秒（84 次/分钟）** + 单条重试 4 次（退避 0.6/1.2/1.8 秒），
重跑后 **660/660 全部拿到结论、0 条缺席**，耗时 8 分 54 秒、花费 ¥0.63。

**教训：算误报率之前先看覆盖率。** 覆盖率不到 100% 时，缺席的条目会被算成误报，
数字会系统性偏高。脚本现在把覆盖率单独打在最前面。

### 7.2 第一次跑忘了过滤 `kind=real`

把 18,104 条 `simu` 也算进来了（22,040 条），分组数字完全不对。
加上过滤后回到 3,936 / 460，与 11-20 文档逐格一致才敢继续。

### 7.3 别把结果写进 `calls_eval/`

那个目录 2026-11-21 已冻结只读。本脚本输出在 `cloud/test/out-cgodial-fusion.jsonl`。

## 八、一个可以提、但**还没做**的改进

**规则 S4 托底分档**：

```
现在：规则 S4 + AI < 2  →  一律抬到 warn（会推送）
提议：规则 S4 + AI = 0  →  只抬到 watch（记录，不推送）
      规则 S4 + AI = 1  →  仍然抬到 warn（AI 也说可疑）
```

- 支持的理由：AI 在 455 条上给出了有理由的判断（「正常客服、未涉及钱款」），
  强制推送等于用一个主观分数否定一个更好的判断；30 通评估集上托底一次没用上。
- 反对的理由：**n=15 的诈骗样本不足以证明 AI 不会漏。** 如果真实诈骗里出现
  「规则看到要钱词、AI 觉得是正常客服」，放松托底就是漏报。

**所以这条只写进待办，没有改代码。** 要动它，先在更大的诈骗样本上验证 AI 的漏报率。

## 九、复现

```bash
cd D:/华为ict/交付_银盾_GitHub

# 冒烟（6 条，约 10 秒）
node cloud/test/cgodial-fusion.js --limit 6

# 本报告的全量（460 + 200，约 9 分钟，约 ¥0.6）
node cloud/test/cgodial-fusion.js --conc 3 --n 200

# 只看规则已误报的那 460 条
node cloud/test/cgodial-fusion.js --group fp

# 规则单票（11-20 那份，对照用）
node cloud/test/cgodial-fp.js
```

⚠️ **不要调大 `--conc`。** 云端限流是每秒 4 次 / 每分钟 100 次，超过就 429，
结果会被污染成"误报"。脚本默认并发 3 + 全局 700 ms 节流。
