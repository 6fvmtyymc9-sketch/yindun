## 一、结论先行

**做了两轮，跑通了，结论是：LoRA 能把塌缩治好、能把分布外性能拉回基线，但这一轮的规模还不足以超过基线。**

第一轮（正常侧只有 CGoDial 长对话）出现塌缩：同源分布极好、真实分布全崩。

| 老师定的成功判据 | 目标 | 第一轮 v1 | 第二轮 v2（补正常短信） | 判定 |
|---|---|---|---|---|
| CGoDial 留出 300 通正常，误报 | 降到两成以下 | **1 / 300（0.33%）** | **1 / 300（0.33%）** | ✅ 两轮都达成 |
| holdout 诈骗召回 | ≥ 19/20 | **20 / 20** | **17 / 20** | ⚠️ v1 达成，v2 掉了 3 条 |
| 30 通真人录音正常，误报 | 要下降（基线 10/15） | **15/15**（恶化） | **音频 8/15、文字 11/15** | ⚠️ v2 消除塌缩，音频略优于基线、文字略差 |

**第一轮暴露问题，第二轮验证诊断并部分修复。** 这个顺序比直接报一个漂亮数字更有价值——它把"为什么失败"变成了可复现、可修正的结论：

> 只要正常侧只有一种文风，模型就学会"认文风"而非"认诈骗"，在真实分布上一律判是。把正常侧换成"长对话 + 短营销短信"各一半、其余一个参数不动，塌缩随即消失（30 条里首次出现判否、reason 从 5 种增至 7 种），分布外误报回到基线水平。

**但 v2 并没有超过原模型**，且诈骗召回下降了 3 条。所以最终结论是：

> **当前 1,900 条 / 2 epoch 的规模只够"修复塌缩"，不够"超越基线"。** 要让 LoRA 真正产生价值，需要更大的、多源分层的正常数据（见第五节）。

**三条不能说的话**：不能说"LoRA 无效"（同源 82%→0.33% 是真的）；不能说"误报降到 0.33%"（那是同源分布）；不能说"v2 已经比原模型好"（召回掉了 3 条）。

## 二、第一轮训练做了什么

### 2.1 数据

用 `tools/build_judge_data.py` 生成，脚本从 `tools/sft_server.py` 直接 import 提示词，**训练与推理的 prompt 一字不差**。

| 集合 | 条数 | 正负 | 来源 |
|---|---|---|---|
| train | 1,900 | 诈骗 952 / 正常 948 | 正常：CGoDial `real` 政务热线 ASR；诈骗：`Telecom_Fraud_Texts_8` 五个类别 |
| val | 100 | 均衡 | 从 train 切 5% |
| heldout_cgodial | 300 | 全正常 | CGoDial 按场景配额留出（gov 200 / 交管 40 / etc 40 / 珠宝 20） |
| **leak_check** | — | — | **0**（文本级去重，防止 CGoDial 常见开场白造成 id 不同的重复泄漏） |

诈骗五类取自 `Telecom_Fraud_Texts_8`（`tools/build_fraud_texts.py`，可复现）：冒充公检法 1,565、贷款征信 1,218、客服退款 1,502、冒充熟人 1,426、刷单返利 3,416，合计 9,127 条，按 `--per-class` 抽样。

**这里已经埋下了本实验最大的缺陷**：正常侧 100% 是政务热线长对话（100~800 字、客服腔、ASR 连续文本），诈骗侧 100% 是短信短文本。两侧的**文体与长度分布完全错开**。

### 2.2 配置

与原始 `AntiFraud-SFT/args.json` 对齐（除了学习率）：

| 参数 | 值 | 与原模型对比 |
|---|---|---|
| `train_type` | lora | 同 |
| `lora_rank` / `alpha` | 32 / 32 | 同 |
| `target_modules` | `all-linear` | 同 |
| `freeze_vit` / `freeze_aligner` | True / True | 同（音频编码器与投影层冻结） |
| `loss_scale` | **last_round** | 同（只对第二轮"结论"算 loss，不学人造的场景标签） |
| `learning_rate` | **1e-4** | 原模型 5e-5，本次提高一档 |
| `num_train_epochs` | 2 | 同 |
| `max_length` | 2048 | 同 |
| `bf16` / `gradient_checkpointing` | True / True | 同 |
| 有效批 | 2 × 8 = 16 | — |

可训练参数 **7,995 万**（占全模型 0.94%）。

### 2.3 训练结果

```

train_loss 0.1319 ｜ eval_loss 0.0013 ｜ eval_token_acc 0.9995 ｜ 显存 23.8 GB
```

**训练 loss 低不代表模型变好**，这一点在本实验里被完整验证：`eval_loss 0.0013` 的模型在真实分布上误报 100%。原因见第四节。

## 四、第一轮的根因：模式塌缩 + 认文风

### 4.1 塌缩的直接证据

30 通真人录音（文字模式）里，LoRA 只输出了 **5 种不同的 reason**，其中 17 条是同一句：

```
17× 冒充老师、领导或亲友，以代购、垫付、急用钱为由要求转账
 4× 以点赞、刷单、做任务返利为名，诱导下载软件或先垫付资金
 3× 冒充平台客服，以退款、理赔为名诱导操作账户或提供验证码
```

而 base 模型在 CGoDial 300 条上给出 **293 种不同 reason**。塌缩是微调引入的，不是原模型的问题。

### 4.2 机理

1. 训练集正常侧 100% 是 CGoDial 政务热线：长、客服腔、ASR 连续、无口语碎片。
2. 训练集诈骗侧 100% 是短信：短、模板化、必含索款或链接。
3. 在只有两类、且两类在**长度和文体上完全可分**的数据上做 SFT，最小化 loss 的最短路径是学"长文客服腔 → 否，短句 → 是"，而不是学诈骗语义。
4. 真实分布（老人收到的短信、家里人的电话）恰好落在"短句"一侧 → 一律判是。

**这不是 LoRA 的失败，是训练数据构建的失败。** 与 11-20 那次"SFT 恒答是"的性质不同：那次是负样本答案没进 loss（数据标注缺陷），这次是负样本进了 loss 但分布太单一（数据覆盖缺陷）。

### 4.3 为什么 CGoDial 上看起来完美

CGoDial 留出 300 条与训练集**同源**：同一批政务热线、同一套 ASR 输出、同样的客服腔。模型在上面 99.7% 判否，本质是**认出了熟悉的文体**，而不是判断出"这不是诈骗"。

所以"误报降到 0.33%"这个数字，**只能说明模型能拟合训练分布，不能说明它具备反诈判别力**。任何把这一行单独摘出来宣传的写法都是不诚实的。

## 五、第二轮：按诊断补数据后的对照（验证"根因是不是数据"）

第四节给出的诊断是"训练数据正常侧来源单一"。**这个诊断必须被验证，否则只是猜测。** 于是当天中午立刻做了第二轮：只改一处——正常侧混入营销短信。

### 5.1 唯一变量

| | 第一轮（v1） | 第二轮（v2） |
|---|---|---|
| 正常侧 | **100% CGoDial 政务热线**（长对话，100~800 字） | **50% CGoDial + 50% 营销通知短信**（`Telecom_Fraud_Texts_8` 的 `label0`，17,048 条中可用 11,784 条，中位 85 字） |
| 诈骗侧 | 五类短信，1,000 条 | 完全相同 |
| 数据量 / epoch / 超参 / 留出集 | 1,900 × 2，其余全同 | 完全相同 |
| train_loss / 用时 | 0.1319 / 14.3 min | 0.1353 / 13.9 min |

`label0` 那批是联通、京东等营销短信，含"点击链接""限时""免费领取"这类**与诈骗短信高度相似的词**，只是意图合法——正是我们缺的"像诈骗的正常短文本"。

### 5.2 结果对照（三档：base / v1 / v2）

| 评测集 | 口径 | base | v1（纯长对话） | **v2（混入短信）** |
|---|---|---|---|---|
| CGoDial 300（同源正常） | 模型结论 | 246/300 | 1/300 | **1/300** |
| holdout 诈骗 20（短信） | 模型结论 | 20/20 | 20/20 | **17/20** |
| holdout 正常 15（短信，分布外） | 模型结论 | 6/15 | **13/15** | **6/15** |
| 真人录音 30 · 文字 | 模型结论 | 10/15 | **15/15** | **11/15** |
| 真人录音 30 · 音频 | 模型结论 | 10/15 | **15/15** | **8/15** |
| 真人录音 30 · 音频 | 诈骗召回 | 15/15 | 15/15 | **15/15** |

（表内"误报"均指正常样本被判诈骗数）

### 5.3 三个结论

1. **诊断被证实。** 只补正常短信、其余一个字不改，塌缩就从"30 条全判是、只有 5 种 reason"变成"30 条里 7 条判否、6~7 种 reason，且首次出现「这是一通关于日常事务的正常业务沟通」这类判否理由"。**所以根因确实是数据分布，不是 LoRA、不是音频通道、不是训练配置。**

2. **短信域基本恢复，通话域只是回血。** holdout 正常（短信）从 13/15 回到 **6/15**，与 base 持平；真人录音音频从 15/15 回到 **8/15**，比 base 的 10/15 还稍好；文字模式 11/15，比 base 的 10/15 略差。**两条都不再塌缩，但都没有明显超越原模型。**

3. **代价是诈骗召回下降。** holdout 从 20/20 掉到 **17/20**（漏 3 条），这是加入了大量"含链接但不诈骗"的营销短信后，模型对含链接的诈骗变宽松了。真人录音的 15/15 召回没掉。

### 5.4 这说明什么

**方向对了，力度不够。** 1,900 条、2 epoch 的数据量，只够把模型从"塌缩"拉回"接近原模型"，不足以让它超过原模型。想让 LoRA 真正有价值，需要：

- 正常侧继续扩源：真人电话口语转写（当前只有 30 条评估集，不能用于训练）、快递/外卖/医院回访等场景
- 数据量提到 1 万条以上、按长度与场景分层
- 单独调"含链接"这一类的正负配比——它是当前唯一确定变差的子集

**仍然不能说 LoRA 成功。** 准确表述是：**v2 消除了塌缩、把分布外性能拉回基线水平，但没有超过基线；要超过，还需要更大的、多源的正常数据。**

## 七、下一步建议（给老师）

**第五节的第二轮已经做过第 1 条的一半**（正常侧混入营销短信，占比 50%），效果是"消除塌缩、回到基线"。要再往上走，按性价比排序：

1. **继续扩正常侧的来源**（已验证方向有效，缺的是量与多样性）
   - ✅ 已做：短信正常侧 `label0` 17,048 条营销/通知短信，混入 50%
   - ⏳ 待补：**通话正常侧的多场景**——快递、外卖、医院回访、维修、村委通知等。当前真人电话误报 8/15（音频），是所有指标里最弱的一环，而这一类恰恰是老人最常接的电话
   - ⏳ 待补：真人电话的**口语转写**（现有 30 通评估集已冻结，不能用于训练，必须另录或另采）

2. **提高数据量**：v2 仍是 1,900 条 / 2 epoch。按经验，要让 LoRA 超过 base，同任务数据量至少要 5,000~10,000 条，且正负与场景都要分层

3. **按长度分层抽样**，保证"短正常"与"短诈骗"、"长正常"与"长诈骗"都有样本，打断"长度→标签"的捷径

4. **单独调"含链接"子集**：v2 唯一确定变差的是 holdout 诈骗召回（20→17），三条漏报全部含链接/要求点击。加入大量"含链接但合法"的营销短信后，模型对链接的敏感度被稀释了，需要针对这一子集补正样本

5. **加一个反捷径检查**（写进评测脚本）：分别统计短文本（<60 字）和长文本（≥60 字）上的误报率，若两者差距 >30 个点，说明模型仍在认文风

6. 数据补齐后重训，仍用同一份 CGoDial 留出 300 + holdout 35 + 30 通真人录音三套一起验，**三套都过才算过**

**关于线上**：两轮结果都不支持接入。`SFT_URL` 继续留空，理由更新为"v2 已消除塌缩但仅回到基线水平、且召回下降 3 条，需扩数据后重测"。

## 八、边界说明（引用数字时必须连带引用）

1. **训练 loss 0.0013 不代表模型好**，本实验就是反例，任何汇报都不要单独引用 loss。
2. **CGoDial 300 条与训练集同源**，0.33% 不能当作泛化能力；两轮都是这个数，因为它测的就是"拟合没拟合上"。
3. **30 通真人录音样本极小**，15 条正常里多错 5 条就是 33 个点的差异，只能定性说"改善/恶化"，不能报具体提升百分比。
4. **两轮都是 1,900 条、2 个 epoch**，未做超参搜索；结论只针对这组配置，不能外推成"LoRA 在该任务上的能力上限"。
5. **v1 里音频与文字模式的结论一致**（都是 15/15），说明瓶颈不在音频通道，而在数据分布——这一点很重要，它排除了"必须用音频才能判"的另一种解释。
6. **不能说"LoRA 无效"**：同源分布上 82%→0.33% 是真实的，模型确实学会了说"否"，只是 v1 学错了依据。
7. **也不能说"v2 已经比原模型好"**：v2 的音频误报 8/15 略优于 base 的 10/15，但文字 11/15 略差、holdout 召回 17/20 低于 base 的 20/20。**整体是"回到基线"，不是"超过基线"。**
8. **holdout 那 15 条正常样本是人工构造的短信**，不是真实用户收到的消息，它只能证明"分布匹配与否"，不能当线上误报率。
