# 短信同号累计规则

> 2026-11-17 实现，对应第三批送审的判定链增量。
> 代码：`app/src/com/yindun/guard/RepeatSms.java`、`SmsReceiver.poolRepeat()`、`Judge.mergeBurst()`

## 一、问题从哪来

2026-11-16 真机上，老人收到同一个陌生号码发来的三条短信：

```
我是警察
赚钱
转钱
```

单条判分：

| 短信 | 得分 | 阶段 | 级别 | 后果 |
|---|---|---|---|---|
| 我是警察 | 65 | S3 | high | 弹浮条 |
| 赚钱 | 15 | S1 | watch | **一声不响** |
| 转钱 | 35 | S1 | watch | **一声不响** |

后两条完全没反应。可这三条连起来是「亮身份 → 抛诱饵 → 催转账」的完整剧本。

**根因不是阈值没调好，是结构问题**：系统按条独立判分，剧本被切碎了。
骗子只要把一套话拆成几条发，每条都能压在报警线以下，永远不触发。
调低阈值能救这一次，但正常短信会开始误报，老人一旦觉得「这玩意儿老瞎叫」就去关权限 —— 比漏报更致命。

## 二、做法

同一号码在 **10 分钟**内发来 **3 条及以上**时，把各条合起来再判一次。

### 合并公式

```
合并分 = 15（陌生号码基础分，只算一次）
       + Σ 各条的实质分
       + 连发加成
```

- **实质分** = 单条规则分 − 15（扣掉陌生号码那一次基础分，避免三条白拿三次）
- **连发加成** = 从第 3 条起每条 +15，即 `(条数 − 2) × 15`

### 只累计陌生人

| 排除哪种 | 为什么 |
|---|---|
| 通讯录里的人 | 连发三条是家常事（先发文字再发图片） |
| 服务号 | 连发三条是业务通知（银行动账、快递进度） |
| 验证码短信 | 按「谁发的」单独判，混进累计会互相污染 |
| 官方宣传短信 | 已经豁免过，不该被翻旧账 |

剩下的只有一种：陌生人反复发。这本身就是一个信号。

### 只算规则分，不算模型分

`Judge.Result` 拆出两个字段：

- `score` —— 最终分，可能被端侧模型抬过
- `ruleScore` —— 纯规则分，模型没参与

累计只用 `ruleScore`。

**为什么**：实测踩到的坑 —— 一条正常快递短信「请及时取件」，规则判 0 分，端侧小模型却给了 94%，被抬到 warn(45)。
如果累计拿 `score` 去加，模型这一次误报会被当成"实质证据"滚进累计，
三条正常快递短信合起来就凑到 60 分报警。
**模型说不出"这是个剧本"，累计要的恰恰是剧本证据。**

### 只抬不降

合并分没有超过单条分时原样返回，不会把一条已经明确高危的短信"平均"下来。

### 落盘，不放内存

`SharedPreferences`（`yd_repeat_sms`），每个号码一条记录：
`首条时间,末条时间,条数,实质分和,最高阶段序号,正文hash`

**为什么**：短信广播来时进程可能是被系统刚拉起的，判完又可能被回收。
内存计数撑不过两条短信之间的空闲。实测：杀掉进程后第 4 条仍然接上了计数。

其它细节：
- 窗口过期（超 10 分钟）自动从头算
- 同一条短信被重复广播（EMUI/MTK 见过，双卡也可能各报一次）5 秒内同正文只计一次
- 号码归一化：去掉空格、短横、`+86` / `0086` 前缀
- 最多保留 24 个号码的记录，超了删最旧的

## 三、实测结果

模拟器（Android 11，端侧模型在跑）：

| 场景 | 单条 | 合并后 | 结论 |
|---|---|---|---|
| 15300000004：「我是警察」「赚钱」「转钱」 | 65 / 15 / 35 | 第 3 条 **100 分 block** | ✅ 弹红色浮条 |
| 15300000004 被杀进程后再发第 4 条「你先把钱转过来」 | 15 | **115 分 block** | ✅ 计数接续，说明落盘生效 |
| 15300000003：三条正常快递短信 | 0 / 0 / 0 | 30 分（不合并） | ✅ 不误报 |
| 15300000005：「转账」「银行卡」两条 | 30 | 不构成连发 | ✅ 不合并 |
| 15300000002：三条快递（旧代码） | 0 / 0 / 45 | 60 分 warn | ❌ 旧代码把模型分算进去了，已修 |

第 2 行值得单独说：「你先把钱转过来」单条只有 15 分（词表里没有「转过来」这个说法），
是累计把它救回来的 —— 这也印证了累计的价值不在"加几分"，而在"把同一来源的多条当成一件事看"。

## 四、已知风险与未做的事

1. **云端没有同步这套规则**。`cloud/src/Judge.js` 只做单条复核，拿不到同号上下文。
   端侧是实时链路，云端是事后复核，影响有限；要补得让云端查短信记录表。
2. **端侧模型误报仍在**（与累计无关）：
   - 「请及时取件」→ 94%、「转账」→ 52%，单独一条就会弹 warn
   - 留出集（35 条）上模型是 6.7% 误报 / 10% 漏报，把阈值从 0.5 提到 0.9 指标完全不变，
     说明**调阈值救不了**，得换模型（等 SFT / GPU 服务器）
   - 这次的改动只是确保模型误报**不会**被累计放大
3. **3 条起算门槛是拍的**。10 分钟窗口也是。有真实误报数据后再调。
   参数集中在 `RepeatSms.java` 顶部四个常量，改完要重跑下面这组验证。

## 五、复验方法

```bash
# 三条诈骗剧本，同一号码
adb -s emulator-5554 emu sms send 15300000004 "我是警察"; sleep 4
adb -s emulator-5554 emu sms send 15300000004 "赚钱";     sleep 4
adb -s emulator-5554 emu sms send 15300000004 "转钱";     sleep 4
adb -s emulator-5554 logcat -d | grep -E "短信累计|同号连发"

# 三条正常短信，换一个号码，应当不报
adb -s emulator-5554 emu sms send 15300000003 "您的快递已到菜鸟驿站"
adb -s emulator-5554 emu sms send 15300000003 "取件码 8321"
adb -s emulator-5554 emu sms send 15300000003 "请及时取件"
```

判据：看到 `★ 同号连发合并` 说明合并生效；三条正常短信**不该**出现这一行。
