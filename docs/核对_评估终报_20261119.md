## 二、核心问题：「规则漏报 50%」用错了门槛

### 他的数字是对的，我复现了

| 他报的 | 我复算 |
|---|---|
| 阶段 ≥ S2 → 35.3% | 35.2% |
| 阶段 ≥ S3 → 50.0% | 49.8% |
| 阶段 ≥ S4 → 54.7% | 48.5%（这一档略有差，可能样本边界） |

算法没错。问题在**门槛是他自己设的**——他自己也写了「服务端没有只跑规则的开关，门槛是脚本设的」。

### 服务端的真实门槛在哪

`cloud/src/server.js:597`：

```js
const isFraud = ai ? ai.isFraud : local.level !== 'none';
```

`cloud/src/Judge.js` 的 `levelOf()`：

```js
case 'S2': return 'warn';
case 'S1': return 'watch';
default:  return 'none';      // 只有 S0 才是 none
```

**所以服务端认为「命中 S1（15 分）就算诈骗」，不是 S2，更不是 S3。**

按这个真实门槛，1,070 条的结果：

| 口径 | S0（漏） | S1 | S2 | S3 | S4 | 真实漏报率 |
|---|---|---|---|---|---|---|
| 线上 `who=''`（现状） | 201 | 176 | 156 | 52 | 485 | **18.8%** |
| App `who='stranger'`（+15 分） | 45 | 192 | 211 | 71 | 551 | **4.2%** |

### 所以真实情况是：这是两层门槛，不是一层

| 你要测什么 | 门槛 | 漏报率 |
|---|---|---|
| **识别**：有没有被认出来（子女端收到提醒） | stage ≥ S1 | **18.8%** |
| **拦截**：有没有红屏挡住（`server.js:635` 要求 `isFraud && stage >= 3`） | stage ≥ S3 | **50.0%** |

**两个数都对，但必须标清是哪一层。** 对外只说一个数一定被追问。

建议报告里这样写：

> 规则引擎在 1,070 条诈骗文本上：识别层（S1 起，推送给子女）漏报 18.8%；
> 拦截层（S3 起，红屏阻断）漏报 50.0%。两者差异来自 S1/S2 只提醒不拦截，属设计如此。

## 三、50% 和 14.6% 不是同一个口径，不能并列

现在报告里是：

```
规则                    漏报 50.0%
线上融合(规则+DeepSeek)   漏报 14.6%
```

- 规则的 50.0% 是 **stage ≥ S3**
- 融合的 14.6% 是**顶层 `isFraud`**（也就是 DeepSeek 的判定）

两个门槛不同，并列会造出「DeepSeek 把漏报从 50% 降到 14.6%，改善 35 个点」的结论。

**同一口径下的真实对比**是：

| 同用「识别层」（stage ≥ S1 / isFraud） | 漏报率 |
|---|---|
| 纯规则 | 18.8% |
| 规则 + DeepSeek 融合 | 14.6% |

**改善 4.2 个百分点，不是 35 个。** 这个结论对产品评价影响很大，宁可自己说清楚，
也别让评委替我们算出来。

（如果确实想说「DeepSeek 救回了很多」，正确表述是：在**拦截层**，DeepSeek 把 50% 的漏报
压到 14.6%，因为它能把规则漏掉的 S3 级话术认出来。但这不等于它比规则强 35 个点。）

## 四、必须补的第 5 条 caveat（最危险的一条）

Fraud-R1 的 `generation model` 字段，每一条都是 **`deepseek-r1`**。

**用 DeepSeek 评判 DeepSeek 生成的内容，存在同源偏差，14.6% 这个数会虚高。**

而且 `category: phishing` / `subcategory: phishing email`，中位长度 702 字符——
**这是钓鱼邮件，不是短信，更不是通话**。他 caveat 第 1 条写「短信/邮件形态」，
建议直接改成「钓鱼邮件形态」。

补一条：

> 5. Fraud-R1 的文本由 DeepSeek-R1 生成，本项目用 DeepSeek 做文本复核，存在同源偏差，
>    「融合 14.6%」应视为**上限估计**，不能等同于对真实人写诈骗短信的识别率。

## 五、两处认知要更新

他说「端侧 TinyBERT 实现未给 / SFT GPU 隧道未通，表里留 `--`」——这两条已经过时：

- **SFT 隧道 11-18 晚已打通**，云端 `curl 127.0.0.1:8099/health` → 200/84ms，
  `/risk` → 200/158ms。现在可以跑「录音 → SFT」那一路了。
  但注意：SFT 只能评音频，Fraud-R1 是文本，所以**文本评估里 SFT 那栏留 `--` 是对的**，
  理由要改成「模型为音频模态，不适用于文本样本」。
- **端侧 TinyBERT 在 App 里有实现**（`app/src/com/yindun/guard/TinyBert.java`），
  缺的是模型权重文件，不是代码。
